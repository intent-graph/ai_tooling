Ledger row ids (`Lnnn`) refer to the consolidated claims ledger; source ids `SRC-nnn` refer to its source list; D1, D2, C2 and C3 refer to the maintainer questions file. All claims are restated as generic database and architecture rules.

## L1 headline

The maintainer's codified database practice is a rich, largely coherent doctrine that mostly agrees with the research on declarative integrity, naming and migration, extends it on keys, caches, JSON contracts, write ordering and bulk execution, and contradicts it on five points (soft delete as default, a shared database behind a function API, views excluded, logic placed in the database, updated_at set by the writer); certainty is grounded in the doctrine's own text, not checked against the running system.

Where the doctrine disagrees with itself (each is a gap in the maintainer's record, not in the research):
- Soft delete is called the primary driver of key choice in one guideline and independent of composite keys in the architecture note; partial indexes work with any key, so that rationale does not carry the composite choice.
- No application role holds DELETE, yet the archive-then-delete rule and cache invalidation need it; one admin role holds it for the invalidation functions.
- Views are rejected in the architecture note, recommended for active-row filtering in the temporal guideline, and materialized views are 'not used'.
- Validation is described as enforced where the data lives, while the same pages say it currently runs inside functions with triggers optional, and a best-practice list says to validate at the application layer; a direct write can bypass function-level validation.
- Where asynchronous work runs is not single: an in-database scheduler, an external poller for the cache queue, and a queue-driven worker with a lease all appear.
- The cache refresh example loops row by row although the function guideline forbids loops, and no page says how concurrent consumers of the invalidation queue avoid double work.

### Answers to maintainer questions

**D1, primary-key type (`DATA.SCHEMA.3`).** The doctrine does not pick one global type; it picks by table shape. Single-key tables use identity columns, not serial (MAINT-C04), sized by expected cardinality: 4-byte integer under about two billion rows, 8-byte for very large tables or keys referenced by large tables (MAINT-C05). Scoped tables use a composite key that leads with the scope column, at most about four columns (MAINT-C01, MAINT-C02, MAINT-C03). UUIDs only for global uniqueness, external integration or sequence contention, never as the default; a deterministic UUID may be derived from a composite natural key (MAINT-C06). It is silent on time-ordered UUIDs and on enumeration risk. Against the research: agrees on identity over serial (L177) and on random UUIDs not being a default (L179); differs from the D1 recommendation (bigint by default) only in default width, and adds composite scope-leading keys, which the research does not cover. Suggested record: identity by default, width by cardinality, composite for scoped tables, UUIDv7 left to the maintainer because the doctrine has no position.

**D2, deletion (`DATA.LIFECYCLE.1`).** Per-table gradient by retention need: full version history, partial soft delete, archive table, plain hard delete (MAINT-C18). Soft delete is the default for user-facing transactional data (about 60% of tables), marked by a nullable deleted_at (MAINT-C19). Its cost is paid explicitly: constraints and uniqueness exempt deleted rows (MAINT-C11), cascades re-implement the foreign-key graph in dedicated functions (MAINT-C20, MAINT-C21), hard delete only for rebuildable caches or after an archive copy, and no DELETE grants (MAINT-C22). Against the research: agrees with L205 (decide per entity) and with the archive option of L204; contradicts the D2 recommendation (hard delete plus same-transaction archive by default, soft delete only where the product offers undo), which rested on one critique and no defender. The doctrine is that defender, with the mitigations the critique says are missing. Suggested record: the maintainer's soft-delete-by-default, with the five mitigations as its conditions.

**C2, logic in the database (`DATA.LOGIC`).** Default is application code; a function is created only when it earns its cost by reuse across consumers, hiding internals, database-owner-tunable performance, or integrity beyond constraints (MAINT-C42). Once past that gate, a wide band lives in the database: cascades, multi-table atomic validation, state transitions with logging, set-based algorithms over large data (MAINT-C44); the doctrine lists the costs it accepts (MAINT-C45) and its conventions (MAINT-C46, MAINT-C47). Triggers are used for validation, integrity and per-scope schema enforcement, not for updated_at (MAINT-C17, MAINT-C37). Against the research: agrees with the cost-benefit gate and application-first default (L214, L215, L041, L042); contradicts the C2 recommendation (domain logic and workflow in Python, the database for invariants and narrow triggers) and L215 in extent, on where cascades, multi-table validation and state logic live; it is the heavier-database position that L214 records with T4 support only, now with a practitioner behind it. Suggested record: the maintainer's four-reason gate plus the listed in-database band, with the research split kept as the default for projects with a single application.

**C3, contract schema (`DATA.ACCESS.2`).** Functions are the contract between the database and several backends; the signature is stable and the body tunable (MAINT-C41). Views are explicitly rejected, base tables stay directly queryable for simple reads, and the ladder is query, then function, then procedure (MAINT-C43). The contract evolves additively with coordinated breaking changes and no version numbers (MAINT-C47). Against the research: agrees with the function half of L187 and contradicts its view half; contradicts L044 (one application owns its database) because the doctrine's database is shared by many backends. For a single application that owns its database the doctrine is silent, so the C3 recommendation (base tables through the ORM, views for reporting) is neither supported nor refuted for that case. Suggested record: function contract when two or more consumers share the database, with views excluded, and base tables for a single owner.

Not covered (single private source): partitioning and retention by partition drop, time-ordered UUIDs, isolation levels and optimistic concurrency, the atomic hand-off to an external broker, ORM practice, backup and high availability, sessions, whether row-level policies are deployed. Style rules for SQL formatting and test-script mechanics were skipped as instructed.

### Doctrine-internal tensions

1. Soft delete is called the primary driver of key choice in one guideline and independent of composite keys in the architecture note; partial indexes work with any key, so that rationale does not carry the composite choice.
2. No application role holds DELETE, yet the archive-then-delete rule and cache invalidation need it; one admin role holds it for the invalidation functions.
3. Views are rejected in the architecture note, recommended for active-row filtering in the temporal guideline, and materialized views are 'not used'.
4. Validation is described as enforced where the data lives, while the same pages say it currently runs inside functions with triggers optional, and a best-practice list says to validate at the application layer; a direct write can bypass function-level validation.
5. Where asynchronous work runs is not single: an in-database scheduler, an external poller for the cache queue, and a queue-driven worker with a lease all appear.
6. The cache refresh example loops row by row although the function guideline forbids loops, and no page says how concurrent consumers of the invalidation queue avoid double work.

### Answers to maintainer questions

**D1, primary-key type (`DATA.SCHEMA.3`).** The doctrine does not pick one global type; it picks by table shape. Single-key tables use identity columns, not serial (MAINT-C04), sized by expected cardinality: 4-byte integer under about two billion rows, 8-byte for very large tables or keys referenced by large tables (MAINT-C05). Scoped tables use a composite key that leads with the scope column, at most about four columns (MAINT-C01, MAINT-C02, MAINT-C03). UUIDs only for global uniqueness, external integration or sequence contention, never as the default; a deterministic UUID may be derived from a composite natural key (MAINT-C06). It is silent on time-ordered UUIDs and on enumeration risk. Against the research: agrees on identity over serial (L177) and on random UUIDs not being a default (L179); differs from the D1 recommendation (bigint by default) only in default width, and adds composite scope-leading keys, which the research does not cover. Suggested record: identity by default, width by cardinality, composite for scoped tables, UUIDv7 left to the maintainer because the doctrine has no position.

**D2, deletion (`DATA.LIFECYCLE.1`).** Per-table gradient by retention need: full version history, partial soft delete, archive table, plain hard delete (MAINT-C18). Soft delete is the default for user-facing transactional data (about 60% of tables), marked by a nullable deleted_at (MAINT-C19). Its cost is paid explicitly: constraints and uniqueness exempt deleted rows (MAINT-C11), cascades re-implement the foreign-key graph in dedicated functions (MAINT-C20, MAINT-C21), hard delete only for rebuildable caches or after an archive copy, and no DELETE grants (MAINT-C22). Against the research: agrees with L205 (decide per entity) and with the archive option of L204; contradicts the D2 recommendation (hard delete plus same-transaction archive by default, soft delete only where the product offers undo), which rested on one critique and no defender. The doctrine is that defender, with the mitigations the critique says are missing. Suggested record: the maintainer's soft-delete-by-default, with the five mitigations as its conditions.

**C2, logic in the database (`DATA.LOGIC`).** Default is application code; a function is created only when it earns its cost by reuse across consumers, hiding internals, database-owner-tunable performance, or integrity beyond constraints (MAINT-C42). Once past that gate, a wide band lives in the database: cascades, multi-table atomic validation, state transitions with logging, set-based algorithms over large data (MAINT-C44); the doctrine lists the costs it accepts (MAINT-C45) and its conventions (MAINT-C46, MAINT-C47). Triggers are used for validation, integrity and per-scope schema enforcement, not for updated_at (MAINT-C17, MAINT-C37). Against the research: agrees with the cost-benefit gate and application-first default (L214, L215, L041, L042); contradicts the C2 recommendation (domain logic and workflow in Python, the database for invariants and narrow triggers) and L215 in extent, on where cascades, multi-table validation and state logic live; it is the heavier-database position that L214 records with T4 support only, now with a practitioner behind it. Suggested record: the maintainer's four-reason gate plus the listed in-database band, with the research split kept as the default for projects with a single application.

**C3, contract schema (`DATA.ACCESS.2`).** Functions are the contract between the database and several backends; the signature is stable and the body tunable (MAINT-C41). Views are explicitly rejected, base tables stay directly queryable for simple reads, and the ladder is query, then function, then procedure (MAINT-C43). The contract evolves additively with coordinated breaking changes and no version numbers (MAINT-C47). Against the research: agrees with the function half of L187 and contradicts its view half; contradicts L044 (one application owns its database) because the doctrine's database is shared by many backends. For a single application that owns its database the doctrine is silent, so the C3 recommendation (base tables through the ORM, views for reporting) is neither supported nor refuted for that case. Suggested record: function contract when two or more consumers share the database, with views excluded, and base tables for a single owner.

### Gaps

- No position on time-ordered UUIDs, on key enumeration, or on optimistic version columns and isolation levels; the doctrine does not state a default concurrency control beyond locks, advisory locks and single-statement atomicity.
- Time-bounded retention by partition drop is not practiced (partitioning is only a prepared path through scope-leading keys); the research recommendation L206 has no counterpart.
- How concurrent consumers of an invalidation queue avoid double work (compare L413) and how a database change and an external message are made atomic (compare L409) are not stated.
- No statement on ORM use, backup and recovery, high availability, sessions, multi-tenancy beyond scope-leading keys, or whether row-level policies are deployed (they appear as illustrations).
- Doctrine statements are the maintainer's codified rules; they were not checked against the running system, and several include figures (percentages of tables) given by the doctrine itself.
