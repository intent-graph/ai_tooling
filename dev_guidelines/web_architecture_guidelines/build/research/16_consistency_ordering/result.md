# Research result: consistency, atomicity and ordering across the tiers (area CONS, round 3)

Ledger row ids (`Lnnn`) refer to the consolidated claims ledger; source ids `SRC-nnn` refer to its source list.

## L1 headline

Best practice is consistent and well grounded at the Postgres mechanism level (isolation anomalies, retry-the-whole-transaction, locks, non-transactional sequences, outbox plus idempotent consumers), but the ledger had no isolation-level claims at all; the open architecture choice is the default concurrency-control strategy (SERIALIZABLE with retry vs explicit locks vs optimistic version column), and the sync vs async boundary rests on two T2 API guidelines plus the 202 status-resource pattern, so certainty there is "majority", not "consensus".

Clusters (cluster claim; agreement; certainty; ids):
1. Postgres isolation levels permit different anomalies; record the level per use case, never assume. Read Committed allows lost updates by read-modify-write and phantoms; Repeatable Read is snapshot isolation (no phantoms in Postgres, write skew possible); only Serializable prevents write skew. Consensus; grounded. CONS-C01, C02, C03.
2. Serializable plus whole-transaction retry is the documented simplest route to correctness, with preconditions (all relevant transactions use it, short, read-only declared, not valid on replicas). Consensus on mechanism; grounded. C04, C05, C06, C07, C08.
3. Let the database enforce invariants declaratively; check-then-insert in application code races under non-serializable isolation. Consensus; grounded. C09, C10.
4. Explicit locks and optimistic versioning are the alternatives; locks never span user think time; business transactions spanning requests need a version check. Consensus on mechanism; the choice is contested. C11, C12, C13, C14, C15, C16, C17.
5. Sequences are non-transactional: gaps are normal, gapless needs explicit serialization, and id order is not commit order, so incremental readers keyed on id can skip rows. Consensus (T1 for gaps; T3 for the reader hazard); grounded. C18, C19, C20, C21, C22.
6. Atomicity ends at the database boundary: delivery is at-least-once, exactly-once is effectively-once (retry plus idempotent effect), and the outcome of a lost COMMIT acknowledgement is unknowable by the client. Consensus; grounded. C23, C24, C25, C26.
7. Idempotency-key server contract and multi-step request design (recovery points, atomic phases, concurrent duplicate answered 409). Majority; grounded (draft is T2). C27, C28, C29.
8. Within one Postgres use a local ACID transaction; sagas and compensation only when a business transaction spans separate stores, and compensation is a designed business operation. Consensus; mixed grounded and inferred. C30, C31.
9. Sync vs async boundary: validate and commit the intent inside the request, defer slow or foreign side effects, answer 202 with a status resource whose states, errors, retention and cancel path are designed. Majority; grounded for pattern, inferred for the rule of thumb. C32, C33, C34.
10. Read-your-writes breaks only where a second copy exists (replica, cache, async projection); show pending state from the status resource instead of assuming. Majority; grounded definition, inferred application. C35.
11. Double submit and concurrent tabs: layered defense (disabled button, 303 after POST, server idempotency key, unique constraint), concurrent edit of one record is a lost-update problem answered with a version check. Majority; T4 only for the render-time token. C36, C37.

Live debates:
- Default concurrency control: Postgres docs prefer SERIALIZABLE for all writes with retry; Jepsen and replica limits point to selected SERIALIZABLE, locks and constraints; Fowler ties optimistic vs pessimistic to conflict rate (C15).
- Outbox reader ordering: xid8 horizon filter (Dudycz) vs high-water-mark gap detection vs a locked counter table (C20).
- Helland: entity-scoped atomicity is argued for near-infinite scale; for one Postgres it is a design option, not a constraint (C23).

Not covered: saga isolation countermeasures (the saga page names the problem; its countermeasure list was not extracted); distributed-transaction protocols (2PC, PREPARE TRANSACTION); linearizability across replicas (high availability is out of round scope); event sourcing and CQRS ordering; UX copy for pending states; Kleppmann's book chapters (unreadable, only search extracts).

**Isolation and anomalies**

- **CONS-C01** | Choose and record the transaction isolation level per use case; in Postgres Read Committed permits nonrepeatable reads, phantoms and serialization anomalies, Repeatable Read permits only serialization anomalies (no phantoms), Serializable permits none. | decision | postgres | S01 (table) | consensus | - | grounded
- **CONS-C02** | Under Read Committed a concurrent UPDATE waits for the first writer and then re-evaluates its condition on the new row version; a read-modify-write done in application code (SELECT, compute, UPDATE) can therefore overwrite a concurrent change, so express the change as one atomic statement (`SET n = n + 1`), lock the row, or version it. | practice | postgres | S01 (Read Committed), S19 (lost update note) | consensus | - | grounded for the re-evaluation; inferred for the application-code consequence (from S01 plus S19)
- **CONS-C03** | Repeatable Read is snapshot isolation: concurrent updates of the same row fail with "could not serialize access" (SQLSTATE 40001) and must be retried, while write skew (two transactions reading overlapping data and updating different rows) remains possible; only updating transactions can fail. | principle | postgres | S01, S17 (documented behavior matches snapshot isolation) | consensus | - | grounded
- **CONS-C04** | If Serializable is used for all writes and all reads that need a consistent view, no other effort is needed for consistency; make it a framework-level default (`default_transaction_isolation`) with automatic retry rather than a per-call burden. | decision | postgres | S05, S01 | consensus (one T1 source family) | - | grounded
- **CONS-C05** | Serializable has preconditions and limits: lower-isolation transactions in the mix void the guarantee; the protection does not extend to hot standby or logical replicas (use Repeatable Read plus explicit locks on the primary there); data read is not valid until its transaction commits; unique-constraint violations can still occur after an explicit "key absent" check. | practice | postgres | S05, S01 | consensus | - | grounded
- **CONS-C06** | Keep Serializable cheap: declare read-only transactions, keep transactions short, bound connections with a pool, avoid sequential scans (they take relation-level predicate locks), and drop explicit locks that Serializable made redundant. `SERIALIZABLE READ ONLY DEFERRABLE` blocks until a safe snapshot, the one case where Serializable blocks and Repeatable Read does not. | practice | postgres | S01 (Serializable section) | consensus | - | grounded
- **CONS-C07** | On 40001 retry the entire transaction including the logic that chooses the SQL and values; retry 40P01 (deadlock) too; retry unique_violation (23505) only with care because it may be persistent; allow many attempts under contention; Postgres has no automatic retry, so the application layer (use-case boundary, [L066, L228]) owns a bounded retry wrapper. | practice | postgres | S04, S01, S08 | consensus | - | grounded (wrapper placement inferred)
- **CONS-C08** | Do not treat a documented isolation level as proof: Jepsen found G2-item anomalies under Serializable in Postgres 9.5.22 to 13 (conflict-detection flaw, patched in a later minor release) and Bailis et al. found a duplicate-creating SSI bug in 2015; keep patch level current and back critical invariants with constraints (C09) rather than isolation alone. | practice | postgres | S17, S19 | consensus | - | grounded
- **CONS-C09** | Enforce uniqueness, referential integrity and similar invariants with declarative database constraints; application-level validation (check, then write) is correct only under serializable isolation, and Postgres and MySQL default to weaker levels (Bailis et al.: 12.7% of Rails validations are uniqueness checks, which produced duplicates under concurrent workers). Boundary: DATA. | principle | postgres | S19, S01 | consensus | - | grounded
- **CONS-C10** | For "insert or update" use `INSERT ... ON CONFLICT DO UPDATE`, which guarantees one of the two outcomes even under high concurrency, instead of select-then-branch. | practice | postgres | S07 | consensus | - | grounded

**Locking, optimism, strategy**

- **CONS-C11** | `SELECT ... FOR UPDATE` blocks other writers only while held; it does not stop a later conflicting update once the lock is released unless the row was actually updated while held; under Repeatable Read take locks before the first query, because the snapshot freezes at the first statement. | practice | postgres | S05, S02 | consensus | - | grounded
- **CONS-C12** | Prevent deadlocks by acquiring locks on multiple objects in one consistent order everywhere; Postgres detects deadlocks and aborts one transaction, so retry the aborted one. | practice | postgres | S02, S04 | consensus | - | grounded
- **CONS-C13** | Never hold a database transaction or lock open across user think time; a business transaction that spans several requests is protected by a version check validated inside one short system transaction at write time (optimistic offline lock), the database-side partner of the HTTP ETag rule [L260]. | principle | neutral | S02, S14 | consensus | - | grounded
- **CONS-C14** | Choose optimistic locking when conflicts are rare; choose pessimistic locking when conflicts are frequent or when losing a long piece of user work at final commit is unacceptable. | decision | neutral | S14, S15 | consensus | rule depends on conflict rate, not on technology | grounded
- **CONS-C15** | The default concurrency-control strategy is a recorded decision among (a) SERIALIZABLE with retry for all transactions, (b) default isolation plus selected explicit locks and constraints, (c) optimistic version columns on user-edited rows. | decision | postgres | S05, S17, S14, S15 | contested | Postgres docs (S05): Serializable for everything, no other effort; Jepsen (S17): selected Serializable, explicit locking or redesign where strictness matters; S05 itself: use Repeatable Read plus locks when replicas must be protected; Fowler (S14, S15): by conflict rate. Applies by workload: low contention and framework retry favor (a); user-edited long forms favor (c). | grounded for each position; the combination (a) for writes plus (c) for edited records is inferred
- **CONS-C16** | Prefer transaction-level advisory locks (released at commit) over session-level ones, which survive rollback and break under transaction pooling [L200]; never call a locking function in the same query level as a LIMIT, because the lock may be taken on rows beyond the limit. | practice | postgres | S02 | consensus | - | grounded
- **CONS-C17** | A lease-based distributed lock that guards correctness needs a fencing token the storage layer checks, because a paused holder can act after its lease expired; a lock used only to save duplicate work may stay best-effort. In this stack the row version or a unique constraint is the fencing mechanism, so prefer them to an external lock service. | principle | neutral | S16 | consensus | - | grounded for the argument; inferred for the stack application

**Sequences and ordering**

- **CONS-C18** | Sequence values are non-transactional: a `nextval` is not returned on rollback or crash, `INSERT ... ON CONFLICT` can consume values without inserting, so gaps are normal and Postgres states that sequences cannot be used for gapless numbering [extends L179]. | principle | postgres | S03 | consensus | - | grounded
- **CONS-C19** | Do not expose a sequence value outside the database (to a user, a message, another system) before its transaction has committed. | practice | postgres | S03 | consensus | - | grounded
- **CONS-C20** | An id assigned from a sequence does not reflect commit order: a lower id can commit after a higher one, so a reader that polls with `WHERE id > last_seen` (outbox relay, change feed, incremental export) can skip the late row forever; read only rows from transactions older than the oldest in-flight one (an `xid8` column compared with `pg_snapshot_xmin(pg_current_snapshot())`), or detect gaps with a high-water mark and wait. | decision | postgres | S24, S03 (mechanism) | contested | Dudycz (S24): xid8 horizon filter recommended, with the caveat that order then follows transaction start; gap detection (as in the Marten library, reported in S24) is non-trivial; a locked counter table removes gaps but serializes all writers and is rejected. One T3 source for the hazard; the mechanism is T1. | grounded for the mechanism; the polling consequence is T3, the same hazard plausibly applies to `updated_at` cursors (inferred)
- **CONS-C21** | If a business rule requires gapless, ordered numbers (invoice numbers), allocate them in a dedicated counter row updated inside the business transaction, accepting that this serializes the writers; do not derive them from a sequence. | decision | postgres | S03, S24 | consensus | - | inferred (S03 forbids the sequence use; S24 describes the counter-table cost)
- **CONS-C22** | `FOR UPDATE SKIP LOCKED` gives an inconsistent view and suits queue tables only [L413]; under Read Committed, `ORDER BY` plus a locking clause can return rows out of order after a lock wait, which Repeatable Read and Serializable turn into a 40001 instead. | practice | postgres | S06 | consensus | - | grounded
- **CONS-C23** | Helland: transactional atomicity is scoped to one entity (one key, one place); across entities use messages, and alternate indexes cannot be kept transactionally consistent at very large scale. For one Postgres this is a design option: keep aggregates small and addressable by key so a later split does not need distributed transactions, but do not give up cross-table transactions that a single database offers. | principle | neutral | S11 (sections "Atomic Transactions Cannot Span Entities", "Entities Manage Per-Partner State") | contested | Helland: entity-scoped atomicity is required once data outgrows one node; [L125] and [L113] (one Postgres, one deployable until proven otherwise): cross-table ACID is the point of the database. Apply Helland when a split is planned. | grounded for the paper's claim; the single-Postgres reading is inferred

**Atomicity, delivery, idempotency**

- **CONS-C24** | Where messages are delivered at least once, the receiver records which messages it already processed in the same transaction as the state change and answers a repeat the way the first was answered; this extends [L410] and upgrades [L270] (idempotency key and effect recorded atomically) from open to grounded. | practice | neutral | S11 ("Entities Manage Per-Partner State"), S22, S13 | consensus | - | grounded
- **CONS-C25** | "Exactly-once" is not available across a process or network boundary because the effect and its acknowledgement are not atomic (Helland's failure window); design for at-least-once delivery plus idempotent effects and call the result effectively-once. | principle | neutral | S11, S13, S25 | consensus | - | grounded
- **CONS-C26** | If the connection drops while COMMIT is in flight, the client cannot know whether it committed (Postgres defines SQLSTATE 08007 `transaction_resolution_unknown` and 40003 `statement_completion_unknown`; Jepsen saw 2 of 952 writes fail with an I/O error yet persist); retry only idempotent operations, or reconnect and verify by a key or transaction id. The same ambiguity exists between browser and server when a response is lost. | principle | postgres | S08, S25, S20 (client cannot tell lost response from lost request) | consensus | - | grounded
- **CONS-C27** | An idempotency-key contract needs more than [L269]: a key is unique and never reused with a different payload (answer 422), a retry that arrives while the first is still running gets 409, a missing required key gets 400, expiry is a published policy, the lookup key is scoped (per user, for example), and the stored first response is replayed. The IETF text is a draft (T2); retention differs by source (24 hours Stripe per [L269]; a reaper at 72 hours in S22). | decision | http | S10 (sections 2.2 to 2.7, 5), S22 | majority | S10 and S22 agree on mechanism; S22 serializes duplicates with a locked key row instead of answering 409; thresholds differ | grounded
- **CONS-C28** | For a request that mutates foreign state (payment, remote API): split it into atomic phases (local transactions between foreign calls), name a recovery point after each phase and each foreign call, commit before the foreign call, pass an idempotency key to the foreign system, and run a completer for abandoned requests and a reaper for old keys; extends [L234, L246]. | practice | postgres | S22 | majority | single T3 source, no dissent found (as in [L246]) | grounded
- **CONS-C29** | A post-commit hook (Django `on_commit`, [L233]) is not part of the transaction: if the process dies after commit the side effect is lost, and an exception in one hook can skip later hooks unless `robust=True`; use it for losable work (cache invalidation, best-effort email) and the outbox [L409] when the follow-up must not be lost. Enqueuing before commit lets a worker run on uncommitted data; enqueuing after commit risks a crash between the two. | decision | python | S09, S23 | consensus | - | grounded
- **CONS-C30** | Within one Postgres use one local ACID transaction, not a saga; adopt sagas only when a business transaction spans services with separate databases, accepting that sagas lack isolation (concurrent sagas can see anomalies; countermeasures must be designed) and require hand-written compensations instead of automatic rollback; orchestration (central coordinator) vs choreography (events) is a further decision. | decision | neutral | S12, S11 | consensus | the default-no-saga rule for a one-database stack is inferred | grounded for the saga costs; inferred for the default
- **CONS-C31** | Compensation is a business operation, not a technical undo: use tentative operations (reserve, then confirm or cancel) with an explicit right to cancel, manage the uncertainty in per-partner state, and accept that some effects (a sent email) cannot be compensated. | principle | neutral | S11 ("Tentative Operations, Confirmation, and Cancellation"), S12 | consensus | - | grounded for tentative operations; "not compensable" inferred

**Sync vs async boundary and the user**

- **CONS-C32** | Inside the request: validate input and authorization (reject with 400 before accepting), perform every change that must be atomic with what the user sees next, and persist the intent to do deferred work in that same transaction. Defer: work with foreign side effects, work expected to last more than a few seconds (rules of thumb: 1 s per [L271], 10 s in S21), and fan-out. Normal API calls answer in about 100 ms, and I/O-bound work stays synchronous but nonblocking. | decision | neutral | S20, S21, S23 | majority | thresholds differ (1 s vs 10 s, see [L271]); the "same transaction" rule is from the outbox sources | grounded for the pattern; inferred for the combined rule
- **CONS-C33** | A deferred operation exposes a dedicated status resource: 202 with `Location` and `Retry-After`; status in a documented closed set (pending, running, succeeded, failed, canceled); `createdAt` and `lastUpdatedAt` to tell stalled from running; a structured RFC 9457 error when failed; a retention policy (`Expires`); 303 See Other to the result; DELETE on the status resource to cancel; do not poll the target resource and read 404 as "not yet". Extends [L271]. | practice | http | S20, S21 (done, error, metadata; expiry of 30 days suggested) | consensus | - | grounded
- **CONS-C34** | 202 means accepted, not done: the accepted job record must be durable before the 202 is sent so the status endpoint can answer after a crash, and the submit needs an idempotency key because the client cannot distinguish a lost response from a lost request. | practice | neutral | S20, S23 | majority | - | grounded for the key; durable record inferred (from S20 plus S23)
- **CONS-C35** | Read-your-writes (a process always sees its own updates; session consistency is the same within a session) is a per-operation requirement, "most desirable but not always required"; with one Postgres primary it holds after commit and breaks only where a second copy exists (replica, cache, asynchronous projection), so after an async step show the user the pending state from the status resource or the optimistic local value rather than a read that may not include the work yet. | principle | neutral | S18 | majority | - | grounded for the definitions; inferred for the single-primary statement and the UI rule (replicas are out of round scope)
- **CONS-C36** | Prevent double submit in layers: disable the submit control and show a pending state (UX), answer a successful POST with 303 to a GET page [L258], send a server-checked idempotency key or form token minted at render time, and keep a unique constraint as the last backstop; none alone suffices. | decision | http | S10, S20 (key), T4 forum and blog extracts seen in search only, not read in full | majority | the layering is the stated T4 consensus; the key part is T2 | inferred (layering across sources; T4 not used as sole ground)
- **CONS-C37** | Two tabs or users editing the same record are a lost-update case, not a duplicate case: carry a version in the form, check it in the write (C13, [L260]), answer conflict, and show the user both versions; and in Django, wrap multi-step writes in `atomic`, use `durable=True` to assert an outermost transaction, and note that `on_commit` callbacks registered after a rolled-back savepoint are discarded. | practice | python | S09, S14, [L008] | consensus | - | grounded (conflict UI is inferred)

### Gaps (open)

- Saga isolation countermeasures (semantic locks, commutative updates, versioning): the saga page names the problem but the countermeasure list was not extracted; open.
- Two-phase commit and `PREPARE TRANSACTION` in Postgres: not researched; likely out of scope for a single-database stack.
- Event ordering across several consumers or partitions (per-key ordering guarantees of brokers): not covered because the stack has no broker by default; open if a broker is chosen [L126].
- Kleppmann's book chapters on isolation and consensus: unreadable here; no claim depends on them; a later pass could cite them.
- Read-your-writes with replicas and caches: only a definition source (S18); replication is deferred in the round scope.
- Double-submit evidence is T4 for the render-time token; a T1 or T2 source for the form-token pattern (OWASP synchronizer token covers CSRF, [L331]) was not found.
- User-facing communication of pending, failed and compensated states (copy, notification channel): not researched; boundary with PRESENTATION and real-time [L006].
