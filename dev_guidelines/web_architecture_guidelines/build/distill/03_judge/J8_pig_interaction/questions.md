# J8 pig-web-defaults PIG-WEB.INTERACTION: questions for the maintainer

None.

Every judged node of the browser and agent surface has a winner in the default context (a classic website, one team, JavaScript + Python + Postgres, humans and agents as users, a database shared by several backends and by reporting, consoles and scripts; Python renders the pages). Four choices the evidence presents as contested were decided without a trade-off between forces the node itself serves, because the default context fixes the condition each side wins under:

- **Push channel** (server-sent events first, or WebSocket first): pages are correct without push and clients catch up after any gap, so a proxy that delays a stream costs latency, never correctness. Server-sent events are the default for one-way push; WebSocket is used for two-way, high-frequency traffic (live typing, shared text editing); WebSocket for everything wins when users reach the application through intermediaries the team cannot configure and buffering is observed there.
- **Agent tokens** (sender-constrained or plain bearer): bound by consequence. Scopes that allow payments, transfers, deletions or bulk exports require tokens bound to a key the client holds; short-lived, narrow bearer tokens are accepted for everything else, so agent clients that cannot hold a key can still read and make reversible changes.
- **Agent protocol** (an agent-protocol server, plain HTTP with a published description, or both): both, layered. Agents are users in the default context, so agents the team does not build must connect; the agent-protocol server is a thin adapter over the same described HTTP core and holds no rule. HTTP with its description alone wins when every agent client is the team's own code.
- **Approval of agent actions** (confirmation per action, automatic classifier, structural limits, approval on a separate device): reads and reversible writes proceed; irreversible or external effects wait for the owning user's approval of the exact action on the application's own page, and the server refuses the effect without it. Automatic approval is kept only for recoverable effects in developer tooling.

Not asked here, because it already awaits the maintainer elsewhere: when several backends read the same data, who applies a per-user visibility rule ("a draft is visible only to its author"). It reaches two nodes of this unit: which events a live channel may send to a subscriber, and which mentioned users may be notified of a comment. Until it is answered, both nodes record the stated default: each backend applies the filter, from one shared written specification that lists every place the data can surface, and every backend runs the same tests that check those places deny what they must. Database read functions that receive the verified user stay acceptable when a per-user rule must hold for two or more backends.

One consequence of that default the maintainer should see when answering: database roles that may read the tables directly, such as reporting and operator roles, see every row, comments, notifications and change records included, unless their own access is restricted. The filtering above protects what the application sends; it does not protect against those roles. Until the question is answered, both nodes therefore require that those roles get no direct read access to comment content or to comments with a narrower audience than their target, and read comments only through a view limited to comments everyone who sees the target may see, or not at all. If a project does not apply that restriction, the leak to those roles is a known limit, stated where comments are documented.

Also settled without asking, and worth knowing: on flows that hand out scarce goods or reward automation per account (limited stock, referral credit), per-agent quotas and approval by the owner do not stop one party that runs many accounts, each with its own approved agent. There, completing the flow requires a human step on the application's own page, or agents are refused, whatever their identity. Which flows are of that kind is a decision each project records.
