## Decided for this context (MD-03)

A classic website (documents, forms, CRUD), one team, JavaScript + Python + Postgres, single tenant, humans and agents as users. **The database is shared by several backends and by other consumers: BI and reporting, admin consoles, scripts.** Assumed: online use; Postgres is a long-term commitment; write load fits one primary; the team can write and test database functions.

Who reaches the database, and how:
- **each backend**: its own role; calls the API functions, one call per business operation in its own transaction (never several calls wrapped in one); may read simple data directly; never writes state columns or multi-table data directly; may assert an end-user actor;
- **BI and reporting**: a read-only role with table and column grants, on a replica or reporting copy when its load matters;
- **admin consoles and scripts**: an operator role that calls the API functions like a backend and reads the tables and columns its tasks need (reporting restrictions); asserts only itself as actor;
- **migrations and human-run data jobs**: the owner role, never used to serve requests; changes state columns only through their writer function or as a recorded exception (checklist of L545); asserts the operator and ticket id;
- **browsers and agents**: never connect; they go through a backend.

**Actor trust**: the database verifies the consumer (session role), not the end user; the acting user is the consumer's claim. Writes without an actor are refused, the role-to-actor pairing above is checked, and audit records both the role and the claimed actor.

**In one line**: Postgres is the authority for the truth of stored data and for everything that must hold whoever touches it, per-user write rules decidable from the row included; each backend is the authority for its product policy (not stored in the data), its users' identity and its workflow; browsers and agent clients hold copies for feedback and latency and decide nothing durable.

**How placements were chosen**: correctness and security decide which tiers may be the authority; among those, the force whose loss is hardest to repair later wins (changeability of the rule's location, then performance, then scalability); latency and performance justify copies, never a move of authority.

**Certainty**: *grounded* = the verdict rests on read evidence; *inferred* = it follows from grounded rows but no source states it, or it is a judgment between positions; *open* = not decided, or a named part not known; *MD-0n* = set by that maintainer decision (with any tension against the evidence noted in `records.md`).

## Where the matrix meets the maintainer's decisions and doctrine

- **Maintainer decisions applied**: MD-01 (no row-level security by default; authorization in the backend with per-role privileges as second gate) in GUARD.3 and ROW_SECURITY; MD-02 (interface description always in sync; origin per project) in RECORD.3 and TYPE_CHAIN; MD-03 (shared database; multi-table operations, privileges and audit in the database; function API as default contract) in the default context and every placement that relied on a single consumer.
- **Tensions with the evidence, not overridden**: MD-01 against L619 and L688 (row security when several consumers share the database); MD-03 against L044 and L622 (one application owns its database; no schema across a boundary, which BI reading base tables touches) and against L215 and L066 (application-first logic). The MD-01 and MD-03 pair also leaves per-user read filters duplicated across backends: Q1, `undecided: awaiting maintainer, read visibility of rows with per-user rules when several backends share the database` (per-user write rules are settled in the writer functions).
- **Against the doctrine (1, partial)**: GUARD.2 against L471, which makes CHECK constraints and triggers optional; here declarative constraints are required, because only they bind every writer (owner-run migrations included) and procedural checks need serializable isolation or a lock.
- **Doctrine adopted as the max choice**: authorization in two layers (L468); the cost list for database logic (L472); core writes never asynchronous (L482); the function gate, the in-database band, multi-table operations as functions and one writer per state column (L527, L528, L584, L596); the function API with views off the contract (L515, L516, L517); derived caches in database tables (L534, L532, L535, L536); data schedules inside Postgres (L604); the live database as the truth for structure (L474).
