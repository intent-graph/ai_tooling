## DATA Durable Data

- **Question**: how the database carries out the work the placements give it: organizing facts, guarding them, keeping them correct over time, and deriving values.
- **Positions**: none of its own (owns no row); roll-up of its four children, under the work J1 and MD-03 give the database.
- **Decision**: roll-up. The database is the system of record (RECORD.1) and holds everything that must hold whoever touches the data (MD-03). It realizes that work in four ways:
  - **organize**: each fact stored once, in tables normalized at least to third normal form and further where the design calls for it (DATA.ORGANIZE);
  - **guard**: every rule a declarative constraint can express is declared; the rest is checked by writer functions under an isolation level or lock that makes the check correct; concurrent and partial change is caught inside one transaction (DATA.GUARD);
  - **maintain**: structure changes only through versioned migrations applied by automation, incompatible changes go expand, migrate, contract, and the live database is the truth for structure (DATA.MAINTAIN);
  - **derive**: store the minimum, compute the rest; every stored derived value is a copy with a stated sync and staleness (DATA.DERIVE).
- **Rejected**: none at this level; each child records its own.
- **Realizes**: through its children, RECORD.1, RECORD.3, GUARD.2, GUARD.5, DERIVE.1. Not realized by any philosophy DATA node (gap 1): RECORD.2 (the function API as default contract, MD-03), the database share of ACT.1 (each business operation one function call; one writer function per state column, L584, L596), the per-role layer of GUARD.3, ACT.4 (audit). The target hierarchy places the database's function API under DATA; the skeleton has it only at PIG-WEB.DATA.INTERFACE, which has no philosophy counterpart. Proposal for the skeleton owner, not applied: a philosophy node `DATA.INTERFACE` (realizes RECORD.2 and the database share of ACT.1; refined by PIG-WEB.DATA.INTERFACE), judged as a realization of J1's verdicts because it would own no row.
- **State**: `known | gap: no philosophy realizer for RECORD.2, the database share of ACT.1, ACT.4 and the per-role layer of GUARD.3 under MD-03; data lifecycle (retention, recovery) has no principle row`.

## DATA.ORGANIZE Organized Facts

- **Question**: how facts are shaped so that each is stored once and changed in one place.
- **Positions**:
  - P1 third normal form by default: every non-key field states a fact about the key, the whole key and nothing but the key (L037; SRC-254 T2, SRC-291 T3; L469 MAINT).
  - P2 third normal form as the practical ceiling; higher forms (Boyce-Codd, fourth, fifth) only in specific multi-valued or overlapping-key designs (L039, majority; SRC-291 T3 says they are rarely considered, SRC-254 T2 describes fourth and fifth normal form without ranking and has no Boyce-Codd section).
  - P3 denormalize where measured performance requires it, the application guarding the redundancy (L168, owned by PIG-WEB.DATA.DERIVE.1; SRC-254, SRC-291); under L469 (MAINT) only with a sync plan chosen before it is built and recorded in the table comment.
  - P4 a new one-to-one attribute is a nullable column by default; a separate table only for, in this order, cardinality likely to change, a different permission boundary, an independent audit or lifecycle, blast radius on heavily used tables; sparsity and NULL count are not reasons (L470 MAINT). The opposite position (split to avoid NULLs) is named by L470 itself; no ledger row argues for it.
- **Forces**: all positions serve integrity, the node's purpose: each fact stored and changed in one place, so no update anomaly or inconsistent dependency can arise (L038; SRC-254, SRC-291). P2 and P3 trade some of it for design effort and read performance (normalization spreads data over several records, L168). P4 trades a nullable column against a join on every read that needs the attribute.
- **Decision**:
  - **The rule is "each fact once" (L038); the normal forms are its tests.** Every table passes third normal form (L037, L469; MAINT and research agree). Boyce-Codd, fourth and fifth normal form are applied where they apply, because the anomaly those forms remove is of the same kind third normal form removes (L039; SRC-254 for fourth and fifth normal form, which it covers; the Boyce-Codd claim is inferred, SRC-254 has no Boyce-Codd section).
  - **Where a Boyce-Codd decomposition loses a dependency, the lost dependency is enforced by a constraint trigger under DATA.GUARD's rule (Serializable or a lock)** (changed after review, M4). The higher forms do not "cost nothing": where candidate keys overlap, a Boyce-Codd decomposition is not always dependency-preserving, so a dependency one table's key enforced in third normal form can come to span two tables and can no longer be enforced by a key (inferred from the standard theory; not in the ledger). The cost is an integrity cost, a rule moving from a declarative key to a procedural cross-table check; enforcing it by trigger keeps both "each fact once" and "every rule enforced", which is the max under the selection rule.
  - **Denormalization is not an organizing choice.** A denormalized value is a derived copy of a fact stored elsewhere: it is governed by DATA.DERIVE and ALLOCATION.DERIVE.1, and it exists only with the sync plan of L469 recorded before it is built (what and why, sync level, freshness, change frequency, impact of divergence, drift detection and reconciliation, alerting).
  - **One-to-one attributes**: L470 adopted on authority and as the max choice. Its split criteria are integrity and security reasons (a fact whose cardinality will change, a permission boundary, its own audit or lifecycle, blast radius); sparsity is not, because a split states no fact more precisely and adds a join on every read.
  - **Nullable columns state their meaning.** A column is nullable only when absence is a meaningful state of the fact (L485; L040 cites the Postgres guidance that most columns are NOT NULL, SRC-134 T1); where several nullable columns must be present together, a CHECK states it (inferred from L485 and L174).
  - **Under MD-03** the schema is read directly by BI and operator roles (RECORD.2, access paths): normalization is what keeps every consumer's view of a fact identical without consumer-side reconciliation (inferred).
- **Rejected**:
  - P2 as a ceiling: rejected; stopping at third normal form where overlapping keys or independent multi-valued facts exist leaves the anomalies L038 exists to prevent. Acceptable not to analyze beyond third normal form when every candidate key is a single column, and no multi-valued facts (narrowed after review, M4: a single composite candidate key is not enough, as Kent's own fifth-normal-form example, an all-key table of agents, companies and products, still needs fifth normal form; SRC-254).
  - P3 as an organizing default: never. Acceptable as a derived copy when measured read performance requires it, with L469's sync plan and DATA.DERIVE's sync gradient (L532) and drift guard (L533).
  - Splitting a one-to-one attribute for sparsity or NULL count: rejected (L470). A split wins only under L470's criteria.
- **Gap**: collation. J1 owns collation in DERIVE.2 (the database is the authority for every order it serves) and left its choice "open under DATA". No ledger row grounds a choice of collation. Handed, open, to J6 (PIG-WEB.DATA.ORGANIZE.3, column types), to decide with evidence or keep open; the philosophy-level consequence of DERIVE.2 is only that collation is a declared property of the stored text, not of a consumer (inferred).
- **Realizes**: ALLOCATION.RECORD.1 (holds the durable facts in the form the system-of-record placement gives the database). Refines python-kb-philosophy:STRUCTURE and :DATACENTRICITY (skeleton links).
- **State**: `known | unvalidated: the Boyce-Codd claim and the trigger for a lost dependency, the co-presence CHECK, and the MD-03 consequence are inferred | gap: collation choice has no row (handed to J6)`.

## DATA.GUARD Guarded Consistency

- **Question**: how the database keeps data valid and consistent under concurrent and partial change.
- **Positions**:
  - P1 model data with the most precise structure available so illegal states cannot be represented: NOT NULL, CHECK, foreign keys and domains in the database, precise types at the boundary (L485; SRC-338 T2, SRC-134 T1). Placement: GUARD.2 requires declarative constraints (L040, L473, L471 MAINT).
  - P2 application-side validation as the guard (common practice, L040's note; rejected by J1 in GUARD.2: check-then-write is correct only under serializable isolation, L473).
  - P3 state the consistency model per operation (L043; SRC-232 T2) against P3' classifying the datastore as "CP" or "AP" (the practice L043 rejects).
  - P4 a lock that guards correctness carries a fencing token the storage checks; in this stack the row version or a unique constraint is the fencing, preferred to an external lock service (L476; SRC-346 T2); against P4' a lease-based lock service without fencing; P4'' a best-effort lock used only to save duplicate work (L476 allows it).
- **Forces**: P1, P3, P4 serve integrity under concurrency and partial failure. P2 serves changeability (rules tested in memory, L042) and loses integrity whenever a second writer or a concurrent request exists (L473), which MD-03 makes the default. P3' serves brevity and hides latency and multi-object transactions (L043). P4' serves availability of the lock and loses correctness when a paused holder acts after its lease expired (L476). P4'' serves efficiency only.
- **Decision**: the database guards consistency in six ways, each the realization of a J1 verdict.
  - **Declare every rule a declarative constraint can express** (GUARD.2, L485, L040, L473): NOT NULL unless absence is a meaningful state; row-local CHECK paired with NOT NULL (L174); foreign keys; unique, partial unique and exclusion constraints for cross-row rules (L175); domains for value types used in several places. Constraints are named, so a violation maps to a stable error (L495). Required, not optional: only declarative constraints bind every writer, owner-run migrations and human-run jobs included (J1, GUARD.2).
  - **Rules no constraint can express** (other multi-row rules, legal transitions, dependencies lost by a Boyce-Codd decomposition) are checked in the writer function or a constraint trigger, run under Serializable isolation with retry or after locking the governing row; the function or trigger asserts the isolation it needs, set per consumer role (GUARD.2, L577, L573). The default isolation level belongs to J6 (PIG-WEB.DATA.CONCURRENCY.1).
  - **Partial change**: each business operation commits or rolls back as one transaction inside one function call; callers never pass partial steps (RULES.5; ACT.1; L584 MAINT; MD-03). Per X3: one business operation is one database function call in its own transaction (J1 R1-4); backends never compose several calls into one operation. A database function may call another domain's published functions inside the same transaction: composition across domains happens in the database. What is forbidden across domains is direct access to another domain's tables, not calling its published functions.
  - **Concurrent change**: detection inside the writer function, which takes the expected version as a parameter; no transaction or lock is held across user think time (GUARD.5, L475).
  - **Mutual exclusion that guards correctness is enforced by the store**: row version, unique constraint or row lock inside the transaction; a lease (GUARD.5, frequent costly conflicts) is checked by the writer function as a fencing token (L476). A lock outside the database is acceptable only to save duplicate work.
  - **The consistency model is stated per operation** (L043): which isolation, whether it reads the primary or a replica, and what staleness it accepts. Reports on a replica accept snapshot anomalies (L573, via GUARD.2); a check that decides a write never reads a replica (inferred from L573).
- **Access guarding** (realization of GUARD.3's database layer; not in the node's question as worded, see gap 1): each consumer has its own role, neither owner nor superuser; grants bound which functions it may execute and which tables and columns it may read; state columns are revoked from direct update so the writer function is the only path (MD-01, MD-03, GUARD.3). Realized at PIG-WEB.DATA.GUARD.2 (J6). Row-level security is not a default (MD-01).
- **Awaiting maintainer** (changed after review, B1, X1): `undecided: awaiting maintainer, read visibility of rows with per-user rules when several backends share the database` ("a draft is visible only to its author"; J1's Q1). Not settled here. The graph records J1's stated default word for word: A provisional, with one written specification per rule and a shared denial suite; B acceptable when a per-user read rule must hold for two or more backends. That is: each backend filters these reads from one shared written specification, with a shared denial-test suite every backend runs; database read functions that receive the verified actor (verified by the backend, still a claim to the database, J1 R1-3) are acceptable when a per-user read rule must hold for two or more backends, which under MD-03 can easily be the case. The database's part otherwise is the per-role grants above. Consequence: roles that may SELECT the base tables (reporting, operator) see every row, comments included, unless their own role is restricted.
- **MAINT**: L471 adopted on authority (database enforcement is the source of truth; application validation an optimisation). J1's partial verdict against L471 ("triggers and CHECK constraints optional as defence in depth") is inherited and realized here; no new verdict.
- **Rejected**:
  - P2 for any rule that must hold for every writer: never (GUARD.2). Application validators stay as generated or tested copies, for feedback (RULES.1).
  - P3': never; a store label hides the per-operation guarantee that matters (L043).
  - P4' for correctness: never (L476). P4'': acceptable when the lock only avoids duplicate work and a duplicate is harmless, or is caught by a constraint.
- **Realizes**: ALLOCATION.GUARD.2 (invariants), ALLOCATION.GUARD.5 (concurrency control). Links proposed, not created: realizes ALLOCATION.GUARD.3 (database layer per consumer role) and ALLOCATION.RULES.5 (atomicity ends at the transaction).
- **State**: `known | conflict: against L471 (MAINT) on optional CHECK constraints, inherited from J1 GUARD.2 | undecided: awaiting maintainer, read visibility of rows with per-user rules when several backends share the database (J1 Q1; recorded default: A provisional, with one written specification per rule and a shared denial suite; B acceptable when a per-user read rule must hold for two or more backends) | unvalidated: the stack form of fencing (L476) and "no deciding read on a replica" are inferred`.

## DATA.MAINTAIN Maintained Over Time

- **Question**: how schema and data evolve without breaking running code, and what is the source of truth for structure.
- **Positions**:
  - P1 every schema change is a versioned migration in version control with the code, ordered, applied only by automation, as an explicit release step, the same way in every environment, never by hand (L046; SRC-220 T2, SRC-022 T1, SRC-183 T2, SRC-187 T2). The doctrine agrees and adds re-runnable DDL, one owner role per table, long data work kept out of automated runs (L519 MAINT, owned by J6).
  - P2 hand-applied or ad hoc changes to production structure (the practice L046 rejects).
  - P3 a backward-incompatible change proceeds expand, migrate, contract, so every phase can be released, verified and rolled back (L047; SRC-186 T2, SRC-190 T2, SRC-220 T2, SRC-311 T3, SRC-278 T3).
  - P3' a breaking change to the function API is coordinated with every consuming team and deployed together (L517 MAINT, owned and judged by J6 at PIG-WEB.DATA.INTERFACE.1; cited here, not judged).
  - P4 the live database is the source of truth for structure: table and function documentation is generated from it (L474 MAINT; SRC-220).
  - P5 conventions evolve forward only: new tables follow the new rule, legacy ones are not renamed in bulk (L474 MAINT), against P5' bulk renaming to the new convention.
- **Forces**: integrity of running code and data across releases. P1 and P3 serve it and cost process (each change small, several releases for one incompatible change). P2 serves speed and loses reproducibility and the record of what changed. P3' serves speed of a coordinated change and, unless every consumer deploys in one step with the migration, leaves a window where old code runs against the new structure. P5' serves uniformity of names and breaks every consumer of the old names, several under MD-03.
- **Decision**:
  - **One path of change**: structure and database functions change only through versioned migrations, reviewed, applied by automation as an explicit step of every release, identically in every environment (L046, L519; consensus and MAINT agree). Long-running data work is a versioned script outside the automated migration run, launched by a human under the checklist of L545 with a ticket id (L519, L545; J1's owner-role access path). No production change, structural or data, is ad hoc SQL.
  - **Origin of change and truth of state are distinct, and must agree**: migrations are the only origin of change; the live database is the truth for current structure, from which documentation, persistence models and function wrappers are generated (L474; RECORD.3, MAINT, max). A structure the migrations would not produce is a defect to reconcile, not a new truth (inferred from L046 with L474; the drift check, such as comparing a freshly migrated database's catalogue with production, has no source read; mechanism handed to J6).
  - **Incompatible changes go expand, migrate, contract** (L047), for tables and for the function API alike: add the new structure or function beside the old, move every consumer, then remove the old in a change marked coordinated once no deployed consumer references it (L192; RECORD.3's catalogue diff in CI fails on a removal not so marked). Max: the database and its consumers never deploy atomically, and under MD-03 several consumers (backends, BI, consoles, scripts) deploy on their own schedules; expand, migrate, contract is the only route that keeps every running version working (inferred from L047 with MD-03).
  - **Conventions evolve forward only** (L474, MAINT, max): a rename is itself an incompatible change for every consumer; new objects follow the new rule.
  - **Principle-level requirement** (changed after review, m8): an incompatible change keeps every running consumer working. How the function API meets it, and the verdict on L517, belong to J6, which counts that departure once for both graphs (X2): "deployed together" stays acceptable only when every consumer of the changed object ships in the same deployment as the migration; otherwise a breaking change goes expand, migrate, contract. This node cites that verdict; it does not count it.
- **Rejected**:
  - P2: never.
  - P3', a breaking change deployed together: not judged here (m8, X2); the verdict on L517 is J6's, at PIG-WEB.DATA.INTERFACE.1, and is cited above.
  - P5': acceptable only through expand, migrate, contract, when the inconsistent name costs more than moving every consumer (inferred).
- **Out of this node's rows**: retention, deletion, history tables, bulk jobs and recovery are realized at PIG-WEB.DATA.MAINTAIN.2 to .5 (J6) and have no principle-level row here (gap 3). ACT.4 (audit) is realized at PIG-WEB.DATA.MAINTAIN.3; no philosophy link (gap 1).
- **Realizes**: ALLOCATION.RECORD.3 (keeps the database structure as the origin of every stored fact and of the function API's contract). Refines python-kb-philosophy:REPRODUCIBILITY (skeleton link). Link proposed, not created: realizes ALLOCATION.ACT.4 through history kept in the database.
- **State**: `known | unvalidated: the drift check between live catalogue and migration history, and expand-contract as the only route under MD-03, are inferred | gap: data lifecycle (retention, recovery) has no principle row`. (The former conflict state on L517 is removed after review, m8: the L517 verdict and its conflict are carried once, by J6.)

## DATA.DERIVE Derived, Not Stored

- **Question**: what is stored and what is derived from stored facts.
- **Positions**:
  - P1 store the minimum and derive the rest: eligibility for serving is computed from the state plus the deletion marker, not stored; a derived outcome (an aggregate result) is its own row rather than a state value (L488 MAINT; agrees L072, SRC-304 T3).
  - P2 store derived values for read performance: generated columns for same-row values (L176; SRC-142), derived summaries with a sync mechanism (L531, L532 MAINT), denormalization where measured (L168).
  - P3 encode a derived outcome or eligibility as a stored state value or flag maintained by code (the practice L488 rejects).
- **Forces**: P1 serves integrity: a value that is not stored cannot diverge from its facts. P2 serves read performance and costs a sync mechanism and a drift risk (L532: triggers never diverge but cost write latency; scheduled refresh has a staleness window). P3 serves query convenience and creates a second, divergent statement of the same fact.
- **Decision**: realization of DERIVE.1 (J1), the doctrine being the max choice.
  - **Compute on read by default** (L488, L072; DERIVE.1's first option): eligibility and other predicates over stored facts are computed, not stored.
  - **A derived outcome is a fact of its own**: an aggregate result is stored as its own row, never folded into a state value (L488). Where a state label must agree with such facts, the facts are written first and the label flipped last by its single writer function (L597, L596; J6's PIG-WEB.DATA.CONCURRENCY.6).
  - **A stored derived value is a copy** (RULES.1): allowed when computing on read is measured to be too costly (L168), in DERIVE.1's order: same-row values as generated columns (L176); values that must change atomically with their source maintained in the same transaction, by a trigger, or by the writer function only when the source table admits no other writer (L532; aligned with J6's review fix M2, since only what is bound to the table holds for every writer under MD-03); values that tolerate a stated staleness in cache tables with scheduled refresh or an invalidation queue (L532, L535, L536). Each copy has the sync plan of L469 recorded before it is built and the drift guard of L533. Mechanisms belong to J6 (PIG-WEB.DATA.DERIVE.1 and .2).
- **Rejected**:
  - P2 as a default: rejected; acceptable when measured read cost requires it, under DERIVE.1's order, L469's sync plan and L533's drift guard.
  - P3: never as code-maintained state. A stored predicate is acceptable only as a generated column, which cannot diverge, when an index or a consumer needs it stored (inferred from L176).
- **Realizes**: ALLOCATION.DERIVE.1 (keeps derived values in the tier and freshness the placement sets).
- **State**: `known | unvalidated: the order of options is inherited from DERIVE.1, where it is marked inferred; the trigger-first rule for same-transaction copies and the generated-column exception for stored predicates are inferred`.
