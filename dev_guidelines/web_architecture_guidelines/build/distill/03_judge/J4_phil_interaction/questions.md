# J4 web-app-philosophy INTERACTION: questions for the maintainer

None.

Every INTERACTION node has a winner in the default context (a classic website, one team, JavaScript + Python + Postgres, humans and agents as users, a database shared by several backends and by reporting, consoles and scripts). The two choices the evidence presents as contested were settled without asking, each by a stated condition:

- Automated traffic on sensitive flows (deny automation, or admit agents): the contest is resolved flow by flow, not dissolved. Agents that identify and authenticate themselves are admitted and limited by quota; anonymous automation is denied or challenged on the flows whose automation harms the business. Denying automation still wins on a flow that hands out scarce goods or rewards automation per account (limited stock, referral credit): quotas per agent and approval by the owner do not stop one party that runs many accounts, each with its own approved agent. On such a flow, completing it requires a human, or agents are excluded, whatever their identity. Which flows are of that kind is a decision each project records.
- Choice of real-time channel: correctness never depends on the channel, because every page is correct on plain load and clients catch up after a gap; the simplest channel that meets the need wins.

Not asked here, because it is already awaiting the maintainer elsewhere: when several backends read the same comments, who applies a per-user visibility rule ("a draft reply is visible only to its author"; "a note addressed to named people is visible only to them"). It is the read-visibility question raised for authorization as a whole. Until it is answered, the comments node records the stated default: each backend applies the filter, from one shared written specification that lists every place a comment can surface (lists, counts, notifications, search results, history, exports, cache validators, live channels), and every backend runs the same tests that check those places deny what they must. Database read functions that receive the verified user stay acceptable when a per-user rule must hold for two or more backends.

One consequence of that default the maintainer should see when answering: database roles that may read the comment tables directly, such as reporting and operator roles, see every comment, internal notes and narrow-audience replies included, unless their own access is restricted. The comments node therefore requires, until the question is answered, that those roles get no direct read access to comment content or to comments with a narrower audience than their target, and read comments only through a view limited to comments everyone who sees the target may see, or not at all. If a project does not apply that restriction, the leak to those roles is a known limit, stated where comments are documented.
