# Claims ledger, part 3: language-general principles sent by the JavaScript guideline

Part 3 of the claims ledger. Part 1 (`../claims_ledger.md`) is read-only and untouched; part 3 only adds rows L1501 to L1999 (this file uses L1501 to L1565) and sources REG-1501 to REG-1999 (`sources_part3.md`). Nothing here is grouped under the target hierarchy, owned, judged or dropped.

What was sent. The JavaScript guideline's package (`../../../../../javascript_guidelines/build/handoff/to_software_guideline/package.md`, Part A and Part B) offers the principles of its philosophy graph that hold for any language: 56 nodes sent whole (Part A) and the general parts of 9 nodes that stay there narrowed (Part B). Its claims resolve in the JavaScript guideline's research results (`../../../../../javascript_guidelines/build/research/<slot>/result.md`, slot by claim-id prefix) and its sources in that guideline's source register (`../../../../../javascript_guidelines/build/audit/source_register.md`). The maintainer's ruling (relayed in `../../inputs_from_javascript_guideline.md`): code design belongs in this guideline as long as it holds for every language; JavaScript-specific mechanisms and examples stay in the JavaScript guideline.

Row rule. One row per sent node (uid prefixed `JS:` in `merges`, followed by the claim ids the node rests on). The `statement` is the node's general intent stated so that it holds for every language; JavaScript mechanisms, examples and APIs are removed and each removal is written down in the row's `positions` as "Dropped as JavaScript-specific". A sent node was already judged in the JavaScript guideline, so each row is marked `origin: judged in the JavaScript guideline` and the judge here re-examines it rather than inheriting it. The `positions` column keeps the origin's rejected alternatives and contested points with the condition under which they would win (where the origin states none, the row says so), the origin's epistemic state, the origin's links to other sent nodes (mapped to the row ids here; links to nodes that stay in the JavaScript guideline are named as such), and where a part 1 row states the same thing or an adjacent one, `see also Lnnn`. A `see also` marked `same` states the same thing as the part 1 row; marked `adjacent` it covers a neighbouring point; neither is merged (part 1 is read-only).

Columns as in part 1: `id`, `statement`, `merges`, `areas` (origin branch of the JavaScript philosophy graph, JSG), `level` and `stack` (as recorded by the origin claims; stack is `neutral` for every row because the statements are language-neutral, the origin stack is kept in brackets), `agreement` (as recorded by the origin claims), `positions`, `certainty` (grounded, inferred or open; the row's own certainty, not the origin's carried over), `sources` (register ids, new ones in `sources_part3.md`, reused ones from part 1's `../sources.md`).

Two claims of CONTROL.LIFECYCLE (ASYNC-C05, RUNTIME-C37) are named by the origin's epistemic state but are not carried as a claim table in the package; they are read from the JavaScript research results and listed in `merges` with their source.
