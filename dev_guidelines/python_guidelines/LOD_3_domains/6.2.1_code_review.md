## Core Concept
<!-- Lines 30-50 -->

**Definition:** Code review is the practice of having one or more people examine code changes before they are merged, with goals of catching issues, ensuring standards, and sharing knowledge.

**Key Benefits:**
- Catch bugs before they ship
- Maintain code quality and consistency
- Share knowledge across the team
- Provide learning opportunities
- Create shared ownership

**Review Mindset:**
- For authors: Feedback improves your code
- For reviewers: You're helping, not gatekeeping
- For both: Assume good intent; text lacks tone

## What to Review
<!-- Lines 119-119 -->

### Correctness
<!-- Lines 122-132 -->

```python
# Check: Does it handle edge cases?
def divide(a: float, b: float) -> float:
    return a / b  # ❌ What about b=0?

# Check: Are assumptions valid?
def process_users(users: list[User]) -> None:
    first = users[0]  # ❌ What if empty list?
```

### Clarity
<!-- Lines 135-148 -->

```python
# Review: Is this understandable?
def proc(d, f):  # ❌ Unclear names
    return [f(x) for x in d if x]

# Better
def filter_and_transform(
    items: list[T],
    transform: Callable[[T], R]
) -> list[R]:
    return [transform(item) for item in items if item]
```

### Security
<!-- Lines 160-171 -->

```python
# Check: SQL injection?
cursor.execute(f"SELECT * FROM users WHERE id = {user_id}")  # ❌

# Check: Command injection?
os.system(f"convert {filename}")  # ❌

# Check: Secrets in code?
API_KEY = "sk_live_abc123"  # ❌
```

### Performance
<!-- Lines 174-186 -->

```python

for user in users:
    orders = db.query(Order).filter_by(user_id=user.id).all()  # ❌

    config = load_config()  # ❌ Load once outside loop
```

## Giving Feedback
<!-- Lines 189-189 -->

### Feedback Types
<!-- Lines 192-208 -->

```markdown
**Blocking (Request Changes)**
- Security vulnerabilities
- Correctness bugs
- Missing tests for critical paths

**Non-blocking (Comment)**
- Style preferences not in linter
- Alternative approaches to consider
- Questions for clarification

**Nitpick (Optional)**
- Minor style suggestions
- Prefix with "nit:" to signal low priority
```

### Good Feedback Examples
<!-- Lines 211-228 -->

```markdown
❌ "This is wrong"
✅ "This will throw IndexError for empty lists. Consider:
   `first = items[0] if items else None`"

❌ "Bad variable name"
✅ "Consider renaming `d` to `user_data` for clarity"

❌ "Fix the tests"
✅ "The test doesn't cover the case where `quantity` is 0.
   Could you add a test like `test_order_zero_quantity`?"

❌ "Why did you do it this way?"
✅ "I'm curious about choosing recursion here. Was iteration
   considered? Asking because of the recursion limit for deep trees."
```

### Receiving Feedback
<!-- Lines 231-248 -->

```markdown
## When you get feedback:
<!-- Lines 242-247 -->

1. **Assume good intent** - Reviewers want to help
2. **Ask for clarification** - If feedback is unclear
3. **Push back thoughtfully** - If you disagree, explain why
4. **Thank reviewers** - They spent time on your code

## Response patterns:
<!-- Lines 250-255 -->

- "Good catch, fixed!"
- "I chose X because Y. Would you prefer Z?"
- "Could you clarify what you mean by...?"
- "I see your point, but I think X is better here because..."
```
