## Core Concept
<!-- Lines 35-55 -->

**Definition:** Requirements gathering is the systematic process of discovering, documenting, and validating what a system should do and how it should behave.

**Key Points:**
- Requirements are discovered, not invented
- Stakeholders often can't articulate implicit needs
- What people say they want differs from what they need
- Requirements evolve—capture them iteratively

**The Discovery Mindset:**
- Ask "why?" repeatedly to find root needs
- Observe behavior, not just listen to words
- Document assumptions explicitly
- Validate early and often

## When to Use
<!-- Lines 58-78 -->

**Use When:**
- Starting a new project
- Adding significant features
- Requirements are unclear or conflicting
- Stakeholders disagree on priorities
- Building for unfamiliar domain

**Avoid When:**
- Requirements are already well-documented
- Making minor changes to existing system
- Time pressure makes full analysis impractical (but document this risk)

**Signals You Need More Gathering:**
- Frequent "I thought it would..." from stakeholders
- Different team members have different understanding
- Scope keeps changing
- Requirements documents gather dust unused

## Gathering Techniques
<!-- Lines 81-81 -->

### Stakeholder Interviews
<!-- Lines 84-105 -->

**Preparation:**
- Identify all stakeholder types (users, admins, management, support)
- Prepare open-ended questions
- Schedule adequate time (45-60 minutes)

**Question Types:**

| Type | Example | Purpose |
|------|---------|---------|
| Problem | "What problem does this solve?" | Understand the need |
| Current | "How do you do this today?" | Find pain points |
| Success | "What would success look like?" | Define goals |
| Edge | "What happens when X fails?" | Find edge cases |
| Priority | "What's most important?" | Understand value |

**Interview Tips:**
- Listen more than talk
- Ask follow-up "why" questions
- Take notes on exact words used (domain vocabulary)
- Don't propose solutions during gathering

### Document Analysis
<!-- Lines 108-115 -->

**Sources to Review:**
- Existing system documentation
- Process documents and SOPs
- Support tickets and bug reports
- Training materials
- Competitor products

### Observation
<!-- Lines 118-129 -->

**Watch Users Work:**
- Shadowing: Observe without interrupting
- Think-aloud: User narrates their actions
- Contextual inquiry: Ask questions during observation

**Look For:**
- Workarounds and manual processes
- Frequently repeated actions
- Points of frustration
- Undocumented tribal knowledge

### Workshops
<!-- Lines 132-142 -->

**Group Techniques:**
- Brainstorming sessions
- User story mapping
- Journey mapping
- Prototype walkthroughs

### Requirement Attributes
<!-- Lines 260-271 -->

Each requirement should have:

| Attribute | Purpose |
|-----------|---------|
| ID | Unique identifier (FR-001) |
| Description | What it means |
| Priority | Must/Should/Could |
| Source | Who requested it |
| Status | Proposed/Approved/Implemented |
| Rationale | Why it's needed |

### Validation
<!-- Lines 274-282 -->

Requirements are valid when:
- Stakeholders agree they're correct
- They're testable (can verify when met)
- They're consistent (don't contradict each other)
- They're feasible (can be built with resources)
