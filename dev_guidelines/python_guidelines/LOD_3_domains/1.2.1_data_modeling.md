## Core Concept
<!-- Lines 35-64 -->

**Definition:** Data modeling is the process of defining the structure of your data: what entities exist, what attributes they have, and how they relate to each other.

**Key Points:**
- Data outlives code—design for stability
- Model the domain, not the implementation
- Types and constraints make invalid states impossible
- Schema is documentation that executes

**Why Data First:**
- Code is derived from data structure
- Good data model simplifies code
- Bad data model complicates everything
- Migration costs increase over time

**The Data Model Hierarchy:**
```
Conceptual Model (entities, relationships)
    ↓
Logical Model (attributes, types, constraints)
    ↓
Physical Model (database tables, indexes)
```

## When to Use
<!-- Lines 67-89 -->

**Use When:**
- Starting any project with persistent data
- Adding new features with new entities
- Refactoring existing data structures
- Performance requires structural changes
- Integration with external systems

**Model First When:**
- Requirements are clear enough to identify entities
- Multiple developers need shared understanding
- Data will persist beyond initial implementation
- Integrations depend on data structure

**Signs You Need Better Modeling:**
- Duplicate data in multiple places
- Queries are complex and slow
- Business logic scattered across codebase
- Data integrity issues
- "Just add another column" culture

## Entity Identification
<!-- Lines 92-92 -->

### Finding Entities
<!-- Lines 95-110 -->

**Technique: Noun Extraction**

From requirements, extract nouns:
```
"Users create tasks in projects with due dates and tags"

Nouns: User, Task, Project, DueDate(?), Tag
```

**Questions for Each Noun:**
- Does it have identity? (User: yes, DueDate: no—it's an attribute)
- Does it have attributes? (Task: title, description, status)
- Does it have relationships? (Task belongs to Project)
- Does it have lifecycle? (Task: created → completed → archived)

### Entity vs Attribute vs Value Object
<!-- Lines 113-119 -->

| Type | Has Identity | Has Attributes | Example |
|------|--------------|----------------|---------|
| Entity | Yes | Yes | User, Task, Project |
| Attribute | No | No | title, email, created_at |
| Value Object | No | Yes | Address, Money, DateRange |

## Relationships
<!-- Lines 151-151 -->

### Relationship Types
<!-- Lines 154-172 -->

**One-to-One:** One entity has exactly one of another
```
User ←→ UserProfile
(Each user has one profile)
```

**One-to-Many:** One entity has many of another
```
Project ← Tasks
(One project has many tasks)
```

**Many-to-Many:** Many of one entity relate to many of another
```
Task ←→ Tag (via TaskTag junction)
(Tasks have many tags; tags apply to many tasks)
```

### Modeling Relationships
<!-- Lines 175-196 -->

```python
@dataclass
class Project:
    id: UUID
    owner_id: UUID  # FK to User (one-to-many: User → Projects)
    name: str

@dataclass
class Task:
    id: UUID
    project_id: UUID | None  # FK to Project (nullable one-to-many)
    creator_id: UUID  # FK to User (required one-to-many)
    title: str

# Many-to-many via junction
@dataclass
class TaskTag:
    task_id: UUID  # FK to Task
    tag_id: UUID   # FK to Tag
```

### Cardinality and Optionality
<!-- Lines 199-206 -->

| Notation | Meaning |
|----------|---------|
| 1..1 | Exactly one, required |
| 0..1 | Zero or one, optional |
| 1..* | One or more |
| 0..* | Zero or more |

### Relationship Questions
<!-- Lines 209-219 -->

For each relationship, ask:
- Is it required or optional?
- What happens on delete? (cascade, restrict, nullify)
- Can it change after creation?
- Does it need history?

## Normalization
<!-- Lines 222-222 -->

### Why Normalize
<!-- Lines 225-231 -->

Normalization eliminates data redundancy:
- Updates happen in one place
- No inconsistency between duplicates
- Storage is efficient
- Integrity is enforced

### Normal Forms (Simplified)
<!-- Lines 234-265 -->

**1NF:** No repeating groups
```
# Wrong: tags as comma-separated string
Task(id, title, tags="work,urgent,review")

# Right: separate Tags table
Task(id, title)
TaskTag(task_id, tag_id)
Tag(id, name)
```

**2NF:** No partial dependencies
```
# Wrong: project_name depends on project_id, not task_id
Task(id, project_id, project_name, title)

# Right: project_name in Project table
Task(id, project_id, title)
Project(id, name)
```

**3NF:** No transitive dependencies
```
# Wrong: owner_email depends on owner_id
Project(id, owner_id, owner_email, name)

# Right: email in User table
Project(id, owner_id, name)
User(id, email)
```

### When to Denormalize
<!-- Lines 268-287 -->

Sometimes denormalization is appropriate:
- **Performance:** Reduce joins for frequent queries
- **Read-heavy:** Precomputed aggregates
- **Caching:** Materialized views

Document denormalization decisions:
```markdown
## Denormalization: task_count in Project
<!-- Lines 279-288 -->

**Reason:** Avoid COUNT query on every project list
**Trade-off:** Must update on task create/delete
**Sync strategy:** Update in same transaction
```

### Making Invalid States Unrepresentable
<!-- Lines 346-370 -->

```python
# Weak: status and completed_at can be inconsistent
@dataclass
class Task:
    status: str  # "complete" or not
    completed_at: datetime | None  # Can be None even when complete

# Strong: type encodes state
@dataclass
class PendingTask:
    title: str

@dataclass
class CompletedTask:
    title: str
    completed_at: datetime  # Required

Task = PendingTask | CompletedTask
```
