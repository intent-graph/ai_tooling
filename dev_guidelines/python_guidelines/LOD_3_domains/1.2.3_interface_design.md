## Core Concept
<!-- Lines 30-61 -->

**Definition:** Interface design defines the contracts between components—what operations are available, what inputs they accept, and what outputs they produce.

**Key Points:**
- Interfaces are promises to consumers
- Good interfaces hide implementation details
- Stable interfaces enable independent development
- Design interfaces before implementation

**Interface = Contract:**
```
Consumer → Interface → Implementation
             │
         Promise of:
         - What operations exist
         - What inputs are accepted
         - What outputs are returned
         - What errors can occur
```

**Why Interfaces First:**
- Enables parallel development
- Forces clarity of purpose
- Reveals design problems early
- Documentation that compiles

## When to Use
<!-- Lines 64-85 -->

**Design Interfaces When:**
- Defining module boundaries
- Multiple implementations expected
- Testing requires substitution
- Team members work on different sides
- External consumers will use the code

**Interface First When:**
- Building a library
- Creating service boundaries
- Designing for testability
- Working with abstractions

**Signs of Poor Interfaces:**
- Consumers need to know implementation details
- Frequent breaking changes
- Hard to mock in tests
- Unclear what inputs are valid

## Function Signatures
<!-- Lines 88-88 -->

### Designing Signatures
<!-- Lines 91-106 -->

Function signatures are the atomic unit of interface design.

**Anatomy:**
```python
def create_task(
    title: str,                    # Required, positional-or-keyword
    creator_id: UUID,              # Required, positional-or-keyword
    *,                             # Keyword-only after this
    project_id: UUID | None = None,  # Optional, keyword-only
    due_date: date | None = None,    # Optional, keyword-only
) -> Task:                         # Return type
    """Create a new task."""
    ...
```

### Parameter Design Choices
<!-- Lines 109-140 -->

**Positional vs Keyword:**
```python
# Good: Commonly used params can be positional
create_task("Buy milk", user.id)

# Good: Optional/rare params are keyword-only
create_task("Buy milk", user.id, due_date=tomorrow)
```

**Required vs Optional:**
```python
# Required: Must always be provided
def send_email(to: str, subject: str, body: str) -> None: ...

# Optional with default: Common case has sensible default
def fetch_users(limit: int = 100, offset: int = 0) -> list[User]: ...
```

**Explicit None vs Omission:**
```python
# When None is meaningful
def update_task(id: UUID, due_date: date | None) -> Task:
    # None means "clear the due date"
    ...

# When absence means "don't change"
def update_task(id: UUID, due_date: date | UNSET = UNSET) -> Task:
    # UNSET means "leave as-is"
    ...
```

### Return Values
<!-- Lines 143-165 -->

**Single return type:**
```python
def get_task(id: UUID) -> Task | None:
    """Return Task if found, None if not."""
    ...
```

**Multiple values via dataclass:**
```python
@dataclass
class CreateTaskResult:
    task: Task
    notifications_sent: int

def create_task(...) -> CreateTaskResult:
    ...
```

## Protocols and ABCs
<!-- Lines 168-168 -->

### Protocols (Structural Subtyping)
<!-- Lines 171-199 -->

Protocols define what methods an object must have:

```python
from typing import Protocol

class Repository(Protocol):
    """Interface for data persistence."""

    def save(self, entity: Entity) -> None: ...
    def get(self, id: UUID) -> Entity | None: ...
    def delete(self, id: UUID) -> None: ...

# Any class with these methods satisfies Repository
class InMemoryRepository:
    def save(self, entity: Entity) -> None:
        self._store[entity.id] = entity

    def get(self, id: UUID) -> Entity | None:
        return self._store.get(id)

    def delete(self, id: UUID) -> None:
        del self._store[id]

# Type checker accepts this:
def use_repo(repo: Repository) -> None:
    repo.save(entity)
```

### Abstract Base Classes
<!-- Lines 202-225 -->

ABCs enforce inheritance and can provide default implementations:

```python
from abc import ABC, abstractmethod

class Repository(ABC):
    """Base class for repositories."""

    @abstractmethod
    def save(self, entity: Entity) -> None:
        """Persist an entity."""
        ...

    @abstractmethod
    def get(self, id: UUID) -> Entity | None:
        """Retrieve an entity."""
        ...

    def exists(self, id: UUID) -> bool:
        """Default implementation using get."""
        return self.get(id) is not None
```

### Protocol vs ABC
<!-- Lines 228-250 -->

| Aspect | Protocol | ABC |
|--------|----------|-----|
| Inheritance required | No | Yes |
| Default implementations | No | Yes |
| Runtime checking | Optional | Built-in |
| Duck typing | ✅ Native | ❌ Requires registration |
| Use case | Flexible interfaces | Shared behavior |

**Prefer Protocol when:**
- Multiple unrelated classes implement it
- You want duck typing with type safety
- Testing with mocks

**Prefer ABC when:**
- Sharing common implementation
- Enforcing explicit inheritance
- Runtime isinstance checks needed

## Design Principles
<!-- Lines 253-253 -->

### Minimal Interfaces
<!-- Lines 256-273 -->

Expose only what consumers need:

```python
# Too broad: Exposes internal details
class TaskService:
    def create_task(self, ...) -> Task: ...
    def _validate(self, ...) -> None: ...  # Internal
    def _notify(self, ...) -> None: ...    # Internal
    connection: Connection  # Internal state

# Minimal: Only public operations
class TaskService(Protocol):
    def create_task(self, ...) -> Task: ...
    def get_task(self, id: UUID) -> Task | None: ...
    def list_tasks(self, ...) -> list[Task]: ...
```

### Stable Interfaces
<!-- Lines 276-292 -->

Design for change without breaking consumers:

```python
# Fragile: Adding parameters breaks callers
def create_task(title, description, due_date): ...

# Stable: Keyword-only params are additive
def create_task(
    title: str,
    *,
    description: str = "",
    due_date: date | None = None,
    priority: Priority = Priority.NORMAL,  # Added later, no breakage
) -> Task: ...
```

### Obvious Interfaces
<!-- Lines 295-309 -->

Make correct usage easy, incorrect usage hard:

```python
# Easy to misuse: What's the difference?
def process(data: dict, flag1: bool, flag2: bool): ...

# Obvious: Types guide correct usage
def process(
    data: ProcessInput,
    mode: ProcessingMode,
    output_format: OutputFormat,
) -> ProcessOutput: ...
```

### Consistent Interfaces
<!-- Lines 312-326 -->

Similar operations should have similar signatures:

```python
# Inconsistent: Different patterns for same concept
def get_user(user_id: int) -> User: ...
def fetch_project(id: UUID) -> Project | None: ...
def load_task(task_id: str) -> Optional[Task]: ...

# Consistent: Same pattern throughout
def get_user(id: UUID) -> User | None: ...
def get_project(id: UUID) -> Project | None: ...
def get_task(id: UUID) -> Task | None: ...
```

### Document Contracts

def transfer_funds(
    from_account: UUID,
    to_account: UUID,
    amount: Decimal,
) -> Transfer:
    """Transfer funds between accounts.

    Args:

    """
