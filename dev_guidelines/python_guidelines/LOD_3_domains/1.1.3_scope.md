## Core Concept
<!-- Lines 36-62 -->

**Definition:** Scope definition explicitly states what is included in a project, what is excluded, and what is deferred to future work.

**Key Points:**
- Explicit boundaries prevent scope creep
- "Out of scope" is as important as "in scope"
- Deferred items are not rejected, just delayed
- Scope should be agreed upon by all stakeholders

**The Scope Triangle:**
```
        Scope
         /\
        /  \
       /    \
      /______\
   Time     Resources
```

You can fix two; the third adjusts. Undefined scope means unpredictable time/resources.

## When to Use
<!-- Lines 65-86 -->

**Use When:**
- Starting any project
- Planning a release or sprint
- Stakeholders have different expectations
- Resources or time are constrained
- Scope is unclear or expanding

**Revisit When:**
- Requirements change significantly
- New stakeholder needs emerge
- Timeline or budget changes
- Mid-project course correction needed

**Scope Creep Signals:**
- "While we're at it, can we also..."
- Features appearing without documentation
- Deadlines slipping despite progress
- Team unsure what's "done"

## MVP Definition
<!-- Lines 166-166 -->

### What Makes an MVP
<!-- Lines 169-178 -->

**Minimum:** Smallest possible
**Viable:** Delivers real value
**Product:** Usable by real users

An MVP is NOT:
- A demo or prototype
- An incomplete product
- A feature list arbitrarily cut

### MVP Criteria
<!-- Lines 181-188 -->

Must answer "yes" to all:
1. Does it solve the core problem?
2. Can users accomplish their goal?
3. Is it usable (not just functional)?
4. Can we learn from user behavior?
5. Can we ship it?

### MVP Scoping Process
<!-- Lines 191-202 -->

**Step 1:** List all desired features

**Step 2:** Categorize each:
- Essential: MVP fails without it
- Important: Significantly better with it
- Nice-to-have: Better but not critical

**Step 3:** Include only "Essential" in MVP

**Step 4:** Validate: Is it still viable?

## Managing Scope
<!-- Lines 235-235 -->

### Scope Change Process
<!-- Lines 238-249 -->

When new requests arrive:

```
1. Document the request
2. Assess impact (time, resources, dependencies)
3. Evaluate against current scope
4. Decision: Add (remove something else) / Defer / Reject
5. Update scope document
6. Communicate to stakeholders
```

### Saying No
<!-- Lines 252-262 -->

Scope protection requires saying "no" or "not now":

**"That's a great idea for v2"** — Acknowledge, defer

**"Let's add that to the backlog"** — Capture without committing

**"What would you remove to add this?"** — Trade-off conversation

**"That's out of scope because..."** — Explain the boundary

### Scope Document Maintenance
<!-- Lines 265-271 -->

The scope document is living:
- Review at sprint/iteration boundaries
- Update when changes are approved
- Keep history of changes and reasons
- Make accessible to all stakeholders

### Red Flags
<!-- Lines 274-281 -->

- No written scope document
- Scope changes without impact assessment
- Stakeholders surprised by what's "in" or "out"
- Scope keeps growing, timeline stays fixed
