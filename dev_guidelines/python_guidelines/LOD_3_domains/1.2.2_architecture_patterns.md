## Core Concept
<!-- Lines 42-70 -->

**Definition:** Architecture patterns are proven templates for organizing code into components and defining how those components interact.

**Key Points:**
- Choose the simplest pattern that meets your needs
- Patterns are about boundaries and dependencies
- Wrong pattern creates friction; right pattern enables growth
- Patterns can be mixed within a system

**Why Architecture Matters:**
- Determines how changes propagate
- Affects testability
- Constrains scalability options
- Shapes team organization

**Common Patterns:**
| Pattern | Primary Use | Key Benefit |
|---------|-------------|-------------|
| Layered | General CRUD apps | Simple, familiar |
| Hexagonal | Complex domains | Testability, flexibility |
| Pipeline | Data processing | Clear flow, composability |
| Plugin | Extensibility needed | Customization |

## When to Use
<!-- Lines 73-94 -->

**Choose Architecture When:**
- Starting a new project
- Major refactoring effort
- System boundaries are unclear
- Testability is a priority
- Team needs shared mental model

**Signs of Wrong Architecture:**
- Simple changes touch many files
- Testing requires extensive mocking
- Circular dependencies emerge
- Business logic scattered everywhere
- "Where does this code go?" confusion

**Architecture Selection Timing:**
- Too early: May not understand needs
- Too late: Expensive to change
- Right time: After requirements, before implementation

## Layered Architecture
<!-- Lines 97-97 -->

### Structure
<!-- Lines 100-112 -->

```
┌─────────────────────────────────────┐
│         Presentation Layer          │ ← HTTP handlers, CLI, UI
├─────────────────────────────────────┤
│         Application Layer           │ ← Use cases, orchestration
├─────────────────────────────────────┤
│           Domain Layer              │ ← Business logic, entities
├─────────────────────────────────────┤
│        Infrastructure Layer         │ ← Database, external APIs
└─────────────────────────────────────┘
```

### Layer Responsibilities
<!-- Lines 115-139 -->

**Presentation:** Handle external interface
- Receive requests
- Validate input format
- Call application layer
- Format responses

**Application:** Orchestrate use cases
- Coordinate domain objects
- Handle transactions
- Enforce business workflows
- No business logic

**Domain:** Business rules and entities
- Core business logic
- Entity definitions
- Domain services
- No framework dependencies

**Infrastructure:** External systems
- Database access
- External API clients
- File system
- Message queues

### Rules
<!-- Lines 142-146 -->

1. **Dependency direction:** Upper layers depend on lower
2. **No skipping:** Presentation doesn't call Infrastructure directly
3. **Domain is pure:** No framework imports in domain layer

### Python Example
<!-- Lines 149-172 -->

```
myproject/
├── presentation/
│   ├── api/
│   │   └── routes.py
│   └── cli/
│       └── commands.py
├── application/
│   └── services.py
├── domain/
│   ├── entities.py
│   └── services.py
└── infrastructure/
    ├── database/
    │   └── repositories.py
    └── external/
        └── api_client.py
```

## Hexagonal Architecture
<!-- Lines 175-175 -->

### Structure
<!-- Lines 178-199 -->

```
          ┌─────────────────────────────────┐
          │         Adapters (Driving)       │
          │   HTTP │ CLI │ Queue │ Tests    │
          └───────────────┬─────────────────┘
                          │
              ┌───────────▼───────────┐
              │    Ports (Interfaces)   │
              │ ┌─────────────────────┐ │
              │ │       Core          │ │
              │ │  Domain + Application│ │
              │ └─────────────────────┘ │
              │    Ports (Interfaces)   │
              └───────────┬───────────┘
                          │
          ┌───────────────▼─────────────────┐
          │        Adapters (Driven)         │
          │  Database │ API │ Files │ Cache  │
          └─────────────────────────────────┘
```

### Components
<!-- Lines 202-217 -->

**Core (Inside):**
- Domain entities and logic
- Application use cases
- Pure, no external dependencies

**Ports (Boundaries):**
- Interfaces defining what core needs
- Input ports: What core provides
- Output ports: What core requires

**Adapters (Outside):**
- Implement ports
- Connect to external world
- Easily replaceable

### Benefits
<!-- Lines 220-224 -->

- **Testability:** Core is pure, test without infrastructure
- **Flexibility:** Swap adapters without changing core
- **Clarity:** Explicit boundaries via ports

### Python Example
<!-- Lines 227-255 -->

```python
# Port (interface)
class TaskRepository(Protocol):
    def save(self, task: Task) -> None: ...
    def get(self, id: UUID) -> Task | None: ...

# Core (uses port)
class TaskService:
    def __init__(self, repo: TaskRepository):
        self.repo = repo

    def complete_task(self, id: UUID) -> Task:
        task = self.repo.get(id)
        task.status = TaskStatus.COMPLETE
        self.repo.save(task)
        return task

# Adapter (implements port)
class PostgresTaskRepository:
    def save(self, task: Task) -> None:
        # Database implementation
        pass
```

## Pipeline Architecture
<!-- Lines 258-258 -->

### Structure
<!-- Lines 261-268 -->

```
Input → Stage 1 → Stage 2 → Stage 3 → Output
          │          │          │
          ▼          ▼          ▼
       Transform  Transform  Transform
```

### Characteristics
<!-- Lines 271-276 -->

- **Linear flow:** Data moves through stages
- **Stateless stages:** Each stage is independent
- **Composable:** Stages can be reordered, added, removed
- **Parallel-friendly:** Stages can run concurrently

### Use Cases
<!-- Lines 279-284 -->

- ETL pipelines
- Data processing
- Build systems
- Request processing middleware

### Python Example
<!-- Lines 287-318 -->

```python
from typing import Callable, TypeVar

T = TypeVar("T")

def pipeline(*stages: Callable[[T], T]) -> Callable[[T], T]:
    def run(data: T) -> T:
        result = data
        for stage in stages:
            result = stage(result)
        return result
    return run

# Define stages
def validate(data: dict) -> dict:
    # Validation logic
    return data

def transform(data: dict) -> dict:
    # Transformation logic
    return data

def enrich(data: dict) -> dict:
    # Enrichment logic
    return data

# Compose pipeline
process = pipeline(validate, transform, enrich)
result = process(input_data)
```

### Pipeline vs Layered
<!-- Lines 321-331 -->

| Aspect | Pipeline | Layered |
|--------|----------|---------|
| Data flow | Linear, explicit | Vertical, implicit |
| State | Stateless stages | Stateful services |
| Best for | Data processing | Request/response |

## Selection Guide
<!-- Lines 334-334 -->

### Decision Matrix
<!-- Lines 337-346 -->

| Factor | Layered | Hexagonal | Pipeline |
|--------|---------|-----------|----------|
| CRUD apps | ✅ Best | ⚠️ Overkill | ❌ Poor fit |
| Complex domain | ⚠️ Struggles | ✅ Best | ❌ Poor fit |
| Data processing | ❌ Poor fit | ⚠️ Can work | ✅ Best |
| Many integrations | ⚠️ Messy | ✅ Best | ⚠️ Limited |
| Team familiarity | ✅ Common | ⚠️ Learning curve | ⚠️ Context-dependent |
| Testability needs | ⚠️ Moderate | ✅ Best | ✅ Good |

### Selection Questions
<!-- Lines 349-366 -->

1. **What's the primary activity?**
   - CRUD operations → Layered
   - Complex business rules → Hexagonal
   - Data transformation → Pipeline

2. **How many external integrations?**
   - Few, stable → Layered fine
   - Many, changing → Hexagonal

3. **How important is testability?**
   - Standard → Layered
   - Critical → Hexagonal

4. **What does the team know?**
   - Familiar with layered → Start there
   - Experienced → Choose based on problem

### Mixing Patterns
<!-- Lines 369-374 -->

Patterns can coexist:
- Hexagonal core with pipeline data processing
- Layered app with plugin extensibility
- Main service layered, integrations hexagonal

### Anti-Patterns
<!-- Lines 377-391 -->

**Big Ball of Mud:** No discernible architecture
- Everything depends on everything
- Changes ripple unpredictably

**Over-Engineering:** Architecture for imaginary needs
- Hexagonal for simple CRUD
- Microservices for single app

**Under-Engineering:** No architecture at all
- Works initially, painful at scale
- Technical debt accumulates
