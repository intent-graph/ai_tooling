## Core Concept
<!-- Lines 27-41 -->

Version numbers communicate change impact. Users rely on versions to understand upgrade risk. The scheme you choose should match your stability promises.

**Choosing a Scheme:**
- API stability matters → SemVer
- Time-based releases → CalVer
- Internal/rapid iteration → CalVer or SemVer with 0.x

## Semantic Versioning
<!-- Lines 44-81 -->

SemVer: `MAJOR.MINOR.PATCH`

**Increment Rules:**
- **MAJOR**: Breaking changes (API incompatible)
- **MINOR**: New features (backward compatible)
- **PATCH**: Bug fixes (backward compatible)

```
1.0.0  # Initial stable release
1.0.1  # Bug fix
1.1.0  # New feature
2.0.0  # Breaking change
```

**Pre-release Versions:**
```
1.0.0-alpha.1  # Alpha
1.0.0-beta.1   # Beta
1.0.0-rc.1     # Release candidate
```

**When to Use:**
- Libraries with public APIs
- Packages where users depend on stability
- Long-term maintained projects

**0.x Versions:**
```
0.1.0  # Anything can change
0.2.0  # Breaking changes allowed
1.0.0  # First stable release
```

During 0.x, MINOR can contain breaking changes. This signals "not yet stable."

## Calendar Versioning
<!-- Lines 84-115 -->

CalVer: Version based on release date.

**Common Formats:**
```
2024.1.0     # YYYY.MINOR.MICRO
2024.01.15   # YYYY.MM.DD
24.1         # YY.MINOR
```

**When to Use:**
- Applications (not libraries)
- Projects without API stability promises
- Regular release schedules
- Large frameworks (Ubuntu, pip)

**Examples:**
| Project | Format | Example |
|---------|--------|---------|
| pip | YY.N | 23.3 |
| Ubuntu | YY.MM | 24.04 |
| Black | YY.N.N | 23.10.1 |

**Hybrid Approach:**
```
2024.1.0   # January 2024, first release
2024.1.1   # January 2024, patch
2024.2.0   # February 2024
```

## PEP 440
<!-- Lines 118-151 -->

PEP 440 defines valid Python version strings. All schemes must comply.

**Valid Formats:**
```python
"1.0"           # Simple
"1.0.0"         # Three-part
"1.0.0a1"       # Alpha
"1.0.0b1"       # Beta
"1.0.0rc1"      # Release candidate
"1.0.0.post1"   # Post-release
"1.0.0.dev1"    # Development
```

**Ordering:**
```
1.0.0.dev1 < 1.0.0a1 < 1.0.0b1 < 1.0.0rc1 < 1.0.0 < 1.0.0.post1 < 1.0.1
```

**Invalid (avoid):**
```python
"1.0-beta"      # Use 1.0b1
"1.0_1"         # Use 1.0.1
"v1.0.0"        # No 'v' prefix
```

**Local Versions:**
```python
"1.0.0+local"   # Local version identifier
"1.0.0+build123"  # Not uploaded to PyPI
```

## Changelog
<!-- Lines 154-209 -->

Every version should have a corresponding changelog entry.

**CHANGELOG.md Format:**
```markdown
# Changelog

## [2.1.0] - 2024-01-15
<!-- Lines 170-170 -->

### Added
<!-- Lines 173-174 -->
- New `export_csv()` function

### Changed
<!-- Lines 177-178 -->
- Improved error messages

### Fixed
<!-- Lines 181-182 -->
- Fixed timezone handling in date parser

### Deprecated
<!-- Lines 185-186 -->
- `old_function()` will be removed in 3.0

### Removed
<!-- Lines 189-190 -->
- Removed Python 3.8 support

## [2.0.0] - 2024-01-01
<!-- Lines 193-193 -->

### Breaking Changes
<!-- Lines 196-216 -->
- Renamed `get_data()` to `fetch_data()`
```

**Towncrier (automated):**
```
changes/
├── 123.feature.md   # "Added user export"
├── 145.bugfix.md    # "Fixed date parsing"
└── 150.breaking.md  # "Renamed API method"
```

```bash
towncrier build --version 2.1.0
# Compiles fragments into CHANGELOG.md
```

**Keep a Changelog Principles:**
- Written for humans, not machines
- Entry per version
- Group by change type
- Newest first
