## Core Concept
<!-- Lines 35-59 -->

**Definition:**
- **Constraints** are fixed boundaries you cannot change
- **Assumptions** are beliefs you think are true but haven't verified

**Key Points:**
- Constraints limit your solution space
- Assumptions are risks until validated
- Both must be documented explicitly
- Undocumented constraints cause surprises; unvalidated assumptions cause failures

**The Distinction:**

| Aspect | Constraint | Assumption |
|--------|------------|------------|
| Certainty | Known to be true | Believed to be true |
| Control | Cannot change | May be wrong |
| Action | Design around it | Validate or plan for failure |

## When to Use
<!-- Lines 62-82 -->

**Document Constraints When:**
- Starting a project (capture all known limits)
- Making architectural decisions (constraints limit options)
- Evaluating solutions (does it violate constraints?)
- Onboarding team members (they need context)

**Document Assumptions When:**
- Making decisions based on unverified information
- Dependencies on external factors
- User behavior is expected but not proven
- Technical capabilities are untested

**Warning Signs:**
- "I thought that was obvious"
- Different team members have different understanding
- Decisions invalidated by reality
- Surprises late in project

## Managing Assumptions
<!-- Lines 153-153 -->

### Documenting Assumptions
<!-- Lines 156-170 -->

For each assumption, record:

```markdown
## Assumptions
<!-- Lines 172-180 -->

| ID | Assumption | Risk if Wrong | Validation Plan |
|----|------------|---------------|-----------------|
| A-001 | Users have modern browsers | UI breaks | Check analytics |
| A-002 | API rate limits won't change | Failures | Contract review |
| A-003 | Peak usage 9-5 EST | Scaling issues | Monitor usage |
| A-004 | 100 max tasks per user | Performance | User research |
```

### Risk Assessment
<!-- Lines 173-178 -->

For each assumption:
1. **Likelihood of being wrong:** High / Medium / Low
2. **Impact if wrong:** High / Medium / Low
3. **Priority:** Likelihood × Impact

### Validation Strategies
<!-- Lines 181-196 -->

**For user behavior assumptions:**
- User research / interviews
- Analytics from similar systems
- Beta testing with real users

**For technical assumptions:**
- Proof of concept / spike
- Load testing
- Integration testing early

**For external assumptions:**
- Contract review
- Direct communication with providers
- Written commitments

### When Assumptions Fail
<!-- Lines 199-212 -->

Have contingency plans:

```markdown
Assumption A-003: Peak usage is 9-5 EST

If wrong:
- Immediate: Scale manually
- Short-term: Implement auto-scaling
- Long-term: Redesign for global usage
```
