## Naming Philosophy
<!-- Lines 17-43 -->

Names are the primary interface between code and humans. Invest time finding the right name.

**The 20-Minute Rule:**
If you can't name something well, you may not understand it well. Spending 20 minutes on a name is worthwhile if thousands of developers will read it.

**Good Names Are:**
- **Unambiguous**: Only one interpretation
- **Pronounceable**: Can discuss verbally
- **Searchable**: Unique enough to grep
- **Consistent**: Follow existing patterns

**Name Length Guidelines:**
| Scope | Length | Example |
|-------|--------|---------|
| Loop variable | 1-3 chars | `i`, `x`, `idx` |
| Local variable | Short | `user`, `count` |
| Function | Medium | `calculate_total` |
| Class | Medium | `UserRepository` |
| Module | Short-medium | `auth`, `user_service` |

## Naming Conventions
<!-- Lines 46-82 -->

Python has established conventions (PEP 8). Follow them.

**Convention Table:**

| Element | Convention | Example |
|---------|------------|---------|
| Module | snake_case | `user_service.py` |
| Package | snake_case | `my_package/` |
| Class | PascalCase | `UserService` |
| Exception | PascalCase + Error | `ValidationError` |
| Function | snake_case | `get_user_by_id` |
| Method | snake_case | `calculate_total` |
| Variable | snake_case | `user_count` |
| Constant | UPPER_SNAKE | `MAX_RETRIES` |
| Type variable | PascalCase | `T`, `UserType` |

**Private Indicators:**
```python
_internal_var      # Convention: internal use
__mangled_var      # Name mangling (avoid unless needed)
var_               # Trailing underscore avoids keyword conflict
```

**Special Names:**
```python
__init__           # Constructor
__str__            # String representation
__enter__/__exit__ # Context manager
```

## Naming Hierarchy
<!-- Lines 85-130 -->

Names should reflect scope and importance.

**Module Names:**
- Short, lowercase, descriptive
- Avoid generic names (`utils`, `helpers`, `misc`)
- Use plural for collections: `models`, `exceptions`

**Class Names:**
- Noun or noun phrase
- Describe what it is, not what it does
- Suffix with role: `Repository`, `Service`, `Handler`

```python
# Good
class UserRepository:     # What it is
class EmailValidator:     # What it validates
class PaymentService:     # What domain it serves

# Avoid
class UserManager:        # Vague "manager"
class DataHandler:        # Too generic
```

**Function Names:**
- Verb or verb phrase
- Describe action performed
- Boolean functions: `is_`, `has_`, `can_`

```python
# Good
def calculate_total(items: list[Item]) -> Decimal:
def is_valid_email(email: str) -> bool:
def fetch_user_by_id(user_id: int) -> User:

# Avoid
def process(data):        # Too vague
def do_stuff():           # Meaningless
```

## Domain Vocabulary
<!-- Lines 133-166 -->

Use consistent terminology from your domain.

**Establish a Glossary:**
- Define domain terms once
- Use them consistently everywhere
- Code should match specification language

**Example Domain Vocabulary:**
```python
# E-commerce domain
class Order:          # Not: Purchase, Transaction
class LineItem:       # Not: OrderItem, ProductLine
class Cart:           # Not: Basket, Bag

def place_order():    # Not: submit_order, create_order
def add_to_cart():    # Not: add_item, put_in_basket
```

**Consistency Over Perfection:**
If existing code uses `customer`, don't introduce `client` for the same concept.

```python
# BAD: Inconsistent vocabulary
customer = get_client(id)
user = find_customer(id)

# GOOD: Consistent vocabulary
customer = get_customer(id)
customer = find_customer(id)
```

## Anti-Patterns
<!-- Lines 169-206 -->

Names to avoid and why.

**Meaningless Names:**
```python
# Avoid
data, info, result, value, item, obj, temp, foo, bar

# Better: Be specific
user_data, config_info, validation_result, price_value
```

**Hungarian Notation (Avoid):**
```python
# Avoid encoding type in name
strName = "Alice"    # Type hints exist
lstUsers = []        # Let the type system help
dictConfig = {}

# Better
name = "Alice"
users: list[User] = []
config: dict[str, Any] = {}
```

**Misleading Names:**
```python
# Avoid: Name suggests one thing, does another
def get_user(id):      # Actually creates if not exists
    ...

# Better: Accurate name
def get_or_create_user(id):
    ...
```
