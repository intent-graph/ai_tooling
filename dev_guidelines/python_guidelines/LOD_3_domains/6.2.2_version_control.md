## Core Concept
<!-- Lines 31-53 -->

**Definition:** Version control tracks changes to code over time, enabling collaboration, reversal of mistakes, and understanding of history.

**Key Principles:**
- Commits are the atoms of change
- Each commit should be one logical unit
- History should tell a story
- Never lose work (commit early, commit often)

**Git Mental Model:**
```
Working Directory → Staging Area → Local Repo → Remote Repo
       |                |              |              |
     (edit)         (git add)    (git commit)   (git push)
```

## Commit Practices
<!-- Lines 56-56 -->

### Atomic Commits
<!-- Lines 59-69 -->

```bash
# Good: One logical change per commit
git commit -m "feat: add user registration endpoint"
git commit -m "test: add tests for registration"
git commit -m "docs: document registration API"

# Bad: Multiple unrelated changes
git commit -m "add registration, fix bug, update readme"
```

### Commit Message Format
<!-- Lines 72-104 -->

```
<type>(<scope>): <subject>

<body>

<footer>
```

**Types:**
- `feat`: New feature
- `fix`: Bug fix
- `docs`: Documentation
- `style`: Formatting (no code change)
- `refactor`: Code restructuring
- `test`: Adding/modifying tests
- `chore`: Maintenance tasks

**Examples:**

```bash
# Simple
git commit -m "fix: handle empty user list in dashboard"

# With body
git commit -m "feat(auth): add OAuth2 support

Implements Google and GitHub OAuth providers.
Tokens are stored encrypted in the database.

Closes #123"
```

### Staging Strategically
<!-- Lines 107-118 -->

```bash
# Stage specific files
git add src/auth.py tests/test_auth.py

# Stage specific hunks
git add -p  # Interactive staging

# Review before committing
git diff --staged
```

### Commit Frequency
<!-- Lines 121-135 -->

```bash
# Commit at logical checkpoints
# ✅ After completing a function
# ✅ After tests pass
# ✅ Before taking a break
# ✅ Before risky changes

# Not too granular
# ❌ Every saved file
# ❌ Every line change
```

## Branching Strategies
<!-- Lines 138-138 -->

### Trunk-Based Development
<!-- Lines 141-155 -->

```
main ────●────●────●────●────●────●────●
              │              │
              └──feature──┘  (short-lived)
```

```bash
# Short-lived feature branches
git checkout -b feature/user-auth
# Work for 1-2 days max
git push -u origin feature/user-auth
# Create PR, merge, delete branch
```

### GitHub Flow
<!-- Lines 158-184 -->

```
main ────●────●────●────●────●────●
              │         ↑
              └─feature─┘
              (PR + review)
```

```bash
# 1. Branch from main
git checkout main
git pull
git checkout -b feature/add-search

# 2. Work and commit
git add .
git commit -m "feat: add search functionality"

# 3. Push and create PR
git push -u origin feature/add-search
# Open PR on GitHub

# 4. After review, merge via PR
# 5. Delete feature branch
git branch -d feature/add-search
```

## Git Workflows
<!-- Lines 216-216 -->

### Daily Workflow
<!-- Lines 219-231 -->

```bash
# Start of day
git fetch origin
git status

# On feature branch
git rebase origin/main  # Stay current

# End of day
git push  # Save work to remote
```

### Interactive Rebase (Clean History)
<!-- Lines 249-261 -->

```bash
# Before creating PR, clean up commits
git rebase -i HEAD~3

# In editor:
pick abc123 feat: add search
squash def456 fix typo
squash ghi789 more fixes

# Result: One clean commit
```

### Undoing Changes
<!-- Lines 264-278 -->

```bash
# Undo last commit (keep changes)
git reset --soft HEAD~1

# Undo staged changes
git restore --staged file.py

# Undo working directory changes
git restore file.py

# Revert a pushed commit
git revert <commit-hash>
```

### Useful Aliases
<!-- Lines 281-293 -->

```bash
# In ~/.gitconfig
[alias]
    st = status
    co = checkout
    br = branch
    ci = commit
    lg = log --oneline --graph --all
    undo = reset --soft HEAD~1
    amend = commit --amend --no-edit
```

### Protected Branches
<!-- Lines 296-309 -->

```yaml
# .github/settings.yml (or via GitHub UI)
branches:
  - name: main
    protection:
      required_pull_request_reviews:
        required_approving_review_count: 1
      required_status_checks:
        strict: true
        contexts:
          - tests
          - lint
```
