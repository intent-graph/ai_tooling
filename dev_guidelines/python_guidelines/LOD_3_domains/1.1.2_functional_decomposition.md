## Core Concept
<!-- Lines 30-57 -->

**Definition:** Functional decomposition breaks a system's mission into a hierarchy of capabilities, from abstract goals down to atomic operations.

**Key Points:**
- Top-down only: Start with the goal, decompose downward
- Verb-oriented: Capabilities are actions, not things
- User-centric: Frame in terms of user outcomes
- Testable leaves: Each atomic operation can be tested independently

**The Hierarchy:**
```
Level 0: System Goal (Mission)
    └── Level 1: Core Capabilities (Features)
            └── Level 2: Atomic Operations (Functions)
```

**Why It Matters:**
- Guides module boundaries in architecture
- Defines scope clearly
- Enables prioritization
- Creates natural test targets

## When to Use
<!-- Lines 60-80 -->

**Use When:**
- Defining what a new system does
- Scoping features for a release
- Communicating with stakeholders
- Planning module structure
- Estimating work

**Avoid When:**
- Requirements are already at operation level
- Making minor enhancements
- The system is trivially simple

**Signs of Poor Decomposition:**
- Capabilities overlap significantly
- Operations span multiple capabilities
- Can't explain the hierarchy to non-technical stakeholders
- Implementation doesn't map to capabilities

## The Capability Tree
<!-- Lines 83-83 -->

### Level 0: System Goal
<!-- Lines 86-97 -->

The mission statement—what the system exists to do:

```
"Enable users to manage their personal tasks efficiently"
```

**Characteristics:**
- Single sentence
- User-outcome focused
- Not technical

### Level 1: Core Capabilities
<!-- Lines 100-118 -->

Major features that together fulfill the mission:

```
Level 0: Users manage personal tasks
    │
    ├── 1.1 Create and edit tasks
    ├── 1.2 Organize tasks into projects
    ├── 1.3 Track task status
    ├── 1.4 Set and manage due dates
    └── 1.5 Search and filter tasks
```

**Characteristics:**
- 3-7 capabilities typical
- Each delivers standalone value
- Can be prioritized independently
- Maps to potential modules

### Level 2: Atomic Operations
<!-- Lines 121-149 -->

Indivisible actions that implement capabilities:

```
1.1 Create and edit tasks
    │
    ├── 1.1.1 create_task(title, description)
    ├── 1.1.2 update_task(task_id, changes)
    ├── 1.1.3 delete_task(task_id)
    └── 1.1.4 duplicate_task(task_id)

1.2 Organize tasks into projects
    │
    ├── 1.2.1 create_project(name)
    ├── 1.2.2 assign_task_to_project(task_id, project_id)
    ├── 1.2.3 remove_task_from_project(task_id)
    └── 1.2.4 list_project_tasks(project_id)
```

**Characteristics:**
- Function-like signatures
- Single responsibility
- Directly testable
- Clear inputs and outputs

## Decomposition Process
<!-- Lines 152-152 -->

### Step 1: Define the Mission
<!-- Lines 155-167 -->

Ask: "Why does this system exist?"

**Template:**
```
"Enable [users] to [accomplish goal] [in some context]"
```

**Examples:**
- "Enable developers to track code quality metrics"
- "Enable customers to purchase products online"
- "Enable teams to collaborate on documents"

### Step 2: Identify Core Capabilities
<!-- Lines 170-178 -->

Ask: "What major things can users do?"

**Technique:** Verb extraction from requirements
```
Requirements say: "Users create tasks, organize them, track progress..."
Capabilities: Create, Organize, Track → become Level 1 items
```

### Step 3: Decompose to Operations
<!-- Lines 181-190 -->

For each capability, ask: "What specific actions support this?"

**CRUD Baseline:**
Most capabilities include some combination of:
- **C**reate: Add new items
- **R**ead: View/search items
- **U**pdate: Modify items
- **D**elete: Remove items

### Step 4: Validate the Tree
<!-- Lines 193-199 -->

Check for:
- **Completeness:** Does the tree cover all requirements?
- **Coherence:** Do operations fit their capabilities?
- **Independence:** Can capabilities be built/tested separately?
- **Clarity:** Can stakeholders understand it?

### Step 5: Iterate
<!-- Lines 202-212 -->

Decomposition is not one-and-done:
- Refine as understanding grows
- Merge overlapping capabilities
- Split capabilities that are too large
- Adjust based on implementation learnings

**Cross-ref:** → [1.1.2.2 Flow Mapping](../LOD_4_practices/1.1.2.2_flow_mapping.md)

## Examples
<!-- Lines 215-215 -->

### Example: E-Commerce System
<!-- Lines 218-245 -->

```
Level 0: Customers purchase products online

Level 1: Core Capabilities
├── 1.1 Browse product catalog
├── 1.2 Manage shopping cart
├── 1.3 Complete checkout
├── 1.4 Track orders
└── 1.5 Manage account

Level 2: Operations (partial)
1.2 Manage shopping cart
    ├── add_to_cart(product_id, quantity)
    ├── remove_from_cart(product_id)
    ├── update_quantity(product_id, quantity)
    ├── view_cart()
    └── calculate_totals()

1.3 Complete checkout
    ├── enter_shipping_address()
    ├── select_shipping_method()
    ├── enter_payment_info()
    ├── apply_coupon(code)
    ├── review_order()
    └── place_order()
```

### Example: CLI Tool
<!-- Lines 248-271 -->

```
Level 0: Developers analyze code quality

Level 1: Core Capabilities
├── 1.1 Scan codebase
├── 1.2 Report findings
├── 1.3 Configure rules
└── 1.4 Integrate with CI

Level 2: Operations (partial)
1.1 Scan codebase
    ├── scan_directory(path)
    ├── scan_file(path)
    ├── exclude_patterns(patterns)
    └── scan_incremental(since_commit)

1.2 Report findings
    ├── output_text()
    ├── output_json()
    ├── output_sarif()
    └── filter_by_severity(level)
```

### Anti-Pattern: Implementation-Driven
<!-- Lines 274-286 -->

**Wrong:**
```
Level 1:
├── Database operations
├── API endpoints
├── Background jobs
```

This describes *how*, not *what*. Capabilities should be user-visible features.
