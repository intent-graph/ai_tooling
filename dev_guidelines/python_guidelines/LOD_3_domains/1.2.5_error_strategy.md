## Core Concept
<!-- Lines 30-59 -->

**Definition:** Error strategy defines how your system handles failures—what exceptions exist, how they propagate, and how they're communicated to different audiences.

**Key Points:**
- Design errors as deliberately as features
- Errors are part of the interface contract
- Different audiences need different error information
- Fail-fast reveals problems early

**Error Handling Philosophy:**
```
Detect → Decide → Act → Communicate
   │        │       │         │
 Early    Handle   Recover   Inform
          or         or       right
         Raise     Fail     audience
```

**Why Strategy Matters:**
- Unplanned error handling is inconsistent
- Poor errors waste debugging time
- Good errors guide users to solutions
- Strategy prevents error handling debt

## When to Use
<!-- Lines 62-83 -->

**Design Error Strategy When:**
- Starting a new project
- Defining module boundaries
- Creating public APIs
- Integrating external services
- Adding new failure modes

**Strategy Before Code:**
- Define exception hierarchy early
- Document expected errors in interfaces
- Plan error propagation across layers
- Design error messages for audiences

**Signs of Missing Strategy:**
- Bare `except:` clauses everywhere
- Inconsistent error messages
- Users see stack traces
- Same error handled differently in different places

## Exception Hierarchy
<!-- Lines 86-86 -->

### Domain Exception Base
<!-- Lines 89-101 -->

Create a base exception for your domain:

```python
class TaskError(Exception):
    """Base exception for task domain."""

    def __init__(self, message: str, details: dict | None = None):
        super().__init__(message)
        self.message = message
        self.details = details or {}
```

### Specific Exceptions
<!-- Lines 104-140 -->

Branch for specific failure modes:

```python
class TaskNotFoundError(TaskError):
    """Raised when task doesn't exist."""

    def __init__(self, task_id: UUID):
        super().__init__(
            f"Task not found: {task_id}",
            details={"task_id": str(task_id)}
        )
        self.task_id = task_id

class TaskValidationError(TaskError):
    """Raised when task data is invalid."""

    def __init__(self, field: str, reason: str):
        super().__init__(
            f"Invalid task: {field} - {reason}",
            details={"field": field, "reason": reason}
        )

class TaskPermissionError(TaskError):
    """Raised when user lacks permission."""

    def __init__(self, user_id: UUID, task_id: UUID, action: str):
        super().__init__(
            f"User {user_id} cannot {action} task {task_id}",
            details={
                "user_id": str(user_id),
                "task_id": str(task_id),
                "action": action
            }
        )
```

### Hierarchy Design
<!-- Lines 143-152 -->

```
Exception (built-in)
└── TaskError (domain base)
    ├── TaskNotFoundError (missing resource)
    ├── TaskValidationError (invalid data)
    ├── TaskPermissionError (access denied)
    └── TaskStateError (invalid state transition)
```

### When to Create New Exceptions
<!-- Lines 155-169 -->

Create a new exception when:
- Different handling is required
- Different information is needed
- Users need to catch it specifically

Don't create when:
- Built-in exception suffices (ValueError, TypeError)
- Only message differs
- You're just wrapping another exception

## Error Propagation
<!-- Lines 172-172 -->

### Layer Responsibilities
<!-- Lines 175-182 -->

| Layer | Strategy |
|-------|----------|
| Domain | Raise domain exceptions |
| Application | Catch, log, transform or re-raise |
| Presentation | Catch all, convert to response |
| Infrastructure | Wrap external errors |

### Propagation Patterns
<!-- Lines 185-217 -->

**Let it bubble:**
```python
def get_task(self, task_id: UUID) -> Task:
    task = self.repo.get(task_id)
    if not task:
        raise TaskNotFoundError(task_id)  # Let caller handle
    return task
```

**Catch and transform:**
```python
def create_task(self, data: dict) -> Task:
    try:
        task = Task.from_dict(data)
    except KeyError as e:
        raise TaskValidationError(str(e), "missing field") from e
```

**Catch and log:**
```python
def process_tasks(self, task_ids: list[UUID]) -> list[Task]:
    results = []
    for task_id in task_ids:
        try:
            task = self.process_one(task_id)
            results.append(task)
        except TaskError as e:
            logger.warning("Failed to process task", task_id=task_id, error=str(e))
            # Continue with others
    return results
```

### Fail-Fast vs Resilient
<!-- Lines 220-245 -->

**Fail-fast (default):**
```python
# Stop on first error
for item in items:
    process(item)  # Exception stops everything
```

**Resilient:**
```python
# Collect errors, continue processing
errors = []
for item in items:
    try:
        process(item)
    except ProcessError as e:
        errors.append(e)

if errors:
    raise BatchProcessError(errors)
```

## Error Communication
<!-- Lines 248-248 -->

### Audience-Specific Messages
<!-- Lines 251-281 -->

**For developers (logs):**
```python
logger.error(
    "Database query failed",
    query=query,
    params=params,
    error=str(e),
    traceback=traceback.format_exc()
)
```

**For API consumers:**
```json
{
    "error": {
        "code": "TASK_NOT_FOUND",
        "message": "Task not found",
        "details": {
            "task_id": "123e4567-..."
        }
    }
}
```

**For end users:**
```
"The task you're looking for doesn't exist.
It may have been deleted."
```

### Error Response Format
<!-- Lines 284-303 -->

Standardize API error responses:

```python
@dataclass
class ErrorResponse:
    code: str           # Machine-readable: TASK_NOT_FOUND
    message: str        # Human-readable: "Task not found"
    details: dict       # Additional context
    request_id: str     # For support correlation

def exception_to_response(e: TaskError, request_id: str) -> ErrorResponse:
    return ErrorResponse(
        code=e.__class__.__name__.upper(),
        message=e.message,
        details=e.details,
        request_id=request_id
    )
```

### Error Message Guidelines
<!-- Lines 319-333 -->

**Do:**
- Be specific about what went wrong
- Suggest how to fix it
- Include relevant identifiers
- Use consistent terminology

**Don't:**
- Expose internal details (stack traces, SQL)
- Blame the user
- Use technical jargon for end users
- Include sensitive data
