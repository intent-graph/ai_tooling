## What is an ADR?
<!-- Lines 26-31 -->

A short document that captures:
- The context of a decision
- The decision itself
- The consequences

## When to Write an ADR
<!-- Lines 34-40 -->

- Choosing a database or framework
- Defining API patterns
- Establishing coding conventions
- Selecting deployment strategy
- Any decision that's hard to reverse

## Example ADR
<!-- Lines 83-129 -->

```markdown
# ADR-001: Use PostgreSQL as Primary Database

## Status
<!-- Lines 107-108 -->
Accepted

## Date
<!-- Lines 111-112 -->
2024-01-15

## Context
<!-- Lines 115-121 -->
We need to choose a database for our new order management
system. Requirements:
- ACID compliance for financial transactions
- Support for complex queries with joins
- Team has prior experience with relational DBs
- Expected data volume: ~10M orders/year

## Decision
<!-- Lines 124-125 -->
We will use PostgreSQL 15+ as our primary database.

## Consequences
<!-- Lines 128-128 -->

### Positive
<!-- Lines 131-135 -->
- Strong ACID guarantees for order integrity
- Rich query capabilities for reporting
- Excellent Python support (asyncpg, SQLAlchemy)
- Team familiarity reduces onboarding time

### Negative
<!-- Lines 138-141 -->
- Schema migrations required for model changes
- Horizontal scaling requires more planning
- Need to manage connection pooling

### Neutral
<!-- Lines 144-147 -->
- Will use Alembic for migrations
- Will implement read replicas if needed
```

## Superseding an ADR
<!-- Lines 157-179 -->

```markdown
# ADR-005: Return to REST API

## Status
<!-- Lines 181-182 -->
Accepted (supersedes ADR-003)

## Context
<!-- Lines 185-190 -->
ADR-003 adopted GraphQL for client flexibility.
After 6 months, we've encountered:
- Caching complexity
- N+1 query issues
- Team expertise gaps

## Decision
<!-- Lines 193-197 -->
We will migrate back to REST for new endpoints.
Existing GraphQL endpoints will be maintained
but deprecated over 2 releases.
```
