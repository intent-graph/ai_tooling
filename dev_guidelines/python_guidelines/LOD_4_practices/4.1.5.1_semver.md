> Communicating change impact through MAJOR.MINOR.PATCH.

## Version Meaning
<!-- Lines 20-27 -->

```
MAJOR.MINOR.PATCH
  │     │     └── Bug fixes (backward compatible)
  │     └──────── New features (backward compatible)
  └────────────── Breaking changes
```

## Examples
<!-- Lines 30-38 -->

```
1.0.0  → First stable release
1.0.1  → Bug fix
1.1.0  → New feature added
1.1.1  → Bug fix to new feature
2.0.0  → Breaking API change
```

## Pre-release Versions
<!-- Lines 41-47 -->

```
1.0.0-alpha.1  → Alpha release
1.0.0-beta.1   → Beta release
1.0.0-rc.1     → Release candidate
```

## 0.x Development
<!-- Lines 50-59 -->

```
0.1.0  → Initial development
0.2.0  → Breaking changes allowed
0.9.0  → Approaching stability
1.0.0  → First stable release
```

During 0.x, breaking changes can occur in MINOR bumps.

## What Counts as Breaking
<!-- Lines 62-68 -->

- Removing public API
- Changing function signatures
- Changing return types
- Changing default behavior
- Raising new exceptions

## Not Breaking
<!-- Lines 71-77 -->

- Adding new functions
- Adding optional parameters
- Bug fixes
- Performance improvements
- Documentation changes
