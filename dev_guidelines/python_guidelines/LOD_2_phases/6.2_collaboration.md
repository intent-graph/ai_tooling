## Overview
<!-- Lines 18-37 -->

Software development is a team sport, even when you work alone. Your future self is a collaborator who will read your code months later with no memory of today's context. External contributors may extend your work in ways you never anticipated. Effective collaboration practices make this shared ownership sustainable.

Collaboration has three pillars: code review, version control, and team conventions. Code review is the mechanism for knowledge transfer and quality assurance. Version control is the shared memory of how code evolved. Team conventions are the agreements that reduce friction and cognitive load.

These practices serve a deeper purpose than coordination—they create a shared understanding of the codebase. When everyone reviews code, everyone learns the system. When commits tell a story, newcomers can understand history. When conventions are explicit, debates become discussions about principles rather than preferences.

**The Collaboration Mindset:**
- Write code for readers, not just computers
- Treat review as teaching, not gatekeeping
- Make history navigable, not just accurate
- Prefer explicit conventions over implicit assumptions

## 6.2.1 Code Review
<!-- Lines 40-64 -->

Code review is the practice of having others examine code before it merges. It serves multiple purposes: catching bugs, ensuring consistency, sharing knowledge, and maintaining quality standards. The best reviews improve both the code and the people involved.

Effective review requires the right mindset from both sides. Authors should view feedback as a gift—another perspective that improves their work. Reviewers should be specific, kind, and focused on the code rather than the person. Both should remember that text lacks tone; assume good intent.

The scope of review matters. Small, focused changes are easier to review thoroughly. Large changes overwhelm reviewers and hide issues. If a change is too big to review in one sitting, it should probably be split into smaller pieces.

**What to Look For:**
- Correctness: Does it do what it should?
- Clarity: Can you understand it without the PR description?
- Consistency: Does it follow established patterns?
- Coverage: Are there tests for the changes?
- Completeness: Are edge cases handled?

**Giving Good Feedback:**
- Be specific: "This variable name is unclear" → "Consider renaming `d` to `user_data`"
- Explain why: Not just what to change, but why it matters
- Distinguish severity: Blocking issues vs. suggestions vs. nitpicks
- Offer alternatives: Don't just criticize; propose solutions

## 6.2.2 Version Control
<!-- Lines 67-102 -->

Version control is the practice of tracking changes to code over time. Git dominates modern development, but the principles matter more than the tool: preserve history, enable collaboration, and allow reversal of mistakes.

Commits are the atoms of version control. Each commit should be a logical unit—one idea, one change. Commits that mix refactoring with features, or fix multiple bugs at once, make history hard to navigate. When something breaks, you want to revert one commit, not untangle a mess.

Branching strategies organize parallel work. The right strategy depends on team size, release cadence, and deployment model. Small teams might work on main with feature flags. Larger teams might use feature branches with pull requests. The key is consistency—everyone should follow the same workflow.

**Commit Message Structure:**
```
type(scope): short description

Longer explanation if needed. Why this change was made,
what trade-offs were considered, what alternatives were rejected.

Refs: #123
```

**Common Types:**
- `feat`: New feature
- `fix`: Bug fix
- `refactor`: Code restructuring
- `docs`: Documentation
- `test`: Test changes
- `chore`: Maintenance

**Branching Principles:**
- Keep branches short-lived (days, not weeks)
- Merge frequently to avoid drift
- Delete branches after merging
- Protect main with required reviews

## 6.2.3 Team Conventions
<!-- Lines 105-145 -->

Team conventions are explicit agreements about how to write and organize code. They reduce cognitive load by eliminating recurring decisions and debates. When conventions are clear, developers can focus on solving problems rather than arguing about formatting.

Good conventions balance consistency with flexibility. They should cover the decisions that cause friction (naming, formatting, file organization) while leaving room for judgment on novel situations. Overly rigid conventions create bureaucracy; overly loose conventions create chaos.

Documentation is essential. Conventions that exist only in tribal knowledge are conventions that new team members violate. Write them down, review them periodically, and enforce them with tooling where possible. Automated formatters and linters are conventions that enforce themselves.

**What to Standardize:**
- Code formatting (enforce with tooling)
- Naming conventions (document in style guide)
- File and directory structure (document in README)
- Git workflow (document in CONTRIBUTING.md)
- Review process (document in CONTRIBUTING.md)

**Architecture Decision Records (ADRs):**
ADRs document significant technical decisions. They capture not just what was decided, but why—the context, options considered, and trade-offs accepted. This history prevents re-litigating settled decisions and helps newcomers understand the codebase's evolution.
