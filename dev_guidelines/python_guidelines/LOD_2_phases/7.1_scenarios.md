## Overview
<!-- Lines 22-50 -->

Different application types have different concerns. A CLI tool prioritizes user experience at the command line. A library prioritizes API stability and backward compatibility. A data pipeline prioritizes correctness and observability. This section provides specialized guidance that builds on the general principles.

The patterns in earlier stages apply universally—naming, testing, security, and documentation matter for all Python code. This section adds type-specific considerations: which frameworks to choose, which patterns to emphasize, which pitfalls to avoid.

Each scenario section follows a consistent structure:
- **When to use:** Conditions that make this type appropriate
- **Key concerns:** What matters most for this type
- **Framework choices:** Popular tools and when to use each
- **Patterns:** Type-specific design patterns
- **Anti-patterns:** Common mistakes in this domain

**Scenario Selection Guide:**

| Scenario | Best For | Key Priority |
|----------|----------|--------------|
| CLI | Developer tools, automation | UX, discoverability |
| Web | User-facing apps | Scalability, security |
| Data Pipeline | ETL, batch processing | Reliability, monitoring |
| Library | Reusable code | API stability, docs |
| API | Service interfaces | Consistency, versioning |
| Scientific | Research, analysis | Reproducibility, correctness |
| Scripts | One-off automation | Simplicity, maintenance |

## 7.1.1 CLI Applications
<!-- Lines 53-77 -->

Command-line interfaces are the backbone of developer tooling. A good CLI feels intuitive, provides helpful error messages, and respects Unix conventions.

**Key Concerns:**
- Argument parsing and validation
- Help text and discoverability
- Exit codes and error handling
- Progress feedback for long operations
- Configuration file support

**Framework Choices:**
- **Click:** Decorator-based, composable, good for complex CLIs
- **Typer:** Type-hint-based, modern, auto-generated help
- **argparse:** Standard library, no dependencies, basic needs

**When to Use Each:**
- Simple script with few options → `argparse`
- Tool with subcommands → Click or Typer
- Type-safety priority → Typer

## 7.1.2 Web Applications
<!-- Lines 80-105 -->

Web applications serve HTML pages to browsers. They handle routing, templating, sessions, and often connect to databases and external services.

**Key Concerns:**
- Request handling and routing
- Template rendering
- Session management
- Database integration
- Authentication/authorization
- Static files and assets

**Framework Choices:**
- **Django:** Batteries-included, admin, ORM, best for traditional web apps
- **Flask:** Minimal, flexible, good for smaller apps
- **FastAPI:** Modern, async, best for API-first with some HTML

**When to Use Each:**
- Full web app with admin → Django
- Simple app, maximum control → Flask
- API-first with some pages → FastAPI

## 7.1.3 Data Pipelines
<!-- Lines 108-134 -->

Data pipelines transform data from sources to destinations. They must be reliable, observable, and often handle large volumes.

**Key Concerns:**
- Data validation and quality
- Error handling and retries
- Idempotency
- Monitoring and alerting
- Backfill capabilities
- Schema evolution

**Framework Choices:**
- **Prefect/Dagster:** Modern workflow orchestration
- **Apache Airflow:** Mature, widely adopted
- **dbt:** SQL transformation focus
- **Luigi:** Simple dependency management

**When to Use Each:**
- SQL transformations → dbt
- Complex workflows, dynamic → Prefect/Dagster
- Enterprise, established patterns → Airflow

## 7.1.4 Libraries
<!-- Lines 137-167 -->

Libraries are code designed for reuse by other developers. They have stricter requirements for stability, documentation, and backward compatibility than applications.

**Key Concerns:**
- API design and stability
- Backward compatibility
- Minimal dependencies
- Comprehensive documentation
- Type hints for users
- Version strategy

**Design Principles:**
- Fewer dependencies are better
- Make the common case easy
- Don't surprise users
- Deprecate before removing
- Document everything public

**What Makes a Good Library:**
- Clear, focused purpose
- Intuitive API
- Excellent error messages
- Comprehensive test coverage
- Type-annotated public API

## 7.1.5 APIs
<!-- Lines 170-198 -->

APIs expose functionality over a network. They must be consistent, well-documented, and handle versioning gracefully.

**Key Concerns:**
- Consistent request/response formats
- Authentication and authorization
- Rate limiting
- Error handling
- Versioning strategy
- Documentation (OpenAPI/Swagger)

**Framework Choices:**
- **FastAPI:** Modern, async, auto-docs, best for new APIs
- **Django REST Framework:** When using Django
- **Flask-RESTX:** Flask with API tooling
- **Falcon:** Minimal, fast, bare-metal control

**Design Principles:**
- Use nouns for resources, verbs for actions
- Consistent naming (plural vs singular)
- Proper HTTP status codes
- Pagination for collections
- HATEOAS when appropriate

## 7.1.6 Scientific Computing
<!-- Lines 201-230 -->

Scientific computing emphasizes correctness, reproducibility, and often exploratory analysis. Notebooks are common but require discipline.

**Key Concerns:**
- Numerical correctness
- Reproducibility
- Performance for large data
- Visualization
- Notebook hygiene
- Experiment tracking

**Core Libraries:**
- **NumPy:** Foundation for numerical computing
- **pandas:** Data manipulation and analysis
- **SciPy:** Scientific algorithms
- **matplotlib/seaborn:** Visualization
- **scikit-learn:** Machine learning

**Notebook Best Practices:**
- Restart and run all before committing
- Extract reusable code to modules
- Pin environment versions
- Use nbstripout for clean diffs
- Document assumptions

## 7.1.7 Automation Scripts
<!-- Lines 233-258 -->

Scripts automate tasks—deployment, data migration, system administration. They're often written quickly but may run for years.

**Key Concerns:**
- Robustness (handle failures gracefully)
- Logging (what happened, when)
- Idempotency (safe to re-run)
- Configuration (don't hardcode paths)
- Documentation (what does this do?)

**Script Hygiene:**
- Use `if __name__ == "__main__":`
- Accept arguments, don't hardcode
- Log to stdout/stderr or file
- Return meaningful exit codes
- Handle Ctrl+C gracefully

**When Scripts Become Applications:**
Signs you need more structure:
- Multiple scripts share code
- Configuration becomes complex
- Others need to run your scripts
- Scripts grow beyond ~200 lines
