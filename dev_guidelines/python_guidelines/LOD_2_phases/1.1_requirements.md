## Phase Overview
<!-- Lines 43-45 -->

Requirements analysis transforms **vague ideas into precise specifications**. This phase ensures you understand what to build before deciding how to build it. Skip this phase, and you risk building the wrong thing well.

### Why Requirements Matter
<!-- Lines 48-50 -->

Every downstream decision—architecture, data model, implementation—depends on understanding what you're building. Ambiguous requirements propagate ambiguity. Clear requirements enable clear design.

### What This Phase Produces
<!-- Lines 53-67 -->

By the end of this phase, you should have:
- A clear problem statement
- A capability hierarchy (what the system does)
- Defined scope (what's in, what's out)
- Measurable success criteria
- Documented constraints and assumptions

## 1.1.1 Requirements Gathering
<!-- Lines 70-72 -->

Requirements gathering is **discovering what stakeholders actually need**, not just what they say they want.

### Types of Requirements
<!-- Lines 75-90 -->

**Functional requirements** describe what the system does:
- "Users can create tasks"
- "The system exports data to CSV"
- "Admins can view all user activity"

**Non-functional requirements** describe how the system behaves:
- Performance: "Page loads in < 2 seconds"
- Security: "All data encrypted at rest"
- Reliability: "99.9% uptime"

**Constraints** are fixed boundaries:
- "Must use existing PostgreSQL database"
- "Budget is $50,000"
- "Must launch by Q3"

### Gathering Techniques
<!-- Lines 93-106 -->

**Stakeholder interviews:** Talk to people who will use or be affected by the system. Ask open questions:
- "What problem does this solve?"
- "What do you do today without this system?"
- "What would success look like?"

**Document analysis:** Review existing documentation, processes, and systems.

**Observation:** Watch how users currently work. They often can't articulate implicit knowledge.

## 1.1.2 Functional Decomposition
<!-- Lines 109-111 -->

Functional decomposition breaks the **system goal into a hierarchy of capabilities**.

### The Capability Tree
<!-- Lines 114-135 -->

Start with the mission (what the system is for), then decompose:

```
Level 0: System Goal
    "Users manage their personal task lists"

Level 1: Core Capabilities
    ├── Create and edit tasks
    ├── Organize tasks into projects
    ├── Track completion status
    └── Search and filter tasks

Level 2: Atomic Operations
    ├── create_task(title, description)
    ├── update_task(task_id, changes)
    ├── delete_task(task_id)
    ├── assign_to_project(task_id, project_id)
    ├── mark_complete(task_id)
    └── search_tasks(query, filters)
```

### Why Decomposition Matters
<!-- Lines 138-144 -->

The capability tree:
- **Guides architecture:** Each Level 1 capability might become a module
- **Defines scope:** Level 2 operations are the atomic units to implement
- **Enables prioritization:** Which capabilities are essential vs. nice-to-have?
- **Supports testing:** Each operation becomes a test target

### Decomposition Guidelines
<!-- Lines 147-156 -->

- **Top-down only:** Start at the goal, work down. Never start with implementation.
- **Verb-oriented:** Capabilities are actions. Use verbs: "create," "search," "notify."
- **User-centric:** Frame in terms of what users accomplish, not system internals.
- **Testable:** Each leaf should be independently verifiable.

## 1.1.3 Scope Definition
<!-- Lines 159-161 -->

Scope definition draws a **clear boundary** around what will and won't be built.

### The Scope Document
<!-- Lines 164-188 -->

Every project needs explicit scope boundaries:

```markdown
## In Scope
<!-- Lines 177-181 -->
- Single-user task management
- Basic project organization
- Due date tracking
- Web interface

## Out of Scope (this version)
<!-- Lines 184-188 -->
- Multi-user collaboration
- Mobile applications
- Calendar integration
- Recurring tasks

## Deferred (future consideration)
<!-- Lines 191-195 -->
- File attachments (v2)
- Tags and filters (v2)
- API access (v2)
```

### Why Scope Matters
<!-- Lines 191-197 -->

**Prevents scope creep:** When someone asks "can we also add X?", you can point to the scope document.

**Manages expectations:** Stakeholders know what they're getting and what they're not.

**Enables focus:** The team knows exactly what to build.

### MVP Definition
<!-- Lines 200-210 -->

The Minimum Viable Product (MVP) is the smallest set of capabilities that delivers value:

- Must solve the core problem
- Must be usable (not just functional)
- Must be small enough to ship quickly

## 1.1.4 Success Criteria
<!-- Lines 213-215 -->

Success criteria define **how you'll know the project succeeded**.

### Writing Good Criteria
<!-- Lines 218-241 -->

Criteria must be **measurable and verifiable**:

```markdown
## Success Criteria
<!-- Lines 231-231 -->

### Functional
<!-- Lines 234-237 -->
1. Users can create a task in < 3 clicks
2. Tasks persist across browser sessions
3. Search returns results in < 1 second

### Performance
<!-- Lines 240-242 -->
4. Page load time < 2 seconds on 3G
5. System handles 100 concurrent users

### Business
<!-- Lines 245-248 -->
6. 50% of beta users return after first week
7. Average task completion rate > 70%
```

### From Criteria to Tests
<!-- Lines 244-252 -->

Success criteria become acceptance tests:

| Criterion | Test |
|-----------|------|
| "Create task in < 3 clicks" | UI test: measure clicks from landing to created task |
| "Page load < 2 seconds" | Performance test: measure First Contentful Paint |
| "100 concurrent users" | Load test: simulate 100 users, verify response times |

### Prioritizing Criteria
<!-- Lines 255-264 -->

Not all criteria are equal:
- **Must have:** Project fails without these
- **Should have:** Expected, but project survives without
- **Nice to have:** Bonuses if achieved

**Cross-ref:** → [1.1.4 Success Criteria](../LOD_3_domains/1.1.4_success_criteria.md) for measurement strategies

## 1.1.5 Constraints & Assumptions
<!-- Lines 267-269 -->

Constraints and assumptions are the **hidden factors** that shape decisions.

### Constraints
<!-- Lines 272-289 -->

Constraints are **fixed boundaries** you cannot change:

**Technical constraints:**
- "Must integrate with legacy Oracle database"
- "Must run on Python 3.9+ (corporate standard)"
- "Must deploy to AWS (existing infrastructure)"

**Business constraints:**
- "Budget: $100,000"
- "Timeline: 6 months"
- "Team: 3 developers"

**Regulatory constraints:**
- "Must comply with GDPR"
- "Must pass SOC 2 audit"
- "Must support accessibility (WCAG 2.1)"

### Assumptions
<!-- Lines 292-304 -->

Assumptions are **things you believe to be true** but haven't verified:

```markdown
## Assumptions
<!-- Lines 305-311 -->

1. Users have modern browsers (Chrome, Firefox, Safari latest)
2. Users have reliable internet connectivity
3. Peak usage will be during business hours (9-5 EST)
4. The legacy API will remain stable during development
```

### Managing Assumptions
<!-- Lines 307-318 -->

Every assumption is a risk. For each assumption:
- **Document it:** Make it explicit
- **Validate it:** Can you verify it's true?
- **Plan for failure:** What if it's wrong?

Assumptions that prove false mid-project cause the most painful rework.
