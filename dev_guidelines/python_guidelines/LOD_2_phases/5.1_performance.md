## Overview
<!-- Lines 23-42 -->

Performance optimization follows a fundamental principle: **measure first, optimize second**. Premature optimization—improving code without evidence it's slow—wastes developer time and often makes code harder to maintain without meaningful benefit.

The performance workflow is systematic:
1. **Establish baselines**: How fast is it now?
2. **Identify bottlenecks**: Where is time actually spent?
3. **Optimize the critical path**: Focus on the 20% causing 80% of slowness
4. **Verify improvements**: Did changes actually help?

Python's performance characteristics differ from compiled languages. The GIL (Global Interpreter Lock) affects threading. Dynamic typing adds overhead. But Python's extensive C libraries (NumPy, pandas) and ability to call native code mean raw Python speed rarely matters—what matters is using the right tool for each task.

This section covers the full performance spectrum: profiling to find bottlenecks, optimization techniques, concurrency for I/O-bound work, parallelism for CPU-bound work, async programming for high-concurrency scenarios, and scaling patterns for growing beyond single machines.

## 5.1.1 Performance Mindset
<!-- Lines 45-68 -->

"Premature optimization is the root of all evil" —Donald Knuth

This doesn't mean ignore performance—it means optimize based on evidence, not intuition. Developers are notoriously bad at guessing where time is spent.

**Amdahl's Law**: The maximum speedup from optimizing one part of a system is limited by how much time is spent in that part. If a function takes 5% of total runtime, making it infinitely fast yields only 5% improvement.

**Performance Budget**: Define acceptable performance upfront. "API responses under 200ms" is testable; "make it fast" is not.

**When to Optimize:**
- Measured performance doesn't meet requirements
- Profiling shows a clear bottleneck
- The code is stable (not changing rapidly)

**When NOT to Optimize:**
- "It might be slow" (measure first)
- Micro-optimizations that hurt readability
- Before the feature is complete

## 5.1.2 Profiling
<!-- Lines 71-114 -->

Profiling measures where time (or memory) is actually spent. Python offers several profiling tools for different needs.

**cProfile** (built-in, function-level):
```python
import cProfile
cProfile.run('main()', sort='cumulative')
```

**line_profiler** (line-by-line):
```python
@profile
def slow_function():
    # Each line gets timing data
    ...
```

**memory_profiler** (memory usage):
```python
@profile
def memory_heavy():
    data = [i for i in range(1000000)]
    ...
```

**py-spy** (sampling profiler, production-safe):
```bash
py-spy top --pid 12345
py-spy record -o profile.svg --pid 12345
```

**Profiling Workflow:**
1. Profile the slow operation
2. Sort by cumulative time
3. Find the function taking the most time
4. Drill down into that function
5. Optimize or algorithm-change the bottleneck
6. Re-profile to verify

## 5.1.3 Optimization Techniques
<!-- Lines 117-159 -->

Once profiling identifies bottlenecks, apply targeted optimizations.

**Algorithm Choice**: The biggest wins come from better algorithms. O(n²) to O(n log n) beats any micro-optimization.

**Data Structure Selection**:
- `list`: Sequential access, append
- `set`: Membership testing (O(1) vs O(n))
- `dict`: Key-value lookup
- `deque`: Fast append/pop from both ends

**Caching**:
```python
from functools import lru_cache

@lru_cache(maxsize=128)
def expensive_computation(n):
    ...
```

**Lazy Evaluation**:
```python
# Eager: Computes all immediately
data = [transform(x) for x in items]

# Lazy: Computes on demand
data = (transform(x) for x in items)
```

**Vectorization** (NumPy):
```python
# Slow: Python loop
result = [x * 2 for x in data]

# Fast: NumPy vectorized
result = data * 2
```

## 5.1.4 Concurrency
<!-- Lines 162-200 -->

Concurrency handles multiple tasks that overlap in time. In Python, threading is best for **I/O-bound** work (waiting for network, disk, database).

**The GIL**: Python's Global Interpreter Lock means only one thread executes Python bytecode at a time. This limits CPU-bound threading but doesn't affect I/O-bound work (threads release GIL while waiting).

**threading module**:
```python
import threading

def fetch_url(url):
    response = requests.get(url)
    return response.text

threads = [threading.Thread(target=fetch_url, args=(url,)) for url in urls]
for t in threads:
    t.start()
for t in threads:
    t.join()
```

**concurrent.futures** (higher-level):
```python
from concurrent.futures import ThreadPoolExecutor

with ThreadPoolExecutor(max_workers=10) as executor:
    results = list(executor.map(fetch_url, urls))
```

**When to Use Threading:**
- Network requests
- File I/O
- Database queries
- Any operation that waits

## 5.1.5 Parallelism
<!-- Lines 203-240 -->

Parallelism executes multiple tasks simultaneously on different CPU cores. In Python, use **multiprocessing** for **CPU-bound** work to bypass the GIL.

**multiprocessing module**:
```python
from multiprocessing import Pool

def cpu_intensive(n):
    return sum(i * i for i in range(n))

with Pool(processes=4) as pool:
    results = pool.map(cpu_intensive, [1000000] * 10)
```

**concurrent.futures ProcessPoolExecutor**:
```python
from concurrent.futures import ProcessPoolExecutor

with ProcessPoolExecutor(max_workers=4) as executor:
    results = list(executor.map(cpu_intensive, data))
```

**When to Use Multiprocessing:**
- Mathematical computations
- Image/video processing
- Data transformation pipelines
- Any CPU-bound work

**Overhead Considerations:**
- Process creation is expensive
- Data must be serialized (pickle) between processes
- Shared state is complex

## 5.1.6 Async Programming
<!-- Lines 243-281 -->

Async programming handles thousands of concurrent I/O operations efficiently with a single thread. It's ideal for high-concurrency servers, API clients, and web scrapers.

**Basic async/await**:
```python
import asyncio
import httpx

async def fetch(url):
    async with httpx.AsyncClient() as client:
        response = await client.get(url)
        return response.text

async def main():
    urls = ["https://example.com"] * 100
    tasks = [fetch(url) for url in urls]
    results = await asyncio.gather(*tasks)

asyncio.run(main())
```

**When to Use Async:**
- High-concurrency I/O (thousands of connections)
- WebSocket servers
- API gateways
- Web scraping at scale

**When NOT to Use Async:**
- CPU-bound work (use multiprocessing)
- Simple scripts with few I/O operations
- Libraries don't support async

**The Event Loop**: Async code runs in an event loop that switches between tasks when they await. No actual parallelism—just efficient waiting.

## 5.1.7 Memory Management
<!-- Lines 284-329 -->

Python manages memory automatically, but understanding it helps avoid memory issues.

**Generators for Large Data**:
```python
# Bad: Loads entire file into memory
lines = open('huge.txt').readlines()

# Good: Processes line by line
for line in open('huge.txt'):
    process(line)
```

**`__slots__` for Many Objects**:
```python
class Point:
    __slots__ = ('x', 'y')
    def __init__(self, x, y):
        self.x = x
        self.y = y
# Uses ~40% less memory than regular class
```

**Weak References**:
```python
import weakref
cache = weakref.WeakValueDictionary()
# Objects can be garbage collected even if in cache
```

**Memory Profiling**:
```bash
python -m memory_profiler script.py
```

**Common Memory Issues:**
- Unbounded caches
- Circular references (usually handled by GC)
- Large data structures held unnecessarily
- String concatenation in loops

## 5.1.8 Scaling Patterns
<!-- Lines 332-367 -->

When single-machine performance isn't enough, scale out.

**Vertical Scaling**: Bigger machine (more CPU, RAM). Simple but limited.

**Horizontal Scaling**: More machines. Requires distributed architecture.

**Worker Queues**:
```
[Web Server] → [Redis Queue] → [Worker 1]
                            → [Worker 2]
                            → [Worker N]
```

Tools: Celery, RQ, Dramatiq

**Load Balancing**:
```
[Load Balancer] → [App Server 1]
                → [App Server 2]
                → [App Server N]
```

**Caching Layers**:
```
[Request] → [CDN] → [Redis] → [Database]
```

**Scaling Principles:**
- Stateless applications (store state externally)
- Idempotent operations (safe to retry)
- Graceful degradation
- Circuit breakers for external services
