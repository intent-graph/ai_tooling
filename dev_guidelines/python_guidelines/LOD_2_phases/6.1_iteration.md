## Overview
<!-- Lines 19-38 -->

Software is never finished. Requirements evolve, understanding deepens, and yesterday's clever solution becomes tomorrow's maintenance burden. The iteration phase addresses how to change code that already works—arguably the most common and challenging activity in professional development.

The core tension in iteration is between stability and improvement. Users depend on existing behavior, yet code must evolve to remain maintainable. This phase provides frameworks for navigating that tension: when to refactor, how to track and prioritize debt, when to deprecate features, and how to introduce breaking changes responsibly.

Good iteration practices compound over time. Each well-executed refactoring makes the next change easier. Each properly managed deprecation builds trust with users. Each thoughtfully communicated breaking change demonstrates professionalism. Conversely, neglected iteration creates a downward spiral where changes become increasingly risky and expensive.

**The Iteration Mindset:**
- Code is a living artifact, not a finished product
- Every change carries both benefit and risk
- Transparency with users builds long-term trust
- Small, frequent improvements beat large, infrequent rewrites

## 6.1.1 Refactoring
<!-- Lines 41-64 -->

Refactoring is changing code structure without changing behavior. It is the primary mechanism for keeping code maintainable over time. The key insight is that refactoring is not cleaning up—it is a distinct activity with its own discipline.

Effective refactoring requires two conditions: a clear goal and a safety net. The goal might be improving readability, reducing duplication, or preparing for a new feature. The safety net is tests that verify behavior remains unchanged. Without both, refactoring becomes risky guesswork.

The refactoring catalog (extract function, rename, move, inline, etc.) provides a vocabulary of atomic transformations. Each transformation is small enough to verify and reversible if something goes wrong. Complex restructuring emerges from composing these simple steps.

**When to Refactor:**
- Before adding a feature (prepare the ground)
- After adding a feature (clean up scaffolding)
- When code is hard to understand
- When duplication emerges

**When NOT to Refactor:**
- Without test coverage
- Under time pressure (creates half-done states)
- As a procrastination mechanism
- When a rewrite would be cleaner

## 6.1.2 Technical Debt
<!-- Lines 67-90 -->

Technical debt is the gap between your code's current state and the state it should be in. Like financial debt, it accrues interest—shortcuts today create friction tomorrow. Unlike financial debt, technical debt is often invisible until it blocks progress.

Not all debt is bad. Strategic debt—conscious shortcuts with a plan to repay—can accelerate delivery. The problem is untracked debt that accumulates silently until the codebase becomes a minefield. The solution is making debt visible and managing it intentionally.

Debt manifests in many forms: missing tests, outdated dependencies, inconsistent patterns, unclear boundaries, undocumented assumptions. Each type requires different remediation strategies. Some debt is cheap to carry; other debt compounds rapidly. The skill is distinguishing between them.

**Debt Categories:**
- **Prudent Deliberate**: "We'll ship now and refactor before the next feature"
- **Reckless Deliberate**: "We don't have time for design"
- **Prudent Inadvertent**: "Now we know how we should have done it"
- **Reckless Inadvertent**: "What's layering?"

**Tracking Practices:**
- Document debt in code (TODO/FIXME with tickets)
- Maintain a debt backlog separate from features
- Review debt during planning (allocate capacity)
- Measure debt indicators (cyclomatic complexity, test coverage gaps)

## 6.1.3 Deprecation
<!-- Lines 93-124 -->

Deprecation is the formal process of phasing out features, APIs, or patterns. It bridges the gap between "this works" and "this should go away." Done well, deprecation gives users time to migrate while preventing new adoption of outdated approaches.

The deprecation lifecycle has three phases: announce, warn, remove. In the announce phase, document the deprecation and the migration path. In the warn phase, emit runtime warnings that guide users toward alternatives. In the remove phase, delete the deprecated code. Each phase should span at least one release cycle.

Python provides built-in tools for deprecation. The `warnings` module emits deprecation warnings that users can filter. The `@deprecated` decorator (Python 3.13+) formalizes the pattern. For libraries, semantic versioning guides timing: deprecate in minor versions, remove in major versions.

**Deprecation Checklist:**
- Document why the feature is deprecated
- Provide a clear migration path
- Add runtime warnings with actionable messages
- Announce in release notes
- Set a removal timeline

**Warning Example:**
```python
import warnings

def old_function():
    warnings.warn(
        "old_function is deprecated, use new_function instead",
        DeprecationWarning,
        stacklevel=2
    )
    return new_function()
```

## 6.1.4 Breaking Changes
<!-- Lines 127-159 -->

Breaking changes alter existing behavior in ways that require users to modify their code. They are sometimes necessary but always costly—both for users who must adapt and for trust in your software's stability. The goal is minimizing breaking changes while not being paralyzed by backward compatibility.

The first question is whether a change truly breaks compatibility. Internal implementation changes aren't breaking. Adding optional parameters isn't breaking. Changing return types, removing functions, or altering default behavior—these break compatibility. When in doubt, it probably breaks.

When breaking changes are unavoidable, communication is everything. Users need to know what changed, why it changed, and how to adapt. Semantic versioning signals breaking changes through major version bumps. Changelogs document specifics. Migration guides walk users through updates.

**Minimizing Breaking Changes:**
- Add new functions instead of modifying existing ones
- Use optional parameters with sensible defaults
- Support both old and new patterns during transition
- Design APIs for extension from the start

**When Breaking Changes Are Necessary:**
- Security vulnerabilities require immediate change
- Accumulated debt makes evolution impossible
- The old design was fundamentally flawed
- External dependencies force the change

**Communication Template:**
```markdown

**Why:** [justification]
**Migration:** [step-by-step guide]

```
