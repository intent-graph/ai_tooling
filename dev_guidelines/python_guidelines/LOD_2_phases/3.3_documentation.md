## Overview
<!-- Lines 21-47 -->

Documentation is communication—it serves different audiences with different needs. Good documentation answers questions before they're asked.

**Documentation Principles:**
- Write for your audience (not yourself)
- Keep it close to code (docstrings over wikis)
- Update with code (stale docs mislead)
- Prefer examples over explanations

**Audience Hierarchy:**
| Audience | Needs | Medium |
|----------|-------|--------|
| New users | Quick start | README |
| Users | How to use | Tutorials, API docs |
| Contributors | How it works | Architecture docs, comments |
| Maintainers | Why decisions | ADRs, inline comments |

**Documentation as UX:**
Documentation is part of your interface. Poor docs create support burden and reduce adoption.

## 3.3.1 Documentation Levels
<!-- Lines 50-78 -->

Different documentation serves different purposes. Match the level to the need.

**Documentation Hierarchy:**

| Level | Scope | Format | Audience |
|-------|-------|--------|----------|
| Inline comments | Line/block | Code | Maintainers |
| Docstrings | Function/class | Code | Developers |
| README | Project | Markdown | Everyone |
| API docs | Public interface | Generated | Users |
| Guides | Workflows | Prose | Users |
| Architecture | System design | Diagrams | Contributors |

**When to Write What:**
```
Code is unclear → Inline comment (explain why)
Function contract → Docstring (explain what)
Getting started → README (quick wins)
Reference → API docs (complete interface)
Learning path → Tutorial (step-by-step)
```

## 3.3.2 README Standards
<!-- Lines 81-129 -->

The README is the front door to your project. It should answer: What is this? How do I use it?

**README Structure:**
```markdown
# Project Name

One-line description of what it does.

## Installation
<!-- Lines 100-102 -->

pip install project-name

## Quick Start
<!-- Lines 105-108 -->

from project_name import main_function
result = main_function("input")

## Features
<!-- Lines 111-114 -->

- Feature 1
- Feature 2

## Documentation
<!-- Lines 117-119 -->

Full docs at https://docs.example.com

## License
<!-- Lines 122-137 -->

MIT
```

**Essential Sections:**
1. **Name + Description**: What is it?
2. **Installation**: How to get it
3. **Quick Start**: Working example in <30 seconds
4. **Features**: What it does
5. **License**: Legal terms

## 3.3.3 Docstrings
<!-- Lines 132-173 -->

Docstrings document functions, classes, and modules. They're accessible at runtime and by documentation generators.

**When to Write Docstrings:**
- All public functions and classes
- Complex private functions
- Modules with non-obvious purpose

**Google Style (Recommended):**
```python
def fetch_user(user_id: int, include_inactive: bool = False) -> User | None:
    """Fetch a user by ID.

    Args:
        user_id: The unique identifier of the user.
        include_inactive: Whether to include deactivated users.

    Returns:
        The User object if found, None otherwise.

    Raises:
        DatabaseError: If the database connection fails.

    Example:
        >>> user = fetch_user(123)
        >>> user.name
        'Alice'
    """
```

**Docstring Content:**
- First line: Brief summary (imperative mood)
- Args: Parameter descriptions
- Returns: What's returned
- Raises: Exceptions that may be raised
- Example: Usage example (optional but valuable)

## 3.3.4 API Documentation
<!-- Lines 176-213 -->

API documentation provides comprehensive reference for your public interface. Generate from docstrings.

**Tool Options:**

| Tool | Style | Output |
|------|-------|--------|
| Sphinx | Traditional | HTML, PDF |
| MkDocs | Modern | HTML |
| pdoc | Minimal | HTML |

**MkDocs Setup:**
```yaml
# mkdocs.yml
site_name: My Project
theme:
  name: material

plugins:
  - search
  - mkdocstrings:
      handlers:
        python:
          options:
            docstring_style: google
```

**API Doc Principles:**
- Generate from code (single source of truth)
- Include examples for every function
- Group by functionality, not file
- Keep up-to-date with CI checks

## 3.3.6 Inline Comments
<!-- Lines 269-304 -->

Inline comments explain why, not what. Code should be self-documenting for the what.

**When to Comment:**
- Non-obvious business logic
- Workarounds for bugs/limitations
- Performance optimizations
- References to external resources

**Comment Patterns:**

```python
# GOOD: Explains why
# Use binary search because list is always sorted and large (>10k items)
index = bisect.bisect_left(sorted_items, target)

# BAD: Explains what (code already shows this)
# Loop through items
for item in items:
    ...

# GOOD: References external context
# See RFC 7231 Section 6.5.1 for status code semantics
# https://tools.ietf.org/html/rfc7231#section-6.5.1
```

**TODO/FIXME Conventions:**
```python
# TODO(username): Description of what needs doing
# FIXME: Known bug that needs fixing
# HACK: Temporary workaround, explain why
# NOTE: Important information for maintainers
```
