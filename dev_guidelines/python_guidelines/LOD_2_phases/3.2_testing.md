## Overview
<!-- Lines 21-54 -->

Testing provides confidence that code works correctly and continues to work as it evolves. Tests are executable specifications—they document expected behavior.

**Testing Principles:**
- Tests are code: Apply same quality standards
- Fast tests run often: Keep unit tests fast
- Test behavior, not implementation: Tests shouldn't break on refactoring
- Reproduce before fixing: Write a failing test first

**Testing Pyramid:**
```
        /\
       /  \      E2E (few)
      /----\
     /      \    Integration (some)
    /--------\
   /          \  Unit (many)
  /------------\
```

**Test Categories:**
| Type | Scope | Speed | Dependencies |
|------|-------|-------|--------------|
| Unit | Function/class | Fast | None/mocked |
| Integration | Multiple components | Medium | Real deps |
| E2E | Full system | Slow | All real |

## 3.2.1 Unit Testing
<!-- Lines 57-90 -->

Unit tests verify individual functions and classes in isolation. They should be fast, focused, and independent.

**Unit Test Characteristics:**
- Tests one thing
- No external dependencies (database, network, filesystem)
- Fast (< 100ms each)
- Deterministic (same result every run)

**AAA Pattern:**
```python
def test_user_full_name():
    # Arrange
    user = User(first_name="Alice", last_name="Smith")

    # Act
    result = user.full_name()

    # Assert
    assert result == "Alice Smith"
```

**When to Mock:**
- External services (APIs, databases)
- Non-deterministic behavior (time, random)
- Slow operations
- **Don't mock:** Internal collaborators (usually)

## 3.2.2 Integration Testing
<!-- Lines 93-137 -->

Integration tests verify that components work together correctly. They use real dependencies where feasible.

**Integration Test Scope:**
- Database operations with real database
- API endpoints with test client
- Multi-component workflows
- External service interactions (with test doubles)

**Database Testing Pattern:**
```python
import pytest
from sqlalchemy import create_engine

@pytest.fixture
def db_session():
    """Create test database session."""
    engine = create_engine("sqlite:///:memory:")
    Base.metadata.create_all(engine)
    session = Session(engine)
    yield session
    session.rollback()

def test_create_user(db_session):
    user = User(name="Alice")
    db_session.add(user)
    db_session.commit()

    assert db_session.query(User).count() == 1
```

**API Testing:**
```python
from fastapi.testclient import TestClient

def test_create_user_endpoint(client: TestClient):
    response = client.post("/users", json={"name": "Alice"})
    assert response.status_code == 201
```

## 3.2.3 Fixtures & Factories
<!-- Lines 140-189 -->

Fixtures and factories provide test data. Fixtures are pytest's mechanism for setup/teardown; factories are patterns for creating test objects.

**Pytest Fixtures:**
```python
# conftest.py
import pytest

@pytest.fixture
def sample_user():
    return User(id=1, name="Test User", email="test@example.com")

@pytest.fixture
def authenticated_client(client, sample_user):
    client.force_login(sample_user)
    return client
```

**Fixture Scopes:**
| Scope | Lifetime | Use For |
|-------|----------|---------|
| function | Each test | Default, most cases |
| class | Test class | Shared setup per class |
| module | Test module | Expensive setup |
| session | Entire run | Very expensive (DB schema) |

**Factory Pattern:**
```python
# factories.py
from dataclasses import dataclass

@dataclass
class UserFactory:
    @staticmethod
    def create(**overrides) -> User:
        defaults = {
            "name": "Test User",
            "email": "test@example.com",
        }
        return User(**{**defaults, **overrides})

# Usage
user = UserFactory.create(name="Alice")
```

## 3.2.4 Coverage Strategy
<!-- Lines 192-229 -->

Coverage measures how much code tests exercise. It's a useful metric but not a goal in itself.

**Coverage Philosophy:**
- Coverage is a metric, not a target
- 100% coverage doesn't mean bug-free
- Low coverage indicates untested code
- Focus on critical paths first

**Coverage Configuration:**
```toml
# pyproject.toml
[tool.coverage.run]
source = ["src"]
branch = true
omit = ["*/tests/*", "*/__main__.py"]

[tool.coverage.report]
exclude_lines = [
    "pragma: no cover",
    "if TYPE_CHECKING:",
    "raise NotImplementedError",
    "@abstractmethod",
]
fail_under = 80
```

**What to Test:**
- Business logic (high value)
- Edge cases and error paths
- Public API contracts
- **Skip:** Trivial code, third-party wrappers

## 3.2.5 Test Organization
<!-- Lines 232-273 -->

Consistent test organization makes tests discoverable and maintainable.

**Directory Structure:**
```
tests/
├── conftest.py          # Shared fixtures
├── unit/
│   ├── test_models.py
│   └── test_services.py
├── integration/
│   ├── conftest.py      # Integration fixtures
│   ├── test_api.py
│   └── test_database.py
└── e2e/
    └── test_workflows.py
```

**Naming Conventions:**
- Files: `test_<module>.py`
- Functions: `test_<behavior>` or `test_<method>_<scenario>`
- Classes: `Test<ClassName>`

**Test Naming Examples:**
```python
# Good: Describes behavior
def test_user_with_invalid_email_raises_error():
    ...

def test_calculate_total_with_discount():
    ...

# Avoid: Vague
def test_user():
    ...
```

## 3.2.6 Property-Based Testing
<!-- Lines 276-306 -->

Property-based testing generates random inputs to find edge cases. Use Hypothesis library.

**When to Use:**
- Functions with well-defined properties
- Parsers and serializers
- Mathematical operations
- Finding edge cases automatically

**Hypothesis Example:**
```python
from hypothesis import given, strategies as st

@given(st.lists(st.integers()))
def test_sort_is_idempotent(lst):
    """Sorting twice gives same result as sorting once."""
    assert sorted(sorted(lst)) == sorted(lst)

@given(st.text())
def test_encode_decode_roundtrip(text):
    """JSON roundtrip preserves data."""
    assert json.loads(json.dumps(text)) == text
```

**Common Strategies:**
- `st.integers()`, `st.floats()`, `st.text()`
- `st.lists(st.integers())`, `st.dictionaries()`
- `st.from_type(MyDataclass)`
