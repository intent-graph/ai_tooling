## Overview
<!-- Lines 20-33 -->

Packaging transforms a collection of Python files into a distributable unit that others can install. Modern Python packaging centers on `pyproject.toml` as the single source of truth for project metadata, build configuration, and tool settings. This declarative approach replaces the fragmented landscape of `setup.py`, `setup.cfg`, `requirements.txt`, and scattered tool configurations.

The packaging lifecycle follows a clear progression: define metadata and dependencies in `pyproject.toml`, choose a build backend, generate distribution artifacts (sdist and wheel), and publish to a package index. Each stage has well-established conventions that balance flexibility with ecosystem compatibility.

Dependency management presents one of Python's most nuanced challenges. Unlike compiled languages with static linking, Python resolves dependencies at install time, creating potential for version conflicts. Understanding the distinction between abstract dependencies (what you need) and concrete dependencies (what you installed) prevents the "works on my machine" syndrome that plagues many projects.

## 4.1.1 pyproject.toml
<!-- Lines 36-68 -->

The `pyproject.toml` file is Python's modern packaging standard (PEP 518, PEP 621). It consolidates project metadata, build system configuration, and tool settings in a single, human-readable file.

**Core Sections:**

```toml
[project]
name = "mypackage"
version = "1.0.0"
description = "What this package does"
requires-python = ">=3.10"
dependencies = ["httpx>=0.24", "pydantic>=2.0"]

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[tool.ruff]
line-length = 88
```

The `[project]` table defines metadata that appears on PyPI: name, version, description, authors, classifiers, and dependencies. The `[build-system]` table specifies how to build the package. The `[tool.*]` tables configure development tools.

**Key Principles:**
- Single source of truth for project configuration
- Declarative over imperative (no executable code)
- Standard format readable by any compliant tool

## 4.1.2 Dependency Management
<!-- Lines 71-107 -->

Dependencies come in two flavors: **abstract** (what your code needs to run) and **concrete** (the exact versions installed in a specific environment). This distinction drives the entire dependency management strategy.

**Abstract Dependencies** go in `pyproject.toml`:
```toml
[project]
dependencies = [
    "requests>=2.28",      # Minimum version
    "pydantic>=2.0,<3.0",  # Version range
]

[project.optional-dependencies]
dev = ["pytest>=7.0", "ruff>=0.1"]
```

**Concrete Dependencies** go in lock files (`requirements.lock`, `uv.lock`, `poetry.lock`):
```
requests==2.31.0
certifi==2023.7.22
charset-normalizer==3.2.0
idna==3.4
urllib3==2.0.4
```

The workflow: specify flexible constraints in `pyproject.toml`, generate pinned versions in lock files, commit both. Development uses lock files for reproducibility; packaging uses abstract dependencies for flexibility.

**Dependency Categories:**
- **Runtime**: Required to use the package
- **Development**: Required to develop the package (testing, linting)
- **Optional**: Enable additional features (`pip install mypackage[postgres]`)

## 4.1.3 Build Backends
<!-- Lines 110-143 -->

A build backend transforms source code into distributable packages. The `[build-system]` table in `pyproject.toml` specifies which backend to use.

**Modern Options:**

| Backend | Best For | Philosophy |
|---------|----------|------------|
| **hatchling** | Most projects | Simple, fast, minimal config |
| **setuptools** | Complex builds | Mature, feature-complete |
| **flit-core** | Pure Python | Ultra-minimal |
| **poetry-core** | Poetry users | Poetry ecosystem integration |

**Selection Criteria:**
1. Pure Python package with simple needs → `hatchling` or `flit-core`
2. Package with C extensions → `setuptools` (or `meson-python`)
3. Already using Poetry → `poetry-core`
4. Need dynamic version from git tags → most backends support this

**Minimal Example with Hatchling:**
```toml
[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"
```

Build backends produce two artifact types:
- **sdist** (source distribution): Tarball of source code
- **wheel**: Pre-built package, ready to install without building

## 4.1.4 Publishing
<!-- Lines 146-188 -->

Publishing makes your package installable via `pip install`. The primary targets are PyPI (public) and private indexes (internal packages).

**Publishing Workflow:**
```bash
# Build artifacts
python -m build

# Upload to TestPyPI (testing)
twine upload --repository testpypi dist/*

# Upload to PyPI (production)
twine upload dist/*
```

**Trusted Publishing (Recommended):**

Modern PyPI supports OIDC-based publishing from CI systems. No API tokens to manage:

```yaml
# GitHub Actions
- uses: pypa/gh-action-pypi-publish@release/v1
  # No credentials needed with trusted publishing configured
```

**Private Indexes:**

For internal packages, options include:
- Simple file server (`pip install --index-url`)
- devpi (self-hosted PyPI)
- Cloud solutions (AWS CodeArtifact, GCP Artifact Registry)

**Pre-flight Checklist:**
- [ ] Package name available on PyPI
- [ ] Version number follows PEP 440
- [ ] README renders correctly (test on TestPyPI)
- [ ] License classifier matches LICENSE file

## 4.1.5 Versioning Schemes
<!-- Lines 191-236 -->

Version numbers communicate change impact to users. Python packaging requires PEP 440 compliance, but the semantic scheme is your choice.

**Semantic Versioning (SemVer):** `MAJOR.MINOR.PATCH`
- MAJOR: Breaking changes
- MINOR: New features, backward compatible
- PATCH: Bug fixes

**Calendar Versioning (CalVer):** `YYYY.MM.DD` or `YYYY.MM.MICRO`
- Good for projects without API stability promises
- Common in large applications, frameworks

**Hybrid:** `YEAR.MINOR.PATCH` (e.g., `2024.1.0`)

**Version Sources:**

Modern build backends can derive version from multiple sources:
```toml
# Static in pyproject.toml
[project]
version = "1.2.3"

# Dynamic from __version__
[project]
dynamic = ["version"]
[tool.hatch.version]
path = "src/mypackage/__init__.py"

# Dynamic from git tags
[tool.hatch.version]
source = "vcs"
```

**Changelog Discipline:**

Every version bump should have a corresponding CHANGELOG entry. Tools like `towncrier` automate changelog generation from fragment files:

```
changes/
├── 123.feature.md   # "Added user authentication"
├── 145.bugfix.md    # "Fixed timezone handling"
└── 150.breaking.md  # "Removed deprecated API"
```
