## Overview
<!-- Lines 19-34 -->

Deployment bridges the gap between "it works on my machine" and "it works in production." This phase addresses the operational concerns that determine whether your Python application runs reliably in real-world conditions.

The 12-Factor App methodology provides the foundational principles: configuration through environment variables, stateless processes, explicit dependency declaration, and dev/prod parity. These principles translate into specific Python patterns for configuration management, containerization, and observability.

Modern Python deployment typically involves containers. Docker provides isolation and reproducibility—the same image runs identically in development, staging, and production. Multi-stage builds keep images small; proper layer ordering ensures efficient caching.

Observability—monitoring, logging, and tracing—lets you understand system behavior in production. You can't debug what you can't see. Prometheus metrics, structured logging, and distributed tracing form the observability stack that turns black boxes into transparent systems.

## 4.3.1 Environment Configuration
<!-- Lines 37-79 -->

Configuration varies between environments—database URLs, API keys, feature flags. The 12-Factor App principle: store configuration in environment variables, not in code.

**Environment Variables Pattern:**
```python
import os
from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    database_url: str
    api_key: str
    debug: bool = False

    model_config = {"env_prefix": "APP_"}

settings = Settings()  # Reads APP_DATABASE_URL, APP_API_KEY, etc.
```

**Configuration Hierarchy:**
1. Environment variables (highest priority)
2. `.env` files (development convenience)
3. Default values in code (lowest priority)

**Environment Separation:**
| Environment | Purpose | Configuration Source |
|-------------|---------|---------------------|
| Development | Local work | `.env` file |
| Testing | CI/CD | Environment variables |
| Staging | Pre-production validation | Secrets manager |
| Production | Live users | Secrets manager |

**Secrets Handling:**
- Never commit secrets to version control
- Use `.env.example` with placeholder values
- Production: Use AWS Secrets Manager, HashiCorp Vault, etc.
- Add `.env` to `.gitignore`

## 4.3.2 Containerization
<!-- Lines 82-125 -->

Containers package your application with its dependencies, ensuring consistent behavior across environments. Docker is the standard tool.

**Production Dockerfile Pattern:**
```dockerfile
# Build stage
FROM python:3.11-slim as builder
WORKDIR /app
RUN pip install uv
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev

# Runtime stage
FROM python:3.11-slim
WORKDIR /app
COPY --from=builder /app/.venv .venv
COPY src ./src
ENV PATH="/app/.venv/bin:$PATH"
CMD ["python", "-m", "myapp"]
```

**Multi-Stage Build Benefits:**
- Build dependencies don't bloat final image
- Smaller attack surface (no compilers, dev tools)
- Faster deployments (smaller images to transfer)

**Layer Optimization:**
```dockerfile
# Dependencies change less often than code
COPY pyproject.toml uv.lock ./  # Layer 1: deps
RUN uv sync                      # Layer 2: install
COPY src ./src                   # Layer 3: code (changes most)
```

**Image Selection:**
- `python:3.11-slim`: Good balance of size and compatibility
- `python:3.11-alpine`: Smallest, but musl libc can cause issues
- Distroless images: Maximum security, minimal debugging

## 4.3.3 Monitoring
<!-- Lines 128-176 -->

Monitoring answers: "Is the system healthy? How is it performing?" Metrics provide quantitative answers; dashboards visualize trends; alerts notify on anomalies.

**Prometheus Metrics Pattern:**
```python
from prometheus_client import Counter, Histogram, start_http_server

REQUEST_COUNT = Counter(
    "http_requests_total",
    "Total HTTP requests",
    ["method", "endpoint", "status"]
)

REQUEST_LATENCY = Histogram(
    "http_request_duration_seconds",
    "HTTP request latency",
    ["endpoint"]
)

@REQUEST_LATENCY.labels(endpoint="/api/users").time()
def get_users():
    ...
    REQUEST_COUNT.labels(method="GET", endpoint="/api/users", status="200").inc()
```

**Four Golden Signals:**
1. **Latency**: Time to serve requests
2. **Traffic**: Requests per second
3. **Errors**: Rate of failed requests
4. **Saturation**: Resource utilization (CPU, memory, connections)

**Metric Types:**
| Type | Use Case | Example |
|------|----------|---------|
| Counter | Events that only increase | Request count, errors |
| Gauge | Values that go up and down | Active connections, queue size |
| Histogram | Distributions | Request latency, response size |

**Dashboard Essentials:**
- Request rate and error rate over time
- Latency percentiles (p50, p95, p99)
- Resource utilization (CPU, memory)
- Business metrics (users, transactions)

## 4.3.4 Health Checks
<!-- Lines 179-235 -->

Health checks let orchestrators (Kubernetes, Docker Swarm) know if your application is functioning. Two types: **liveness** (is it running?) and **readiness** (can it serve traffic?).

**Health Endpoint Pattern:**
```python
from fastapi import FastAPI, status
from fastapi.responses import JSONResponse

app = FastAPI()

@app.get("/health/live")
def liveness():
    """Liveness: Is the process running?"""
    return {"status": "alive"}

@app.get("/health/ready")
def readiness():
    """Readiness: Can we serve traffic?"""
    try:
        db.execute("SELECT 1")
        cache.ping()
        return {"status": "ready"}
    except Exception as e:
        return JSONResponse(
            {"status": "not_ready", "reason": str(e)},
            status_code=status.HTTP_503_SERVICE_UNAVAILABLE
        )
```

**Kubernetes Configuration:**
```yaml
livenessProbe:
  httpGet:
    path: /health/live
    port: 8000
  initialDelaySeconds: 10
  periodSeconds: 30

readinessProbe:
  httpGet:
    path: /health/ready
    port: 8000
  initialDelaySeconds: 5
  periodSeconds: 10
```

**Health Check Design:**
- **Liveness**: Should almost always return OK. Only fail if restart would help.
- **Readiness**: Check dependencies (database, cache, external services)
- Keep checks fast (<1 second)
- Don't check transient external services in liveness

**Startup Probes** (Kubernetes 1.16+):
For slow-starting applications, use startup probes to delay liveness/readiness checks until the app is fully initialized.
