## Overview
<!-- Lines 21-41 -->

Security is not a feature—it's a property of the entire system. Every line of code, every dependency, every configuration choice affects security posture. The goal isn't perfect security (impossible) but appropriate security for the risk level.

Python applications face common vulnerability classes: injection attacks (SQL, command, template), authentication/authorization flaws, sensitive data exposure, dependency vulnerabilities, and cryptographic failures. Most vulnerabilities come not from exotic attacks but from mundane mistakes: trusting user input, hardcoding secrets, using outdated dependencies.

Security thinking differs from feature thinking. Features ask "how do I make this work?" Security asks "how could this break?" and "what if the user is malicious?" This adversarial mindset—always assuming inputs are hostile—is the foundation of secure coding.

The security layers:
1. **Secrets Management**: Keep credentials out of code
2. **Input Validation**: Never trust external data
3. **Dependency Auditing**: Know what you're importing
4. **Secure Coding**: Avoid common vulnerability patterns
5. **Defense in Depth**: Multiple layers, no single point of failure

## 5.2.1 Security Mindset
<!-- Lines 44-71 -->

Security is a process, not a product. It requires ongoing attention, not one-time configuration.

**Principle of Least Privilege**: Every component should have only the permissions it needs, nothing more. Database users should have only required table access. API keys should be scoped narrowly.

**Defense in Depth**: Multiple security layers. If one fails, others still protect. Input validation + parameterized queries + least-privilege database user = defense in depth for SQL injection.

**Assume Breach**: Design systems assuming attackers will get partial access. Encrypt data at rest. Segment networks. Log everything for forensics.

**Security vs Usability**: Security that's too annoying gets bypassed. Find the balance—make the secure path the easy path.

**Threat Modeling Questions:**
- What are we building?
- What can go wrong?
- What are we doing about it?
- Did we do a good job?

**Common Mistakes:**
- Security through obscurity (doesn't work)
- Trusting client-side validation
- Logging sensitive data
- Hardcoding secrets "temporarily"

## 5.2.2 Secrets Management
<!-- Lines 74-132 -->

Secrets (API keys, passwords, tokens) must never appear in code, logs, or version control.

**Environment Variables**:
```python
import os

database_url = os.environ["DATABASE_URL"]
api_key = os.environ["API_KEY"]
```

**.env Files (development only)**:
```bash
# .env (gitignored)
DATABASE_URL=postgresql://localhost/myapp
API_KEY=dev-key-not-for-production
```

```python
from dotenv import load_dotenv
load_dotenv()
```

**Production Secrets Managers**:
- AWS Secrets Manager
- HashiCorp Vault
- Google Secret Manager
- Azure Key Vault

**Secret Hygiene:**
- Rotate secrets regularly
- Use different secrets per environment
- Audit secret access
- Never log secrets (even partially)

**Git Protection**:
```bash
# .gitignore
.env
*.pem
credentials.json

# Pre-commit hook to detect secrets
- repo: https://github.com/Yelp/detect-secrets
  hooks:
    - id: detect-secrets
```

**If Secrets Are Exposed:**
1. Revoke immediately
2. Rotate to new secrets
3. Audit for unauthorized use
4. Review how exposure happened

## 5.2.3 Input Validation
<!-- Lines 135-185 -->

Never trust user input. All external data is potentially malicious until validated.

**Validation Layers:**
1. **Syntactic**: Is the format correct? (email, URL, date)
2. **Semantic**: Is the value sensible? (age > 0, price > 0)
3. **Authorization**: Is the user allowed this value?

**Pydantic for Validation**:
```python
from pydantic import BaseModel, EmailStr, conint

class UserCreate(BaseModel):
    email: EmailStr
    age: conint(ge=0, le=150)
    name: str

# Invalid data raises ValidationError
user = UserCreate(email="bad", age=-5, name="")
```

**Allowlists over Denylists**:
```python
# Bad: Trying to block bad inputs
if "<script>" not in user_input:  # Easily bypassed

# Good: Allow only known-good patterns
ALLOWED_CHARS = set("abcdefghijklmnopqrstuvwxyz0123456789-_")
if all(c in ALLOWED_CHARS for c in username):
    ...
```

**Context-Specific Escaping**:
```python
# HTML context
from markupsafe import escape
safe_html = escape(user_input)

# SQL context (use parameters, not escaping)
cursor.execute("SELECT * FROM users WHERE id = %s", (user_id,))

# Shell context (avoid if possible)
import shlex
safe_arg = shlex.quote(user_input)
```

## 5.2.4 Dependency Auditing
<!-- Lines 188-239 -->

Dependencies are code you didn't write but run with full privileges. Supply chain attacks target popular packages.

**pip-audit**:
```bash
pip install pip-audit
pip-audit
# Reports known vulnerabilities in installed packages
```

**Safety**:
```bash
pip install safety
safety check
```

**Dependabot (GitHub)**:
```yaml
# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: pip
    directory: "/"
    schedule:
      interval: weekly
```

**SBOM (Software Bill of Materials)**:
```bash
pip install cyclonedx-bom
cyclonedx-py -o sbom.json
```

**Dependency Hygiene:**
- Pin versions in lock files
- Update regularly (but test first)
- Monitor security advisories
- Minimize dependencies (less code = less risk)
- Audit before adding new dependencies

**Evaluating New Dependencies:**
- Is it actively maintained?
- How many downloads/stars?
- Any known vulnerabilities?
- What permissions does it need?
- Can we implement it ourselves simply?

## 5.2.5 Secure Coding
<!-- Lines 242-291 -->

Secure coding prevents common vulnerability patterns.

**SQL Injection Prevention**:
```python
# NEVER: String formatting
query = f"SELECT * FROM users WHERE id = {user_id}"

# ALWAYS: Parameterized queries
cursor.execute("SELECT * FROM users WHERE id = %s", (user_id,))
```

**Command Injection Prevention**:
```python
# NEVER: Shell=True with user input
subprocess.run(f"convert {filename}", shell=True)

# ALWAYS: List arguments, no shell
subprocess.run(["convert", filename], shell=False)
```

**Path Traversal Prevention**:
```python
from pathlib import Path

def safe_read(user_filename):
    base = Path("/app/uploads")
    target = (base / user_filename).resolve()
    if not target.is_relative_to(base):
        raise ValueError("Path traversal attempt")
    return target.read_text()
```

**Timing Attack Prevention**:
```python
import secrets

# NEVER: Early exit on mismatch
if user_token != secret_token:  # Timing leak!

# ALWAYS: Constant-time comparison
if not secrets.compare_digest(user_token, secret_token):
    ...
```

## 5.2.6 Cryptography Basics
<!-- Lines 294-338 -->

Rule #1: **Don't roll your own crypto.** Use established libraries (`cryptography`, `PyNaCl`).

**Password Hashing**:
```python
from argon2 import PasswordHasher

ph = PasswordHasher()
hash = ph.hash("password123")
ph.verify(hash, "password123")  # Raises on mismatch
```

Never use MD5/SHA for passwords—use Argon2, bcrypt, or scrypt.

**Encryption** (when you need it):
```python
from cryptography.fernet import Fernet

key = Fernet.generate_key()  # Store securely!
f = Fernet(key)
encrypted = f.encrypt(b"secret data")
decrypted = f.decrypt(encrypted)
```

**Secure Random**:
```python
import secrets

# For tokens, passwords, keys
token = secrets.token_urlsafe(32)
```

Never use `random` module for security—it's predictable.

**When to Use Crypto:**
- Passwords → Hash (Argon2)
- Data at rest → Encrypt (AES-GCM via Fernet)
- Data in transit → TLS (let the library handle it)
- Tokens → `secrets.token_urlsafe()`

**When NOT to Roll Your Own:**
- Always
