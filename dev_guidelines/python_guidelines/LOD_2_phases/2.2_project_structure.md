## Overview
<!-- Lines 19-46 -->

Project structure is architecture made visible. The directory layout communicates intent—where to find things, how components relate, what boundaries exist. A well-structured project is navigable by anyone familiar with Python conventions.

Structure decisions should be made once, at project inception, and followed consistently. Changing project layout mid-development is disruptive and error-prone.

**Structure Principles:**
- **Separation of concerns**: Source code, tests, configuration, documentation in distinct locations
- **Flat is better than nested**: Avoid deep hierarchies unless complexity demands them
- **Convention over configuration**: Follow community standards (PEP 517, src-layout)
- **Explicit boundaries**: Package boundaries = architectural boundaries

**Standard Project Anatomy:**
```
project_name/
├── src/project_name/    # Source code (src-layout)
├── tests/               # Test suite
├── docs/                # Documentation
├── pyproject.toml       # Project metadata and dependencies
└── README.md            # Project overview
```

## 2.2.1 Directory Layout
<!-- Lines 49-101 -->

Three layout patterns dominate Python projects. Choose based on project type and distribution needs.

**src-layout (Recommended):**
```
project_name/
├── src/
│   └── project_name/
│       ├── __init__.py
│       └── core.py
├── tests/
├── pyproject.toml
└── README.md
```

**Benefits:**
- Forces installed imports (catches import errors before users do)
- Clean separation: source vs. configuration
- Standard for published packages

**Flat Layout:**
```
project_name/
├── project_name/
│   ├── __init__.py
│   └── core.py
├── tests/
└── pyproject.toml
```

**When to use:** Simple applications, internal tools, rapid prototyping.

**Monorepo Layout:**
```
monorepo/
├── packages/
│   ├── core/
│   │   ├── src/core/
│   │   └── pyproject.toml
│   └── api/
│       ├── src/api/
│       └── pyproject.toml
└── pyproject.toml
```

**When to use:** Multiple related packages, shared development workflow.

## 2.2.2 Module Organization
<!-- Lines 104-149 -->

Modules are the organizational units of Python code. Package structure reflects architectural boundaries—group related functionality, separate unrelated concerns.

**Package vs. Module:**
- **Module**: Single `.py` file
- **Package**: Directory with `__init__.py`

**Organization Patterns:**

```
src/project_name/
├── __init__.py          # Package root (minimal exports)
├── core.py              # Core domain logic
├── models.py            # Data structures
├── services.py          # Business operations
├── exceptions.py        # Custom exceptions
└── utils/               # Subpackage for utilities
    ├── __init__.py
    └── helpers.py
```

**`__init__.py` Philosophy:**
- Keep it minimal—don't do work at import time
- Export public API explicitly
- Avoid `from .module import *`

```python
# src/project_name/__init__.py
"""Project description."""

from project_name.core import process
from project_name.models import Config

__all__ = ["process", "Config"]
```

**Circular Import Prevention:**
- Type hints: Use `TYPE_CHECKING` block
- Runtime: Import at function level if needed
- Best: Refactor to eliminate the cycle

## 2.2.3 Configuration Files
<!-- Lines 152-203 -->

Modern Python projects centralize configuration in `pyproject.toml`. This single file replaces the historical proliferation of `setup.py`, `setup.cfg`, `MANIFEST.in`, and tool-specific config files.

**pyproject.toml Structure:**

```toml
[project]
name = "project-name"
version = "0.1.0"
description = "What it does"
requires-python = ">=3.11"
dependencies = [
    "httpx>=0.24",
    "pydantic>=2.0",
]

[project.optional-dependencies]
dev = ["pytest", "ruff", "mypy"]

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[tool.ruff]
line-length = 88
target-version = "py311"

[tool.mypy]
strict = true
```

**Configuration Hierarchy:**
1. `pyproject.toml` — Project metadata, dependencies, tool config
2. `.env` — Local environment variables (not committed)
3. Tool-specific files only when `pyproject.toml` insufficient

**What Goes Where:**

| Configuration | Location |
|--------------|----------|
| Dependencies | `pyproject.toml` |
| Linter rules | `pyproject.toml [tool.*]` |
| Secrets | `.env` (gitignored) |
| CI pipeline | `.github/workflows/` |
| Pre-commit hooks | `.pre-commit-config.yaml` |

## 2.2.4 Entry Points
<!-- Lines 206-251 -->

Entry points define how users interact with your code—as a library import, CLI command, or application. Python provides multiple mechanisms for entry point definition.

**Library Entry (Default):**
Users import your package:
```python
from project_name import process
result = process(data)
```

**CLI Entry via `__main__.py`:**
Enables `python -m project_name`:
```python
# src/project_name/__main__.py
from project_name.cli import main

if __name__ == "__main__":
    main()
```

**Console Scripts (Installed Commands):**
```toml
# pyproject.toml
[project.scripts]
mycommand = "project_name.cli:main"
```

After installation: `mycommand --help`

**Application vs. Library:**

| Aspect | Library | Application |
|--------|---------|-------------|
| Entry | `import` | CLI/GUI |
| Distribution | PyPI | Container/binary |
| Dependencies | Minimal | Complete |
| Config | Parameters | Files/env vars |

**Best Practice:**
- Libraries: Focus on importable API
- Applications: Provide CLI via `__main__.py` + console_scripts
- Both: Support `python -m package_name` execution
