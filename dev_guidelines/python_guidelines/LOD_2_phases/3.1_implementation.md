## Overview
<!-- Lines 24-50 -->

Implementation transforms design artifacts into executable code. This phase applies the structures defined in the Design phase, respecting the architecture, data models, and interfaces established earlier.

**Implementation Principles:**
- Code is derivative of design—don't invent architecture while coding
- Naming is a strategic decision, not an afterthought
- Types document intent and catch errors early
- Prefer standard patterns over clever solutions

**The Implementation Hierarchy:**
```
Module (structural unit)
  └── Class/Function (behavioral unit)
      └── Block (logical unit)
          └── Expression (computational unit)
```

Each level has naming conventions, typing expectations, and organizational patterns covered in this phase.

## 3.1.1 Naming
<!-- Lines 53-77 -->

Names are the primary interface between code and humans. A well-chosen name communicates purpose, scope, and usage without requiring comments.

**Naming Hierarchy:**
| Level | Convention | Example |
|-------|------------|---------|
| Module | snake_case | `user_service.py` |
| Class | PascalCase | `UserService` |
| Function | snake_case | `get_user_by_id` |
| Variable | snake_case | `user_count` |
| Constant | UPPER_SNAKE | `MAX_RETRIES` |

**The 20-Minute Rule:**
Invest time finding the right name. A good name:
- Is unambiguous in context
- Reveals intent without comments
- Follows domain vocabulary
- Scales with scope (longer names for wider scope)

## 3.1.2 Typing
<!-- Lines 80-107 -->

Type hints serve as executable documentation and enable static analysis. They make code self-describing and catch errors before runtime.

**Typing Strategy:**
1. Always type function signatures (public API)
2. Type complex variables where inference isn't obvious
3. Use strict type checking in CI
4. Prefer concrete types over `Any`

**Basic Patterns:**
```python
def process_items(items: list[str]) -> dict[str, int]:
    """Type hints document contract."""
    return {item: len(item) for item in items}
```

**When Types Add Value:**
- Function boundaries (always)
- Complex data structures
- Public module exports
- Anywhere intent is unclear

## 3.1.3 Functions
<!-- Lines 110-138 -->

Functions are the fundamental unit of behavior. Design them to be small, focused, and testable.

**Function Design Principles:**
- Single responsibility: One reason to change
- Explicit inputs: All dependencies as parameters
- Clear outputs: Prefer return values over mutation
- Reasonable size: If scrolling required, consider splitting

**Signature Patterns:**
```python
# Good: Clear contract, sensible defaults
def fetch_users(
    limit: int = 100,
    *,
    include_inactive: bool = False,
) -> list[User]:
    ...

# Avoid: Unclear, mutable default
def fetch_users(filters={}):  # BAD
    ...
```

## 3.1.4 Iteration Patterns
<!-- Lines 141-175 -->

Python offers multiple iteration approaches. Choose based on readability and memory characteristics.

**Pattern Selection:**

| Pattern | Use When |
|---------|----------|
| `for` loop | Need index, complex logic |
| List comprehension | Simple transformation |
| Generator | Large data, memory matters |
| `map`/`filter` | Functional composition |

**Comprehension Guidelines:**
```python
# Good: Simple, readable
squares = [x ** 2 for x in numbers if x > 0]

# Avoid: Too complex
result = [f(x) for x in items if condition(x) for y in nested if other(y)]
# Prefer explicit loop when logic gets complex
```

**Vectorized Thinking:**
Prefer operations on collections over item-by-item processing:
```python
# Set operations over loops
common = set_a & set_b  # Not: [x for x in a if x in b]
```

## 3.1.5 Classes
<!-- Lines 178-212 -->

Classes organize related data and behavior. Use them when you have clear state and operations on that state.

**When to Use Classes:**
- Data with invariants to maintain
- Multiple related operations on same data
- Need for encapsulation
- Implementing a protocol/interface

**Dataclasses (Preferred for Data):**
```python
from dataclasses import dataclass

@dataclass(frozen=True)
class User:
    id: int
    name: str
    email: str
```

**Protocols (Preferred for Interfaces):**
```python
from typing import Protocol

class Repository(Protocol):
    def get(self, id: int) -> User: ...
    def save(self, user: User) -> None: ...
```

## 3.1.6 Pythonic Idioms
<!-- Lines 215-245 -->

Python has idiomatic patterns that experienced developers expect. Following them improves readability.

**Key Idioms:**
- EAFP: Easier to Ask Forgiveness than Permission
- Context managers for resource management
- Decorators for cross-cutting concerns
- Properties over getters/setters

**Context Managers:**
```python
# Resource management
with open("file.txt") as f:
    data = f.read()

# Custom context manager
from contextlib import contextmanager

@contextmanager
def timer():
    start = time.time()
    yield
    print(f"Elapsed: {time.time() - start}")
```

## 3.1.7 Error Handling
<!-- Lines 248-271 -->

Error handling communicates failure modes and enables recovery. Design errors as part of your API.

**Error Handling Principles:**
- Fail fast: Detect errors early
- Be specific: Custom exceptions for domain errors
- Provide context: Error messages should help debugging
- Don't swallow exceptions silently

**Pattern:**
```python
class UserNotFoundError(Exception):
    """Raised when user lookup fails."""
    def __init__(self, user_id: int):
        self.user_id = user_id
        super().__init__(f"User not found: {user_id}")
```

## 3.1.8 Data Serialization
<!-- Lines 274-303 -->

Serialization converts Python objects to/from external formats. Choose format based on use case.

**Format Selection:**

| Format | Use Case | Human Readable |
|--------|----------|----------------|
| JSON | APIs, configs | Yes |
| YAML | Complex configs | Yes |
| TOML | Simple configs | Yes |
| Pickle | Python-to-Python | No |
| MessagePack | Performance | No |

**JSON Pattern:**
```python
import json
from dataclasses import asdict

# Serialize
json.dumps(asdict(user))

# Deserialize with validation
User(**json.loads(data))  # Or use Pydantic
```

## 3.1.9 Common Gotchas
<!-- Lines 306-334 -->

Python has several surprising behaviors that catch developers. Know them to avoid bugs.

**Mutable Default Arguments:**
```python
# BAD: Shared list across calls
def append_to(item, items=[]):
    items.append(item)
    return items

# GOOD: Create new list each call
def append_to(item, items=None):
    if items is None:
        items = []
    items.append(item)
    return items
```

**Late Binding in Closures:**
```python
# BAD: All functions return 4
funcs = [lambda: i for i in range(5)]

# GOOD: Capture value at definition
funcs = [lambda i=i: i for i in range(5)]
```
