## The Axiom
<!-- Lines 40-44 -->

Intentionality is the meta-principle that governs all others. It states that **nothing exists by accident**. Every decision in software development—from the name of a variable to the choice of architecture—should be deliberate and defensible.

This is not perfectionism. It is not about finding the *optimal* choice every time. It is about ensuring that choices are *conscious*. The opposite of intentionality is not "wrong choice" but "no choice"—code that exists because someone copied it, because "that's how it's always done," or because the author didn't stop to think.

### Why Intentionality Matters
<!-- Lines 47-53 -->

Software systems accumulate decisions. A medium-sized project contains thousands of them: naming conventions, module boundaries, error handling strategies, dependency choices. Each decision creates path dependencies that constrain future decisions.

**Unintentional decisions compound.** A carelessly named function becomes a carelessly named module becomes a carelessly named subsystem. The cost of fixing these compounds over time as more code depends on them.

**Intentional decisions document themselves.** When you can articulate why a decision was made, you create implicit documentation. Future maintainers (including your future self) can understand not just *what* the code does but *why* it was designed that way.

### The Standard
<!-- Lines 56-67 -->

A decision is intentional if you can answer the question: **"Why this and not something else?"**

This doesn't require lengthy justification. Often the answer is simple:
- "We use `snake_case` because it's the Python convention."
- "This is a dataclass because it's a data container with no behavior."
- "We raise `ValueError` here because the input violates a documented precondition."

The point is that an answer exists and you know what it is.

## The Articulation Test
<!-- Lines 70-72 -->

The Articulation Test is the practical application of intentionality. Before committing any decision, apply this test:

### The Test
<!-- Lines 75-79 -->

**Can you explain, in one sentence, why you made this choice?**

If yes, proceed. If no, stop and think.

### Examples
<!-- Lines 82-91 -->

| Decision | Articulation | Verdict |
|----------|--------------|---------|
| Named variable `data` | "It holds the data" | **Fail** - what data? |
| Named variable `user_sessions` | "It holds active session objects for authenticated users" | **Pass** |
| Used a class | "Because classes are good practice" | **Fail** - no reasoning |
| Used a class | "Because this entity has identity and behavior that should be encapsulated" | **Pass** |
| Added a dependency | "It was in the tutorial" | **Fail** - no evaluation |
| Added a dependency | "It solves X, has good maintenance, and we evaluated Y and Z as alternatives" | **Pass** |

### The One-Sentence Rule
<!-- Lines 94-98 -->

The one-sentence constraint is important. If you need a paragraph to justify a decision, the decision may be too complex. Complex decisions should be decomposed into simpler intentional decisions.

**Exception:** Architectural decisions may require more explanation. These should be documented in Architecture Decision Records (ADRs), not in your head.

### When the Test Reveals Problems
<!-- Lines 101-111 -->

If you cannot articulate a decision, you have three options:

1. **Research:** Learn enough to make an intentional choice.
2. **Ask:** Consult someone who understands the tradeoffs.
3. **Default:** Use a well-known convention and document that you're following it.

Option 3 is valid. "We do X because it's the standard Python convention" is an intentional choice. "We do X because I don't know any better" is not.

## Domains of Intentionality
<!-- Lines 114-116 -->

Intentionality applies across all aspects of development. Here are the key domains:

### Naming
<!-- Lines 119-139 -->

Names are the most visible expression of intentionality. Every name answers the question: "What is this thing?"

**Intentional naming:**
- Reveals purpose, not implementation
- Uses consistent vocabulary across the codebase
- Considers the reader's perspective
- Follows the 20-minute rule: invest time to find the Right Name

```python
# Unintentional: What is "d"? What is "process"?
def process(d):
    return d.get("value")

# Intentional: Clear purpose, clear input
def extract_metric_value(measurement: dict) -> float:
    return measurement.get("value")
```

**Cross-ref:** → [0.5 Communication as UX](0.5_communication_ux.md)

### Structure
<!-- Lines 142-162 -->

Structure decisions define how code is organized: modules, packages, classes, functions.

**Intentional structure:**
- Each module has a single, clear responsibility
- Dependencies flow in one direction (no cycles)
- Public interfaces are minimal and stable
- Internal organization supports the public interface

```python
# Unintentional: Everything in one file "because it's small"
# utils.py with 47 unrelated functions

# Intentional: Organized by capability
# validation.py - input validation
# transformation.py - data transformation
# persistence.py - storage operations
```

**Cross-ref:** → [0.2 Structure Primacy](0.2_structure_primacy.md)

### Dependencies
<!-- Lines 165-183 -->

Every dependency is a decision to trust external code with part of your system.

**Intentional dependencies:**
- Solve a specific, identified problem
- Have been evaluated against alternatives
- Are actively maintained
- Have acceptable license terms
- Are pinned to specific versions

```python
# Unintentional: "I found this library online"
# requirements.txt: some-random-lib

# Intentional: Documented decision
# requirements.txt with comment:
# httpx==0.24.0  # Chosen over requests for async support and HTTP/2
```

### Error Handling
<!-- Lines 186-214 -->

How you handle errors reveals your assumptions about failure.

**Intentional error handling:**
- Distinguishes between expected and unexpected errors
- Provides actionable error messages
- Fails fast on invalid state
- Recovers gracefully when recovery is possible

```python
# Unintentional: Catch-all that hides problems
try:
    result = risky_operation()
except Exception:
    pass

# Intentional: Specific handling with clear purpose
try:
    result = parse_config_file(path)
except FileNotFoundError:
    result = get_default_config()  # Expected: use defaults
except json.JSONDecodeError as e:
    raise ConfigurationError(f"Invalid config at {path}: {e}") from e
```

## Anti-Patterns
<!-- Lines 217-219 -->

Unintentionality manifests in recognizable patterns:

### "It's Always Been Done This Way"
<!-- Lines 222-226 -->

Inheriting decisions without understanding them. The previous author may have had good reasons, or may have been as confused as you are now.

**Fix:** Trace decisions to their source. If the source is unknown, evaluate whether the decision still makes sense.

### Cargo Cult Programming
<!-- Lines 229-233 -->

Copying patterns without understanding their purpose. Using design patterns because they're "best practices" rather than because they solve a specific problem.

**Fix:** Before applying a pattern, articulate the problem it solves. If you can't identify that problem in your code, you don't need the pattern.

### Tutorial-Driven Development
<!-- Lines 236-240 -->

Building production systems by stitching together tutorial code. Tutorials optimize for learning, not for production.

**Fix:** Treat tutorials as inspiration, not specification. Understand *why* the tutorial makes each choice, then make your own intentional decisions.

### Resume-Driven Development
<!-- Lines 243-247 -->

Choosing technologies because they look good on a resume rather than because they solve the problem well.

**Fix:** Evaluate technologies against your actual requirements. The best technology is the one that solves your problem with the least complexity.

### Copy-Paste Without Comprehension
<!-- Lines 250-254 -->

Duplicating code (including from Stack Overflow or AI assistants) without understanding what it does.

**Fix:** Before using copied code, be able to explain every line. If you can't, you don't understand it well enough to maintain it.

### Premature Abstraction
<!-- Lines 257-263 -->

Creating abstractions before understanding the concrete cases they should cover. This is unintentional because you cannot articulate what the abstraction is *for*.

**Fix:** Wait until you have 2-3 concrete cases before abstracting. The abstraction should be obvious by then.

## Application
<!-- Lines 266-266 -->

### In Code Review
<!-- Lines 269-278 -->

Use intentionality as a review lens:

- **"Why this name?"** - Can the author articulate what this thing is?
- **"Why this structure?"** - Is the organization deliberate?
- **"Why this dependency?"** - Was it evaluated against alternatives?
- **"Why this error handling?"** - What assumptions does it encode?

Good code review is not about style preferences. It's about surfacing unintentional decisions.

### In Design
<!-- Lines 281-288 -->

Before writing code, make decisions explicit:

1. **State the problem:** What capability are you adding?
2. **Identify decisions:** What choices must you make?
3. **Articulate each choice:** Why this approach?
4. **Document significant decisions:** ADRs for architectural choices.

### In Debugging
<!-- Lines 291-299 -->

Bugs often hide in unintentional decisions. When debugging:

1. **Find the assumption:** What was assumed to be true?
2. **Trace its origin:** Why was this assumed?
3. **Evaluate the assumption:** Was it ever valid? Is it still?

Many bugs are not logic errors but intention errors—the code does what it was told, but it was told the wrong thing because someone didn't think carefully.

### In Learning
<!-- Lines 302-310 -->

When learning a new codebase or technology:

1. **Ask "why" constantly:** Why is it designed this way?
2. **Distinguish convention from decision:** Some things are conventions; others are specific choices.
3. **Look for documentation:** READMEs, ADRs, commit messages often encode intentions.

## Summary
<!-- Lines 313-322 -->

Intentionality is the foundation of professional software development. It transforms coding from a mechanical activity into a craft. Every line of code is a decision; make your decisions conscious.

**The test is simple:** Can you explain why?
