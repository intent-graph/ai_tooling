## The Axiom
<!-- Lines 40-44 -->

Structure Primacy asserts that **the organization of a system matters more than its implementation details**. Code is ephemeral—it can be rewritten, refactored, replaced. Structure is enduring—it defines what is possible and what is natural.

This principle has a corollary: **if the structure is wrong, no amount of clever code can save the system**. Conversely, if the structure is right, even mediocre code can produce a maintainable system.

### The Hierarchy of Decisions
<!-- Lines 47-60 -->

Software design is a hierarchy of decisions:

```
1. Capability: What does the system do?
2. Data Model: What information does it manage?
3. Architecture: How are components organized?
4. Interfaces: How do components communicate?
5. Algorithms: How are operations performed?
6. Code: What is the exact syntax?
```

**Structure lives in levels 2-4.** Implementation lives in levels 5-6. The principle asserts that decisions at higher levels constrain and dominate decisions at lower levels.

### Why Structure Dominates
<!-- Lines 63-78 -->

Consider two scenarios:

**Scenario A:** A well-structured system with poor function implementations.
- Functions can be rewritten one at a time
- Tests verify behavior is preserved
- The system remains coherent during improvement

**Scenario B:** A poorly-structured system with excellent function implementations.
- Changing structure requires coordinated changes across many files
- Tests must be rewritten along with structure
- The system is fragile during improvement
- Individual function excellence doesn't help overall maintainability

Structure is harder to change than code. Therefore, get structure right first.

### The Architectural Ratchet
<!-- Lines 81-87 -->

Structure decisions create a **ratchet effect**: they're easier to tighten than loosen. Adding a dependency is easy; removing it is hard. Splitting a module is easy; merging is hard. Creating an abstraction is easy; removing it is hard.

This asymmetry means structural decisions deserve more upfront thought than implementation decisions. A wrong loop can be fixed in minutes. A wrong module boundary can take weeks to repair.

## What Structure Means
<!-- Lines 90-92 -->

Structure manifests at multiple levels:

### Data Structure
<!-- Lines 95-121 -->

The shape of your data constrains everything else. Data structure includes:

- **Entities:** What things exist in your domain?
- **Attributes:** What do we know about each entity?
- **Relationships:** How do entities relate to each other?
- **Constraints:** What states are valid or invalid?

```python
# Structure: The data model
@dataclass
class User:
    id: UUID
    email: str
    created_at: datetime

@dataclass
class Session:
    id: UUID
    user_id: UUID  # Relationship: Session belongs to User
    expires_at: datetime  # Constraint: Sessions expire
```

Data structure is the most important structure. It outlives code, survives rewrites, and defines what questions you can answer.

**Cross-ref:** → [0.4 Data-Centricity](0.4_data_centricity.md)

### Module Structure
<!-- Lines 124-145 -->

How code is organized into files, packages, and namespaces:

- **Cohesion:** Related things should be together
- **Coupling:** Unrelated things should be separate
- **Dependencies:** Clear direction of dependency flow

```
# Structure: Module organization
src/
├── domain/          # Core business logic (no dependencies)
│   ├── entities.py
│   └── services.py
├── adapters/        # External interfaces (depends on domain)
│   ├── database.py
│   └── http.py
└── application/     # Orchestration (depends on both)
    └── handlers.py
```

Module structure determines what changes together and what can change independently.

### Interface Structure
<!-- Lines 148-166 -->

The contracts between components:

- **Function signatures:** Parameters, return types, side effects
- **Class interfaces:** Public methods, expected behavior
- **Module interfaces:** What a module exports

```python
# Structure: Interface definition
class UserRepository(Protocol):
    """Interface for user persistence."""

    def get(self, user_id: UUID) -> User | None: ...
    def save(self, user: User) -> None: ...
    def delete(self, user_id: UUID) -> None: ...
```

Interface structure defines how components communicate. Good interfaces enable independent evolution; bad interfaces create tight coupling.

### Control Flow Structure
<!-- Lines 169-186 -->

The shape of how data moves through the system:

- **Pipelines:** Input → Transform → Output
- **Request/Response:** Handler receives request, returns response
- **Event-driven:** Publishers emit events, subscribers react

```python
# Structure: Pipeline flow
def process_order(raw_input: dict) -> OrderResult:
    validated = validate_order(raw_input)     # Stage 1
    enriched = enrich_with_inventory(validated)  # Stage 2
    priced = calculate_pricing(enriched)      # Stage 3
    return commit_order(priced)               # Stage 4
```

## Structure Before Code
<!-- Lines 189-191 -->

The practical application of Structure Primacy is **design before implementation**.

### The Design Sequence
<!-- Lines 194-202 -->

1. **Understand the capability:** What does this feature do?
2. **Model the data:** What entities and relationships exist?
3. **Define the architecture:** How do components fit together?
4. **Specify interfaces:** What are the contracts?
5. **Then—and only then—write code.**

This is not waterfall. Steps 1-4 might take minutes for a small feature or days for a major system. The point is that you *think about structure* before you *write implementation*.

### The Cost of Skipping Design
<!-- Lines 205-213 -->

When you jump straight to code:

- You discover structural problems after writing code
- Fixing structure requires rewriting code
- You feel "too invested" to fix structure properly
- Technical debt accumulates
- The system becomes harder to understand and modify

### Minimum Viable Design
<!-- Lines 216-226 -->

Structure-first doesn't mean exhaustive upfront design. It means **enough design to start confidently**:

| Feature Size | Minimum Design |
|--------------|----------------|
| Bug fix | Understand the current structure |
| Small feature | Sketch data model and interface |
| Medium feature | Data model, interface, module placement |
| Large feature | Written design document, ADR |
| New system | Architecture document, data model, API spec |

### Signs You Skipped Design
<!-- Lines 229-235 -->

- "I'll refactor this later" (you won't)
- "I'm not sure where this should go" (structure is unclear)
- "This needs to access that private thing" (boundaries are wrong)
- "Everything depends on everything" (no clear hierarchy)
- "I need to change 12 files for this one feature" (poor cohesion)

## The Hierarchy Principle
<!-- Lines 273-275 -->

Structure should be hierarchical. Every element exists within a clear hierarchy of containment and abstraction.

### The Containment Hierarchy
<!-- Lines 278-293 -->

```
Project
└── Package
    └── Module
        └── Class/Function
            └── Block
                └── Statement
```

At each level:
- The container defines the context
- Elements at the same level are peers
- An element should understand its immediate container
- An element should not skip levels

### The Abstraction Hierarchy
<!-- Lines 296-305 -->

Higher levels deal with broader concerns:

```
Level 0: System (the mission)
Level 1: Capabilities (major features)
Level 2: Operations (specific actions)
Level 3: Implementation (how it's done)
```

### Violations of Hierarchy
<!-- Lines 308-333 -->

**Skipping levels:**
```python
# Bad: Low-level detail in high-level code
def process_order(order):
    # This function shouldn't know about SQL
    cursor.execute("INSERT INTO orders...")
```

**Inverted dependencies:**
```python
# Bad: Core domain depends on external adapter
from database import PostgresConnection  # Domain shouldn't know about Postgres

class OrderService:
    def __init__(self):
        self.db = PostgresConnection()  # Coupling to implementation
```

**Peer coupling:**
```python
# Bad: Sibling modules directly depend on each other's internals
# orders.py
from inventory._internal import _check_stock  # Reaching into sibling's internals
```

### Enforcing Hierarchy
<!-- Lines 336-357 -->

Use these techniques to maintain clean hierarchy:

1. **Dependency injection:** High-level code receives implementations, doesn't create them
2. **Interfaces:** Depend on abstractions (Protocol), not concretions
3. **Module `__all__`:** Explicitly define public interface
4. **Import discipline:** Only import from parent or declared dependencies

```python
# Good: Clean hierarchy through dependency injection
class OrderService:
    def __init__(self, repository: OrderRepository):
        self.repository = repository  # Depends on abstraction

    def create_order(self, items: list[OrderItem]) -> Order:
        order = Order(items=items)
        self.repository.save(order)
        return order
```

## Application
<!-- Lines 360-360 -->

### In New Projects
<!-- Lines 363-370 -->

When starting a new project:

1. **Define the data model first:** What entities exist? What are their relationships?
2. **Sketch the module structure:** What are the major components?
3. **Define key interfaces:** How will components communicate?
4. **Validate with a walking skeleton:** Build a minimal end-to-end flow to verify structure.

### In Existing Projects
<!-- Lines 373-380 -->

When joining or modifying an existing project:

1. **Map the current structure:** Draw the data model, module graph, dependency flow
2. **Identify structural problems:** Where are the pain points?
3. **Evolve structure incrementally:** Refactor toward better structure over time
4. **Don't add to the mess:** New code should follow good structure even if old code doesn't

### In Code Review
<!-- Lines 383-390 -->

Structure-focused review questions:

- **Does this change the structure?** If so, was it discussed?
- **Does this code fit the existing structure?** Or does it fight against it?
- **Are dependencies in the right direction?** High-level to low-level?
- **Is the data model correct?** Will it support future needs?

### In Refactoring
<!-- Lines 393-409 -->

Structure refactoring is different from code refactoring:

| Code Refactoring | Structure Refactoring |
|------------------|----------------------|
| Rename variable | Extract module |
| Extract function | Change dependency direction |
| Simplify conditional | Split or merge packages |
| Remove duplication | Redesign data model |

Structure refactoring is higher risk and higher reward. It should be:
- Planned, not accidental
- Tested at integration level
- Done in dedicated refactoring phases, not mixed with features

## Summary
<!-- Lines 412-422 -->

Structure is the skeleton of your system. Code is the flesh. You can change flesh easily; changing bones requires surgery.

**Get structure right first.** Think about data models, module boundaries, and interfaces before writing implementation code. The few minutes or hours spent on design will save days of rework.
