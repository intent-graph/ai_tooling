## The Axiom
<!-- Lines 39-48 -->

Reproducibility asserts that **software should behave identically given identical conditions**. If I run your code today and next month with the same inputs, I should get the same outputs. If I set up a new machine following your instructions, it should work the same as yours.

This is not merely a nice-to-have. Reproducibility is the foundation of:
- **Debugging:** Reproduce the bug to fix it
- **Testing:** Tests must be deterministic
- **Collaboration:** Everyone works with the same system
- **Deployment:** Production matches development
- **Science:** Results must be verifiable

### The Reproducibility Spectrum
<!-- Lines 51-62 -->

Systems exist on a spectrum:

| Level | Description | Example |
|-------|-------------|---------|
| **Deterministic** | Identical output every time | `2 + 2` → `4` |
| **Reproducible** | Same output given controlled conditions | Tests with seeded random |
| **Replicable** | Similar output with documented variation | ML training with ±1% accuracy |
| **Non-reproducible** | Cannot recreate | "It worked on my machine" |

**Goal:** Maximize determinism where possible; ensure reproducibility everywhere.

### Hidden Non-Determinism
<!-- Lines 65-80 -->

Non-determinism hides in unexpected places:

```python
# Set iteration order (Python 3.7+ preserves insertion order, but sets don't)
for item in {a, b, c}:  # Order may vary

# Dictionary key order in older Python
# Floating point across platforms
# Timestamps
# Random without seed
# Thread scheduling
# Network responses
# File system ordering (glob results)
```

### The Reproducibility Promise
<!-- Lines 83-93 -->

When you claim code is reproducible, you promise:
1. **Environment spec:** What software/versions are required
2. **Input spec:** What inputs are expected
3. **Process spec:** How to run it
4. **Output spec:** What output to expect

If any of these are missing or ambiguous, reproducibility is compromised.

## Determinism
<!-- Lines 96-98 -->

Determinism means **identical behavior every execution**. Pure functions are deterministic; side effects introduce non-determinism.

### Sources of Non-Determinism
<!-- Lines 101-143 -->

**Randomness:**
```python
# Non-deterministic
result = random.choice(options)

# Deterministic (seeded)
rng = random.Random(42)
result = rng.choice(options)
```

**Time:**
```python
# Non-deterministic
timestamp = datetime.now()

# Deterministic (injectable)
def process(data, clock=datetime.now):
    timestamp = clock()
    ...
# In tests: process(data, clock=lambda: fixed_time)
```

**External state:**
```python
# Non-deterministic: File might change
content = open("data.txt").read()

# Deterministic: Hash-verified content
content = load_verified_file("data.txt", expected_hash="abc123")
```

**Ordering:**
```python
# Non-deterministic: Set order not guaranteed
for item in some_set:
    ...

# Deterministic: Sort first
for item in sorted(some_set):
    ...
```

### Making Code Deterministic
<!-- Lines 146-187 -->

**1. Seed all randomness:**
```python
import random
import numpy as np

def setup_determinism(seed: int = 42):
    random.seed(seed)
    np.random.seed(seed)
    # For PyTorch: torch.manual_seed(seed)
    # For TensorFlow: tf.random.set_seed(seed)
```

**2. Inject time:**
```python
from typing import Callable
from datetime import datetime

Clock = Callable[[], datetime]

def create_record(data: dict, clock: Clock = datetime.utcnow) -> Record:
    return Record(data=data, created_at=clock())
```

**3. Sort unordered collections:**
```python
# Before output or comparison
def get_tags(item) -> list[str]:
    return sorted(item.tags)  # Consistent order
```

**4. Control floating point:**
```python
# Rounding for comparison
def assert_close(a: float, b: float, tolerance: float = 1e-9):
    assert abs(a - b) < tolerance

# Or use Decimal for exact arithmetic
from decimal import Decimal
price = Decimal("19.99")
```

### The Determinism Test
<!-- Lines 190-196 -->

**Can someone else run this and get the exact same result?**

If the answer is "yes, but..." there's hidden non-determinism. Document it or eliminate it.

## Environment Isolation
<!-- Lines 199-201 -->

Environment isolation ensures **code runs in controlled, predictable conditions**. Your laptop, your colleague's laptop, CI, and production should all behave the same.

### The Environment Problem
<!-- Lines 204-214 -->

Code depends on its environment:
- Python version
- Installed packages and versions
- System libraries
- Environment variables
- File system paths
- Network access

Any difference can cause different behavior or failures.

### Virtual Environments
<!-- Lines 217-237 -->

**Always use virtual environments.** Never install packages globally.

```bash
# Create isolated environment
python -m venv .venv

# Activate
source .venv/bin/activate  # Unix
.venv\Scripts\activate     # Windows

# Install packages (isolated from system Python)
pip install -r requirements.txt
```

Benefits:
- Each project has its own dependencies
- Versions don't conflict across projects
- Easy to recreate on new machines
- Matches CI/production setup

### Containers for Full Isolation
<!-- Lines 240-268 -->

When virtual environments aren't enough (system dependencies, non-Python tools), use containers:

```dockerfile
FROM python:3.11-slim

WORKDIR /app

# System dependencies
RUN apt-get update && apt-get install -y \
    libpq-dev \
    && rm -rf /var/lib/apt/lists/*

# Python dependencies
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Application code
COPY . .

CMD ["python", "main.py"]
```

Containers provide:
- Identical environment everywhere
- System library isolation
- Network isolation (when needed)
- Reproducible builds

### Environment Variables
<!-- Lines 271-297 -->

Configuration via environment variables should be documented:

```python
# Document required environment
"""
Required environment variables:
    DATABASE_URL: PostgreSQL connection string
    API_KEY: External service API key (optional, defaults to test key)
"""

import os

DATABASE_URL = os.environ["DATABASE_URL"]  # Required
API_KEY = os.environ.get("API_KEY", "test-key")  # Optional with default
```

Use `.env.example` files:

```bash
# .env.example (committed to git)
DATABASE_URL=postgresql://user:pass@localhost/dbname
API_KEY=your-api-key-here
```

## Version Pinning
<!-- Lines 300-302 -->

Version pinning ensures **the same code uses the same dependencies**. Without pinning, `pip install requests` might give different versions over time.

### The Pinning Strategy
<!-- Lines 305-323 -->

**Applications:** Pin exact versions
```
# requirements.txt for applications
requests==2.31.0
pydantic==2.5.2
sqlalchemy==2.0.23
```

**Libraries:** Allow ranges (let applications pin)
```toml
# pyproject.toml for libraries
[project]
dependencies = [
    "requests>=2.28,<3",
    "pydantic>=2.0",
]
```

### Lock Files
<!-- Lines 326-346 -->

Lock files capture the *entire* dependency tree with exact versions:

```bash
# Generate lock file
pip-compile requirements.in -o requirements.txt

# Or with pip-tools
pip freeze > requirements.lock
```

Lock file includes transitive dependencies:
```
# requirements.txt (locked)
certifi==2023.11.17    # Required by requests
charset-normalizer==3.3.2  # Required by requests
idna==3.6              # Required by requests
requests==2.31.0       # Direct dependency
urllib3==2.1.0         # Required by requests
```

### Version Pinning Tools
<!-- Lines 349-356 -->

| Tool | Use Case | Lock File |
|------|----------|-----------|
| pip-tools | Simple projects | requirements.txt |
| Poetry | Complex projects | poetry.lock |
| PDM | Modern projects | pdm.lock |
| uv | Fast installation | uv.lock |

### Updating Dependencies
<!-- Lines 359-378 -->

Pinned dependencies need maintenance:

```bash
# Check for updates
pip list --outdated

# Update lock file
pip-compile --upgrade requirements.in

# Or selectively
pip-compile --upgrade-package requests requirements.in
```

**Strategy:**
1. Update dependencies in CI on a schedule
2. Run tests with updated dependencies
3. Review and merge if tests pass
4. Pin the new versions

### Security Updates
<!-- Lines 381-395 -->

Security updates should bypass normal update caution:

```bash
# Check for vulnerabilities
pip-audit

# Or
safety check
```

Integrate into CI to fail on known vulnerabilities.

## Traceability
<!-- Lines 398-400 -->

Traceability means **every change can be tracked to its source**. When something breaks, you can find what changed and why.

### Git as Audit Trail
<!-- Lines 403-416 -->

Git history is your primary traceability tool:

```bash
# What changed?
git log --oneline

# Who changed it?
git blame file.py

# When did this line appear?
git log -S "search string" --oneline
```

### Commit Discipline
<!-- Lines 419-440 -->

Good commits enable traceability:

```bash
# Bad: Opaque
git commit -m "fix"
git commit -m "updates"

# Good: Traceable
git commit -m "Fix null pointer in user lookup when email missing"
git commit -m "Add retry logic for flaky external API (issue #123)"
```

**Commit message structure:**
```
<type>: <what changed>

<why it changed>

<references>
```

### Versioning Your Code
<!-- Lines 443-454 -->

Tag releases for easy reference:

```bash
git tag -a v1.2.3 -m "Release 1.2.3: Add user export feature"
```

Follow Semantic Versioning:
- **MAJOR:** Breaking changes
- **MINOR:** New features, backward compatible
- **PATCH:** Bug fixes, backward compatible

### Data Traceability
<!-- Lines 457-474 -->

For data pipelines, track data lineage:

```python
@dataclass
class ProcessedData:
    data: DataFrame
    source_file: str
    processed_at: datetime
    processing_version: str  # Code version that processed it
    input_hash: str  # Hash of input data
```

This enables:
- Reproducing historical results
- Debugging data issues
- Auditing transformations

### The Blame Test
<!-- Lines 477-488 -->

**If something goes wrong, can you trace back to the cause?**

- Can you identify the commit that introduced the bug?
- Can you find the PR discussion where the design was decided?
- Can you determine which version of dependencies was used?
- Can you reproduce the exact environment from that time?

If yes, you have traceability. If no, you're flying blind.

## Summary
<!-- Lines 491-501 -->

Reproducibility is the foundation of reliable software. Make code deterministic where possible. Isolate environments so behavior is consistent. Pin dependencies so versions don't drift. Trace changes so you can debug and audit.

**The test:** Can someone else, somewhere else, at some other time, reproduce your results?
