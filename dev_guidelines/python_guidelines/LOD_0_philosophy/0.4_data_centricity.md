## The Axiom
<!-- Lines 38-45 -->

Data-Centric Thinking asserts that **data structures are the primary artifact of software systems**. Code is merely the mechanism that manipulates data. When code is rewritten, the data often remains. When systems are replaced, the data migrates. Data has gravity; code orbits around it.

This principle has profound implications for how you design systems:
- Design data models before writing code
- Make data structures explicit and inspectable
- Treat code as a temporary worker, data as the permanent record

### The Primacy of Data
<!-- Lines 48-59 -->

Consider what survives across system lifetimes:

| Artifact | Lifespan | Survival Rate |
|----------|----------|---------------|
| Framework | 3-7 years | Replaced by next generation |
| Application code | 2-5 years | Rewritten periodically |
| Data model | 10-20+ years | Migrated but preserved |
| Stored data | Decades | Archived, rarely deleted |

The data model you design today will likely be with you—or your successors—for years. The code you write might be rewritten next quarter.

### The Inversion
<!-- Lines 62-74 -->

Traditional thinking: *Data exists to serve the code.*
Data-centric thinking: *Code exists to serve the data.*

This inversion changes how you approach problems:

| Traditional | Data-Centric |
|-------------|--------------|
| What functions do I need? | What data do I have? |
| How do I process this? | What transformation produces desired data? |
| What state does my code need? | What data structure represents the domain? |
| How do I optimize this algorithm? | How do I structure data for efficient queries? |

## Data Outlives Code
<!-- Lines 87-89 -->

Code rewrites are common; data migrations are expensive. This asymmetry should inform your design decisions.

### The Migration Tax
<!-- Lines 92-116 -->

Every data structure change has a cost:

```
Trivial: Add nullable column
  - Migration: ALTER TABLE ADD COLUMN
  - Risk: Low
  - Downtime: None

Moderate: Rename column
  - Migration: Deploy new code → Migrate → Clean old column
  - Risk: Medium (code/data mismatch window)
  - Downtime: None but fragile period

Expensive: Change data shape
  - Migration: Copy data → Transform → Validate → Switch
  - Risk: High
  - Downtime: Possible

Very Expensive: Split or merge entities
  - Migration: New schema → Data transformation → Code changes → Validation
  - Risk: Very high
  - Timeline: Days to weeks
```

### Design for Stability
<!-- Lines 119-151 -->

Given migration costs, design data structures that are likely to be stable:

**Ask future-oriented questions:**
- What fields might we need later? (Consider nullable additions)
- What fields might change type? (Use flexible types where uncertainty exists)
- What relationships might change? (Consider junction tables for flexibility)

**Example: User Addresses**

```python
# Rigid design (harder to evolve)
@dataclass
class User:
    street: str
    city: str
    postal_code: str
    country: str

# Flexible design (easier to evolve)
@dataclass
class Address:
    id: UUID
    user_id: UUID
    address_type: AddressType
    lines: list[str]
    postal_code: str
    country_code: str
    is_primary: bool

# Now users can have multiple addresses, address format can vary by country
```

### The Rewrite Test
<!-- Lines 154-163 -->

Before rewriting code, ask: "Will this change affect the data model?"

- **No data change:** Rewrite freely. This is refactoring.
- **Data change required:** Treat as a database migration. Plan carefully.

Code that changes frequently should be decoupled from data structures that must be stable.

## Set-Theoretic Operations
<!-- Lines 166-168 -->

Data-centric thinking embraces **set theory** as the mental model for data manipulation. Instead of thinking about individual records, think about sets of records and operations on sets.

### The Mental Model
<!-- Lines 171-188 -->

Traditional (imperative): *For each item, do something.*
Set-theoretic (declarative): *Transform this set into that set.*

```python
# Imperative: Focus on individual items
result = []
for user in users:
    if user.is_active:
        result.append(user.name)

# Set-theoretic: Focus on the transformation
result = [user.name for user in users if user.is_active]

# Even more set-theoretic: SQL-like thinking
# SELECT name FROM users WHERE is_active = true
```

### Operations on Sets
<!-- Lines 191-202 -->

Master these fundamental operations:

| Operation | Description | Python | SQL |
|-----------|-------------|--------|-----|
| Filter | Select subset matching predicate | `[x for x in s if pred(x)]` | `WHERE` |
| Map | Transform each element | `[f(x) for x in s]` | `SELECT f(col)` |
| Reduce | Aggregate to single value | `functools.reduce()` | `SUM, COUNT, AVG` |
| Join | Combine sets by key | `{**a, **b}` or merge | `JOIN` |
| Group | Partition by key | `itertools.groupby()` | `GROUP BY` |
| Sort | Order by key | `sorted(s, key=k)` | `ORDER BY` |

### Why Set Thinking Matters
<!-- Lines 205-224 -->

**1. Expresses intent clearly:**
```python
# What: Get names of premium users who logged in this month
premium_names = [
    u.name for u in users
    if u.plan == "premium" and u.last_login >= month_start
]
```

**2. Enables optimization:**
- Set operations can be parallelized
- Database engines optimize set queries
- Batch operations beat item-by-item

**3. Prevents bugs:**
- No off-by-one errors in loops
- No forgotten items
- No mutation during iteration

### Practice: Think Query First
<!-- Lines 227-245 -->

When facing a data problem, write the query before the code:

```
1. What set do I start with? (users)
2. What filter do I apply? (is_active = true)
3. What transformation? (extract name)
4. What aggregation? (count)
```

Then translate to code:

```python
active_user_count = sum(1 for u in users if u.is_active)
# Or: SELECT COUNT(*) FROM users WHERE is_active
```

## Schema as Constraint
<!-- Lines 248-250 -->

Data-centric systems use schemas and types to **make invalid states unrepresentable**. Instead of validating data at runtime, define types that cannot hold invalid data.

### The Constraint Philosophy
<!-- Lines 253-282 -->

**Runtime validation (weak):**
```python
def create_user(email: str, age: int):
    if not is_valid_email(email):
        raise ValueError("Invalid email")
    if age < 0:
        raise ValueError("Age cannot be negative")
    # Still possible to forget validation
```

**Type constraints (strong):**
```python
class Email(str):
    def __new__(cls, value: str):
        if not is_valid_email(value):
            raise ValueError(f"Invalid email: {value}")
        return super().__new__(cls, value)

class Age(int):
    def __new__(cls, value: int):
        if value < 0:
            raise ValueError(f"Age cannot be negative: {value}")
        return super().__new__(cls, value)

def create_user(email: Email, age: Age):
    # If we have an Email and Age, they are valid by construction
    ...
```

### Making Invalid States Unrepresentable
<!-- Lines 285-316 -->

**Example: Order Status**

```python
# Weak: Any combination possible
@dataclass
class Order:
    status: str  # "pending", "shipped", "delivered"
    shipped_at: datetime | None
    delivered_at: datetime | None
    # Problem: shipped_at can be set when status is "pending"

# Strong: Invalid states impossible
@dataclass
class PendingOrder:
    items: list[Item]

@dataclass
class ShippedOrder:
    items: list[Item]
    shipped_at: datetime  # Required, not optional

@dataclass
class DeliveredOrder:
    items: list[Item]
    shipped_at: datetime
    delivered_at: datetime  # Required

Order = PendingOrder | ShippedOrder | DeliveredOrder
# Cannot have delivered_at without shipped_at
```

### Validation at Boundaries
<!-- Lines 319-339 -->

Constraint types work best with **boundary validation**:

```
External Input (untrusted)
       │
       ▼
   [Boundary] ← Validate and convert to domain types
       │
       ▼
 Domain Layer (trusted, constrained types)
       │
       ▼
   [Boundary] ← Convert back for output
       │
       ▼
External Output
```

Inside the domain, you work with trusted types. Validation happens at entry; constraints guarantee correctness internally.

### Pydantic and Type Constraints
<!-- Lines 342-361 -->

Pydantic excels at boundary validation:

```python
from pydantic import BaseModel, EmailStr, conint

class UserInput(BaseModel):
    """External input - validated at boundary."""
    email: EmailStr
    age: conint(ge=0, le=150)

# Converts unvalidated dict to validated model
user = UserInput.model_validate(request_json)
# From here, user.email is guaranteed valid email string
```

## Vectorized Thinking
<!-- Lines 364-366 -->

Vectorized thinking is set-theoretic thinking applied to performance: **operate on all items at once, not one at a time**.

### The N+1 Problem
<!-- Lines 369-390 -->

The canonical anti-pattern:

```python
# N+1: One query per user (terrible)
users = get_all_users()  # 1 query
for user in users:
    orders = get_orders_for_user(user.id)  # N queries
    user.order_count = len(orders)
```

The vectorized solution:

```python
# Batch: Two queries total (good)
users = get_all_users()  # 1 query
user_ids = [u.id for u in users]
orders_by_user = get_orders_for_users(user_ids)  # 1 query, grouped
for user in users:
    user.order_count = len(orders_by_user.get(user.id, []))
```

### Think "All Items" Not "Each Item"
<!-- Lines 393-408 -->

When you catch yourself writing a loop that calls a function per item, ask:
- Can I batch this?
- Can I make one call for all items?
- Can I restructure data to avoid per-item processing?

```python
# Per-item (slow)
for product_id in product_ids:
    price = get_price(product_id)
    prices.append(price)

# Batch (fast)
prices = get_prices(product_ids)  # Single call returns dict
```

### Comprehensions Over Loops
<!-- Lines 411-432 -->

Python comprehensions express vectorized intent clearly:

```python
# Explicit loop
result = []
for x in items:
    if predicate(x):
        result.append(transform(x))

# Comprehension (preferred)
result = [transform(x) for x in items if predicate(x)]

# Generator for lazy evaluation
result = (transform(x) for x in items if predicate(x))
```

Comprehensions:
- Express intent in one line
- Are often faster (optimized C loop)
- Signal "this is a transformation" to readers

### When Loops Are Appropriate
<!-- Lines 435-446 -->

Not everything should be vectorized:

- **Side effects:** `for item in items: send_email(item)`
- **Stateful accumulation:** Requires tracking state across iterations
- **Early termination:** `for item in items: if found(item): break`
- **Complex control flow:** Multiple conditions, nested logic

The guideline: Use comprehensions for pure transformations, loops for effectful operations.

## Summary
<!-- Lines 449-458 -->

Data-centric thinking puts data structures at the center of design. Data outlives code, so design data for stability. Use set-theoretic operations to express transformations clearly. Use types and schemas to make invalid states impossible. Think in batches, not items.

**The mindset:** What data do I have? What data do I need? What transformation connects them?
