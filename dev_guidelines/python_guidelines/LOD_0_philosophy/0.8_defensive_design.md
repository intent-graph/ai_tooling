## The Axiom
<!-- Lines 37-41 -->

Defensive Design asserts that **software should assume things will go wrong and make failures visible immediately**. Rather than optimistically assuming correct inputs and smooth execution, defensive code anticipates errors and handles them explicitly.

This principle comes from the Zen of Python: *"Errors should never pass silently."* A bug that manifests immediately is easier to fix than one that corrupts data silently for weeks.

### The Defensive Mindset
<!-- Lines 44-51 -->

| Optimistic | Defensive |
|------------|-----------|
| Assume inputs are valid | Verify inputs at boundaries |
| Trust all callers | Validate function preconditions |
| Hide errors gracefully | Surface errors immediately |
| Hope for the best | Plan for the worst |

### Why Defense Matters
<!-- Lines 54-66 -->

**Silent failures are expensive:**
- Data corruption goes unnoticed
- Bugs are discovered far from their source
- Debugging becomes archaeology
- Users lose trust

**Loud failures are cheap:**
- Bugs are caught immediately
- Stack traces point to the source
- Debugging is straightforward
- Fixes are quick

### The Trade-Off
<!-- Lines 69-75 -->

Defensive code has a cost: more validation, more error handling, more code. But the alternative—debugging production data corruption at 3 AM—is far more expensive.

**Rule of thumb:** Be defensive at boundaries, trust internally. Validate what comes in; assume internal code follows contracts.

## Explicit Over Implicit
<!-- Lines 78-80 -->

The Zen of Python states: *"Explicit is better than implicit."* Defensive design makes behavior obvious, not magical.

### What "Explicit" Means
<!-- Lines 83-95 -->

**Explicit code:**
- States its assumptions
- Declares its dependencies
- Shows its side effects
- Documents its contracts

**Implicit code:**
- Relies on hidden state
- Has undeclared dependencies
- Hides side effects
- Assumes callers "just know"

### Examples of Explicit Design
<!-- Lines 98-144 -->

**Explicit imports:**
```python
# Implicit: What's in scope?
from module import *

# Explicit: Clear what's used
from module import function_a, function_b
```

**Explicit arguments:**
```python
# Implicit: What's False mean?
process_data(data, False, True, False)

# Explicit: Named arguments
process_data(data, validate=False, cache=True, log=False)
```

**Explicit defaults:**
```python
# Implicit: What happens with None?
def get_user(user_id, cache=None):
    if cache:  # What if cache is falsy but not None?
        ...

# Explicit: Clear default behavior
def get_user(user_id: int, use_cache: bool = True) -> User:
    if use_cache:
        ...
```

**Explicit return types:**
```python
# Implicit: What does this return?
def process(data):
    if valid(data):
        return transform(data)
    # Returns None implicitly

# Explicit: Clear contract
def process(data: InputData) -> OutputData | None:
    if valid(data):
        return transform(data)
    return None  # Explicit return
```

### The Principle of Least Surprise
<!-- Lines 147-168 -->

Code should do what readers expect. Surprises are bugs waiting to happen.

```python
# Surprising: "get" method modifies state
def get_user(user_id: int) -> User:
    user = db.query(User, id=user_id)
    user.last_accessed = datetime.now()  # Side effect!
    db.commit()
    return user

# Unsurprising: Separate concerns
def get_user(user_id: int) -> User:
    return db.query(User, id=user_id)

def record_access(user: User) -> None:
    user.last_accessed = datetime.now()
    db.commit()
```

## Fail-Fast Principle
<!-- Lines 171-173 -->

Fail-fast means **detecting and reporting errors at the earliest possible point**. Don't let invalid data propagate through the system.

### The Propagation Problem
<!-- Lines 176-202 -->

When errors aren't caught early:

```
Invalid input at boundary
    ↓ not validated
Passed to business logic
    ↓ partially processed
Written to database
    ↓ corrupts stored data
Read later by another process
    ↓ causes cryptic error
Debugging nightmare begins
```

When errors are caught early:

```
Invalid input at boundary
    ↓ validated immediately
ValidationError raised
    ↓ with clear message
Caller handles or surfaces error
    ↓ no corruption
Easy to fix
```

### Implementing Fail-Fast
<!-- Lines 205-245 -->

**Validate inputs immediately:**
```python
def create_user(email: str, age: int) -> User:
    # Fail fast: Check preconditions
    if not is_valid_email(email):
        raise ValueError(f"Invalid email format: {email}")
    if age < 0:
        raise ValueError(f"Age cannot be negative: {age}")

    # If we get here, inputs are valid
    return User(email=email, age=age)
```

**Use assertions for invariants:**
```python
def process_batch(items: list[Item]) -> Result:
    # Invariant: batch size must be reasonable
    assert 0 < len(items) <= 1000, f"Invalid batch size: {len(items)}"

    # Invariant: all items must be same type
    assert all(isinstance(i, Item) for i in items)

    # Process with confidence
    ...
```

**Fail on impossible states:**
```python
def handle_status(status: Status) -> str:
    if status == Status.PENDING:
        return "Waiting for processing"
    elif status == Status.COMPLETE:
        return "Processing complete"
    elif status == Status.FAILED:
        return "Processing failed"
    else:
        # Should be impossible if Status enum is complete
        raise AssertionError(f"Unknown status: {status}")
```

### When Not to Fail Fast
<!-- Lines 248-271 -->

Sometimes graceful degradation is appropriate:

- **User-facing applications:** Show friendly error messages
- **Batch processing:** Log errors, continue with valid items
- **Distributed systems:** Retry transient failures

But even in these cases, **log the failure**. Silent swallowing is never appropriate.

```python
# Graceful degradation with logging
def process_items(items: list[Item]) -> list[Result]:
    results = []
    for item in items:
        try:
            results.append(process_one(item))
        except ProcessingError as e:
            logger.error(f"Failed to process {item.id}: {e}")
            # Continue with other items
    return results
```

## Boundary Validation
<!-- Lines 274-276 -->

Boundary validation means **validating data at system boundaries**, then trusting it internally.

### What Are Boundaries?
<!-- Lines 279-287 -->

Boundaries are where untrusted data enters your system:

- **HTTP requests:** User input, external API responses
- **File reads:** Config files, data files
- **Database reads:** Could be corrupted, could be old schema
- **Environment variables:** Could be missing, malformed
- **Function parameters:** From other modules/packages

### The Validation Pattern
<!-- Lines 290-309 -->

```
Untrusted Input
       │
       ▼
   [BOUNDARY]
       │ ← Validate, parse, convert to domain types
       ▼
   Domain Types (trusted)
       │ ← No validation needed internally
       ▼
   Business Logic
       │
       ▼
   [BOUNDARY]
       │ ← Serialize to output format
       ▼
   Output
```

### Implementing Boundaries
<!-- Lines 312-355 -->

**HTTP boundary with Pydantic:**
```python
from pydantic import BaseModel, EmailStr, conint

class CreateUserRequest(BaseModel):
    """Validates external input at HTTP boundary."""
    email: EmailStr
    age: conint(ge=0, le=150)
    name: str

@app.post("/users")
def create_user(request: CreateUserRequest) -> UserResponse:
    # request is already validated - trust it
    user = user_service.create(
        email=request.email,
        age=request.age,
        name=request.name,
    )
    return UserResponse.from_domain(user)
```

**Config boundary:**
```python
@dataclass
class AppConfig:
    database_url: str
    debug: bool
    max_connections: int

    @classmethod
    def from_env(cls) -> "AppConfig":
        """Validate environment at startup."""
        database_url = os.environ.get("DATABASE_URL")
        if not database_url:
            raise ConfigurationError("DATABASE_URL is required")

        return cls(
            database_url=database_url,
            debug=os.environ.get("DEBUG", "false").lower() == "true",
            max_connections=int(os.environ.get("MAX_CONNECTIONS", "10")),
        )
```

### Trust After Validation
<!-- Lines 358-374 -->

Once data crosses a validated boundary, trust it:

```python
def process_user(user: User) -> None:
    # DON'T re-validate domain objects
    # if not is_valid_email(user.email):  # Unnecessary!
    #     raise ValueError(...)

    # DO trust the type system
    send_welcome_email(user.email)  # Known valid from boundary
```

Re-validating wastes CPU and obscures the real boundaries.

## Defensive Coding Practices
<!-- Lines 377-379 -->

Practical defensive techniques for everyday coding.

### Guard Clauses
<!-- Lines 382-406 -->

Handle edge cases first, then proceed with the main logic:

```python
# Without guards: Nested mess
def process(data, config):
    if data is not None:
        if config is not None:
            if len(data) > 0:
                # Finally, the actual logic
                ...

# With guards: Flat and clear
def process(data, config):
    if data is None:
        raise ValueError("data is required")
    if config is None:
        raise ValueError("config is required")
    if len(data) == 0:
        return []  # Early return for empty case

    # Main logic, unindented
    ...
```

### Type Narrowing
<!-- Lines 409-421 -->

Use isinstance checks to narrow types:

```python
def handle_result(result: Success | Failure) -> str:
    if isinstance(result, Success):
        # Type checker knows result is Success here
        return f"Succeeded: {result.value}"
    else:
        # Type checker knows result is Failure here
        return f"Failed: {result.error}"
```

### Defensive Copies
<!-- Lines 424-438 -->

When accepting mutable collections, consider defensive copies:

```python
class Report:
    def __init__(self, items: list[Item]):
        # Defensive copy: Changes to original list won't affect us
        self._items = list(items)

    @property
    def items(self) -> list[Item]:
        # Defensive copy: Callers can't modify our internal list
        return list(self._items)
```

### None Handling
<!-- Lines 441-460 -->

Be explicit about None:

```python
# Bad: None can sneak through
def get_name(user):
    return user.name  # AttributeError if user is None

# Good: Explicit handling
def get_name(user: User | None) -> str:
    if user is None:
        return "Unknown"
    return user.name

# Also good: Require non-None
def get_name(user: User) -> str:
    # Type signature says user can't be None
    return user.name
```

### Resource Cleanup
<!-- Lines 463-482 -->

Always clean up resources, even on error:

```python
# Bad: Connection leaks on error
def query_database():
    conn = create_connection()
    result = conn.execute(query)  # If this fails...
    conn.close()  # ...this never runs
    return result

# Good: Context manager guarantees cleanup
def query_database():
    with create_connection() as conn:
        return conn.execute(query)
    # Connection closed even if execute() raises
```

## Summary
<!-- Lines 485-495 -->

Defensive design assumes failure and makes it visible. Be explicit, not implicit. Fail fast rather than propagate errors. Validate at boundaries, trust internally. Use guard clauses, type narrowing, and resource cleanup to write robust code.

**The test:** If something goes wrong, will I find out immediately and know what happened?
