## The Axiom
<!-- Lines 35-44 -->

Polyglot Pragmatism asserts that **programming paradigms are tools, not religions**. Object-oriented, functional, and imperative styles each solve different problems well. The expert programmer chooses the paradigm that fits the problem, not the one they prefer.

Python is a **multi-paradigm language**. It supports:
- **Imperative:** Sequential statements, mutation, control flow
- **Object-Oriented:** Classes, inheritance, encapsulation
- **Functional:** First-class functions, comprehensions, immutability

This is a feature, not a bug. Different parts of your codebase may warrant different paradigms.

### The Anti-Pattern: Paradigm Dogma
<!-- Lines 47-70 -->

**OOP Dogma:** "Everything is a class"
```python
# Unnecessary class for a simple function
class StringUtils:
    @staticmethod
    def reverse(s: str) -> str:
        return s[::-1]

# Just use a function
def reverse_string(s: str) -> str:
    return s[::-1]
```

**FP Dogma:** "Never mutate anything"
```python
# Awkward immutability for a simple counter
def increment(state: dict) -> dict:
    return {**state, "count": state["count"] + 1}

# Just mutate when it's local and clear
count += 1
```

### The Pragmatic Approach
<!-- Lines 73-81 -->

Ask: **What is the dominant structure of this problem?**

- Taxonomy with shared behavior → OOP
- Data transformation pipeline → FP
- Sequential steps with I/O → Imperative

Then write code in the appropriate style.

### Code as Derivative
<!-- Lines 84-98 -->

Remember from [0.2 Structure Primacy](0.2_structure_primacy.md): code is derivative of structure. The paradigm choice should follow from the design:

```
Data Model → Architecture → Paradigm → Code
```

Not:

```
Favorite Paradigm → Force Design → Awkward Code
```

## Paradigm Selection
<!-- Lines 101-103 -->

How do you choose? Start with these questions:

### The Structure Question
<!-- Lines 106-116 -->

**What is the dominant structure?**

| Structure | Best Paradigm | Why |
|-----------|---------------|-----|
| Entity taxonomy | OOP | Classes model "is-a" relationships |
| Data pipeline | FP | Pure functions transform data |
| Step sequence | Imperative | Statements execute in order |
| Event reactions | FP/Event-driven | Handlers respond to events |
| State machine | OOP or FP | Either works; OOP for complex state |

### The Behavior Question
<!-- Lines 119-128 -->

**What kind of behavior dominates?**

| Behavior | Best Paradigm | Why |
|----------|---------------|-----|
| Polymorphic dispatch | OOP | Method dispatch by type |
| Data transformation | FP | Map/filter/reduce chains |
| I/O operations | Imperative | Side effects are sequential |
| State encapsulation | OOP | Objects hide internal state |

### The Change Question
<!-- Lines 131-141 -->

**What will change over time?**

| Change Type | Best Paradigm | Why |
|-------------|---------------|-----|
| New types with same operations | OOP | Add new classes |
| New operations on same types | FP | Add new functions |
| New steps in sequence | Imperative | Add new statements |

This is the **Expression Problem**: OOP makes adding types easy, FP makes adding operations easy.

### Python's Natural Fit
<!-- Lines 144-168 -->

Python's standard library shows paradigm mixing:

```python
# Imperative: File I/O
with open("file.txt") as f:
    content = f.read()

# Functional: Data transformation
doubled = [x * 2 for x in numbers]

# OOP: Complex state management
class HttpClient:
    def __init__(self, base_url):
        self.base_url = base_url
        self.session = requests.Session()

    def get(self, path):
        return self.session.get(f"{self.base_url}{path}")
```

The standard library doesn't choose one paradigm—it uses each where appropriate.

## OOP When
<!-- Lines 171-173 -->

Use object-oriented programming when the problem has **entities with identity, state, and behavior**.

### Strong Signals for OOP
<!-- Lines 176-227 -->

**1. Is-A Relationships (Taxonomy)**
```python
# Clear hierarchy: Animal → Mammal → Dog
class Animal:
    def speak(self) -> str:
        raise NotImplementedError

class Dog(Animal):
    def speak(self) -> str:
        return "Woof"

class Cat(Animal):
    def speak(self) -> str:
        return "Meow"
```

**2. State Encapsulation**
```python
# Object manages complex internal state
class ShoppingCart:
    def __init__(self):
        self._items: list[Item] = []
        self._discount_code: str | None = None

    def add_item(self, item: Item) -> None:
        self._items.append(item)

    def apply_discount(self, code: str) -> None:
        if self._validate_code(code):
            self._discount_code = code

    @property
    def total(self) -> Decimal:
        subtotal = sum(item.price for item in self._items)
        return self._apply_discount(subtotal)
```

**3. Resource Management**
```python
# Object manages lifecycle of a resource
class DatabaseConnection:
    def __init__(self, url: str):
        self._connection = create_connection(url)

    def __enter__(self):
        return self

    def __exit__(self, *args):
        self._connection.close()
```

### Dataclasses: OOP Without Behavior
<!-- Lines 230-249 -->

When you need structured data without behavior, use dataclasses:

```python
from dataclasses import dataclass

@dataclass
class Point:
    x: float
    y: float

# Immutable variant
@dataclass(frozen=True)
class ImmutablePoint:
    x: float
    y: float
```

Dataclasses give you OOP benefits (type safety, named fields, IDE support) without forcing you to write behavior.

### OOP Anti-Patterns in Python
<!-- Lines 252-280 -->

**God classes:** Classes that do everything
```python
# Bad: Does too much
class UserManager:
    def authenticate(self): ...
    def send_email(self): ...
    def generate_report(self): ...
    def backup_database(self): ...
```

**Anemic domain models:** Classes with only data, no behavior
```python
# Bad: Just use a dataclass or dict
class User:
    def __init__(self):
        self.name = None
        self.email = None
    # No methods, just data
```

**Deep inheritance hierarchies:**
```python
# Bad: Too deep, too coupled
class Animal(Living(Being(Entity(Thing)))): ...
```

## FP When
<!-- Lines 283-285 -->

Use functional programming when the problem is about **transforming data through a series of operations**.

### Strong Signals for FP
<!-- Lines 288-337 -->

**1. Data Pipelines**
```python
# Transform data through stages
def process_orders(raw_orders: list[dict]) -> list[ProcessedOrder]:
    return (
        raw_orders
        | validate_orders
        | enrich_with_customer_data
        | calculate_totals
        | format_for_output
    )

# Or with explicit pipes
validated = [validate(o) for o in raw_orders]
enriched = [enrich(o) for o in validated]
totaled = [calculate_total(o) for o in enriched]
```

**2. Pure Transformations**
```python
# Pure function: Same input → same output, no side effects
def calculate_discount(price: Decimal, discount_rate: float) -> Decimal:
    return price * (1 - Decimal(str(discount_rate)))

# Can be tested trivially
assert calculate_discount(Decimal("100"), 0.1) == Decimal("90")
```

**3. Higher-Order Functions**
```python
# Functions as arguments
def retry(operation: Callable, max_attempts: int = 3):
    for attempt in range(max_attempts):
        try:
            return operation()
        except Exception:
            if attempt == max_attempts - 1:
                raise

# Functions returning functions
def make_multiplier(factor: int) -> Callable[[int], int]:
    def multiply(x: int) -> int:
        return x * factor
    return multiply

double = make_multiplier(2)
triple = make_multiplier(3)
```

### Python's FP Tools
<!-- Lines 340-360 -->

```python
# Comprehensions (preferred in Python)
squared = [x**2 for x in numbers]
evens = [x for x in numbers if x % 2 == 0]

# Built-in higher-order functions
from functools import reduce

mapped = list(map(square, numbers))
filtered = list(filter(is_even, numbers))
total = reduce(add, numbers)

# itertools for complex iteration
from itertools import groupby, chain, islice

grouped = groupby(sorted(items, key=get_category), key=get_category)
chained = chain(list1, list2, list3)
first_ten = list(islice(infinite_generator, 10))
```

### FP Anti-Patterns in Python
<!-- Lines 363-381 -->

**Over-functional:** Using FP constructs where loops are clearer
```python
# Bad: Hard to read
result = reduce(lambda acc, x: acc + [f(x)] if p(x) else acc, items, [])

# Good: Comprehension
result = [f(x) for x in items if p(x)]
```

**Ignoring side effects:** Pretending I/O is pure
```python
# Bad: Hiding side effects in "pure" function
def get_user(user_id: int) -> User:  # Not pure! Calls database
    return database.query(User, id=user_id)
```

## Imperative When
<!-- Lines 384-386 -->

Use imperative programming for **sequential operations with side effects**.

### Strong Signals for Imperative
<!-- Lines 389-433 -->

**1. I/O Operations**
```python
# Sequential file operations
def backup_logs():
    source_dir = Path("/var/log/app")
    backup_dir = Path("/backup/logs")
    backup_dir.mkdir(exist_ok=True)

    for log_file in source_dir.glob("*.log"):
        shutil.copy(log_file, backup_dir / log_file.name)
        log_file.unlink()
```

**2. State Machines**
```python
# Explicit state transitions
def process_stream(stream):
    state = "IDLE"
    buffer = []

    for token in stream:
        if state == "IDLE":
            if token == "START":
                state = "READING"
        elif state == "READING":
            if token == "END":
                yield process_buffer(buffer)
                buffer = []
                state = "IDLE"
            else:
                buffer.append(token)
```

**3. Early Exit / Complex Control Flow**
```python
# Multiple exit points make sense
def find_user(criteria: dict) -> User | None:
    for source in [cache, database, external_api]:
        user = source.find(criteria)
        if user is not None:
            return user
    return None
```

### Imperative Done Well
<!-- Lines 436-472 -->

**Clear variable mutation:**
```python
# Mutation is local and obvious
total = 0
for item in items:
    total += item.price

# Not hidden in nested closures
```

**Explicit control flow:**
```python
# Conditions and loops are clear
if user.is_admin:
    grant_all_permissions(user)
else:
    grant_basic_permissions(user)
```

**Side effects at boundaries:**
```python
# Pure core, imperative shell
def main():
    # Imperative: I/O
    config = load_config()
    data = read_input()

    # Functional: Pure transformation
    result = process(data, config)

    # Imperative: I/O
    write_output(result)
```

## Summary
<!-- Lines 475-485 -->

Paradigms are tools. OOP for entities with identity and behavior. FP for data transformation pipelines. Imperative for sequential I/O and control flow. Python supports all three—use each where it fits.

**The test:** Does this paradigm make the code clearer and more maintainable, or am I using it out of habit?
