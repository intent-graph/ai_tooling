### Findings in detail

F01. Evidence: node constraint "MUST NOT pass unsanitized user input to child_process.exec or execSync, and do not enable the shell option ... with user input"; intent "never a shell string built from input". The quote is Node's own sentence, so the node is faithful to the claim, not to the purpose. A team that sanitizes and then calls exec follows the rule and ships the injection class. Admitted stronger source: OWASP OS Command Injection Defense (SRC-136, restricted to principles: avoid shell, parameterize, allowlist).

F02. Evidence: TYPES-C13 "Consider noUncheckedIndexedAccess"; TYPES-C14 "Consider exactOptionalPropertyTypes"; RUNSEC-C48 quote "Consider enabling secrets detection at the developer level"; SECRETS.5 constraint "MUST run secret detection before commit ... and rotate secrets regularly" (rotation has no quote of its own). Related ledger inconsistency: SUPPLY-C12 text says "consider" while the Node page is imperative (UPDATE.1 is therefore acceptable). INJECTION.6.2 turns "consider resolving the host name" into MUST, but the OWASP SSRF sheet supports it ("connects only to validated addresses"), so it is not counted.

F03. Evidence: decisions_for_review D1 of DEPENDENCIES: "The gates are the build's judgment; no admitted source states them"; Vue, Svelte and Solid excluded for lack of a supported-versions statement and a governance source. I checked the Vue releases page: it states no security-fix window, which agrees with the build, but Vue's security policy may live elsewhere (open, not checked). The platform-first default has no claim (FW-C46 says only that the platform offers components). Node FRAMEWORK_SHORTLIST has no constraints; the node FRAMEWORK_SHORTLIST.1 constraint is about hyphens. Declared invented rule: the gates.

F04. Evidence: node text "(the hashing is inferred, the length rule is read in the v6 docs only)"; SRVSEC-C14 "not grounded: the Node crypto page is truncated in every fetch"; epistemic state is bare `known`. A review fetch truncated the page again. SRVSEC-C05 itself is confirmed on SRC-078.
