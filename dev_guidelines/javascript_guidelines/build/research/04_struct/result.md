# Extraction result: 04_struct (STRUCT, code organization and APIs)

## L1 headline

Authoritative guidance for code organization is strong on module mechanics (T1: MDN, Node, TC39 proposal) and weak on design: layering, naming, function API shape, paradigm and state structure rest on restricted style-guide positions, one-off T2 papers and no T1; certainty: grounded for the mechanics, single-source or contested for the design choices.

Pinned:
- Claims: 67 in total; by agreement: consensus 31, majority 0, contested 5, single-source 31.
- Contested topics: cycles between modules (avoid or tolerate); top-level await as a footgun; named versus default exports; private-member marking (# versus underscore versus TypeScript private); paradigm effect on defects (functional versus procedural, one dataset).
- Register sources not read in full, and why. Every source was read through the fetch tool's digest of the passages requested, never the whole page (tool-extracted). In addition: SRC-027 (ECMAScript living draft) not read at all, the fetch truncates before the Modules section, no claim cites it; SRC-239 (Google JS guide), SRC-244 (Google TS guide), SRC-312 (Airbnb guide) only the requested sections, the Airbnb page was truncated and a first digest line "never have more than 3 parameters" was not confirmed by a second fetch, so it is not used; SRC-052 (tsconfig reference) the digest gave a wrong release number for verbatimModuleSyntax, only one isolatedModules sentence is trusted; SRC-251, SRC-258, SRC-314, SRC-254, SRC-253 only abstract and introduction read; SRC-252 (Codd) only abstract, Section 1 opening and the start of Section 2; SRC-257, SRC-259, SRC-260 PDFs extracted to text but only targeted passages read, and the extended 2018 journal version of SRC-260 was not read.

### Gaps

- Dependency direction as a layering principle: searched the register for T1 or a second independent T2; found only SRC-257 (Parnas 1972, restricted) and the lint mechanism SRC-085 (restricted, states other reasons). C60 is therefore open. Lead for audit: Parnas 1979 "Designing Software for Ease of Extension and Contraction" (IEEE TSE).
- ECMA-262 Modules section: the fetch tool returns the spec truncated at the table of contents, before section 16. Cycle evaluation order, ResolveExport ambiguity and early errors are cited through MDN and Node (mechanism column), not through the spec. A full-page reader is needed.
- State-structure design (normalisation, derived state, single source of truth) for JavaScript application state: no admitted T1; Codd (SRC-252) and Coblenz (SRC-253) give principle and taxonomy only. Immutability mechanics (Object.freeze, const) belong to slot 01 LANG.
- Function API design for application code (parameter objects, return shapes, boolean flags, optional arguments): only restricted TypeScript declaration-file rules, ESLint rule rationale and the W3C TAG positions. The Airbnb guide's treatment of parameters could not be confirmed.
- Naming: JavaScript-specific evidence absent; SRC-260's journal version and SRC-254's experiment language unchecked. Casing conventions (camelCase, PascalCase, CONSTANT_CASE) appear in the guides but were not recorded as claims because they are pure convention.
- verbatimModuleSyntax (SRC-052): the audit read it (TS 5.0, keeps non-type imports); this extraction's digest was unreliable, so no claim is made.
- Barrel files and bundle size: only one T3 synthetic measurement (C29) and one dated T2 position (C32); no T1 on load cost.
