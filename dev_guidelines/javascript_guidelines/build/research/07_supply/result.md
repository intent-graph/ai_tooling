# Research result: slot 07_supply (area SUPPLY, audit group D_supply_fw)

## L1 headline

Authoritative guidance on JavaScript dependencies and supply chain is solid on lockfiles, frozen installs, install-script blocking, trusted publishing and the limits of provenance and audit (grounded in T1 tool docs and OWASP, OpenSSF, Node.js guides), thin on whether a release-age cooldown works and on typosquatting beyond one T2 study, and in open dispute on exact pinning; certainty: grounded on what the fetch digests showed, with every quote marked tool-extracted.

Pinned:
- Claims: 42 in total by agreement: consensus 12, majority 5, contested 1, single-source 24.
- Contested topics: pin exact versus allow ranges versus rely on the lockfile (SUPPLY-C06).
- Register sources not read in full: none was read as a full verbatim page, because the fetch tool returned digests; weakest coverage: SRC-159 SLSA (overview and build-track levels page only, not the whole spec), SRC-155 OWASP NPM cheat sheet (paraphrased digest, wording unverified except where quoted), SRC-156 OWASP supply chain cheat sheet (digest of main headings), SRC-161 Scorecard (nine of the checks), SRC-078 Node security guide (supply-chain sections only), SRC-140 Node SECURITY.md (threat-model digest), SRC-142 (no verification commands shown), SRC-319 (digest), SRC-158 (two pnpm pages, digest), and every paper SRC-280 to SRC-294 (abstract pages only, full text unread).

## L2 claims

Clusters (agreement, certainty, ids):
- Every dependency is trusted code with full process privileges, and Node does not contain it; the usual route in is account or maintainership takeover. (consensus; grounded) SUPPLY-C01, C02, C31, C32
- Reproducible installs: commit the lockfile, install with a frozen lockfile, review lockfile diffs; exact pins alone leave transitive edges open. (consensus; grounded, C07 inferred) SUPPLY-C03, C04, C05, C07, C40
- Install scripts: blocked by default from npm 12 and pnpm 10; before that, disable them; treat scripts as a risk signal; git and URL dependencies refused by default in npm 12. (consensus on the pnpm and npm blocking, single-source on the rest; grounded) SUPPLY-C08, C09, C10, C11, C29
- Release-age cooldown: the mechanism exists in npm, pnpm and Dependabot; efficacy is open, resting on one T1 assertion plus vendor figures; security updates sit outside the cooldown. (consensus on mechanism; open on efficacy) SUPPLY-C12, C13, C14
- Publisher side: trusted publishing over long-lived tokens, token policy dates, 2FA. (consensus; grounded) SUPPLY-C15, C16, C17
- What provenance and signatures do and do not prove, SLSA levels, keyless signing, SBOMs. (single-source mostly; grounded) SUPPLY-C18, C19, C20, C33, C34, C37, C42
- Audit tooling: run against the lockfile; findings are triage, not exploitability; dev versus runtime split is unreliable. (consensus on triage; grounded) SUPPLY-C21, C22, C23
- Names: typosquatting checks, confusion beyond typos, scoped internal packages. (consensus on checks; single-source otherwise; grounded) SUPPLY-C24, C25, C26
- Choosing and keeping dependencies: need, maintenance signals, weak links, Scorecard as evidence, automated updates. (majority; grounded, C36 inferred) SUPPLY-C27, C28, C30, C35, C36
- Hygiene on the edges: CI token least privilege, secrets, README examples, incident response as CISA's position. (consensus on tokens) SUPPLY-C38, C39, C41

Contested topics:
- Pin exact versus ranges versus lockfile only (SUPPLY-C06): Node.js guide and OWASP say pin; OpenSSF npm guide says ranges; He et al. 2025 shows direct pinning can raise malicious-update exposure.

Gaps:
- No peer-reviewed measurement that a cooldown works (C13 open).
- Typosquatting rests on one T2 (C25); no second independent T2.
- Audit false-positive figures are two T2 studies, one measuring its own tool.
- NSA, CISA and ODNI developer guide, OpenSSF malicious-packages dataset: not in the register.
- SLSA Source track, SBOM formats and registry mirroring are not covered by read text.

### Gaps

- Efficacy of a release-age cooldown: searched the register only (SRC-078, 146, 152, 158, 319); T1 sources give behaviour, one T1 asserts "removed within hours", T3 gives vendor figures. Needs a peer-reviewed time-to-removal measurement or a registry dataset.
- Typosquatting: a second independent T2 is missing for C25; SRC-143 (scopes) does not mention typosquatting or dependency confusion.
- Install-script guidance for yarn, bun and Deno is absent; only npm and pnpm docs are in the register.
- Package manager coverage is npm and pnpm; no admitted source for yarn.
- Vendor-dependent tool lists (Socket in SRC-078; Snyk, LavaMoat, Verdaccio in SRC-155) were not used for any tool choice.
- SLSA spec read only through its overview and Build-track levels page; Source track and threats unread.
- Dependency-update policy beyond Dependabot defaults (batching, grouping, automerge): no admitted source.
- Boundary: secrets in code (C38) belongs to RUNSEC; version scope of C09 is npm before v12 only.
- I did not run a new web search in this stage; candidates below come from the audit's own gap list.
