Clusters (agreement, certainty, ids):

- Prototype pollution is the application's job, not Node core's: validate input, because Node trusts application-supplied input (consensus, grounded): C01, C42.
- Block the pollution path: no dynamic nested writes or recursive merges with untrusted keys; Map/Set or null-prototype objects; schema validation; own-property reads (consensus, grounded): C02-C07, C13.
- Partial and heavy defences: --disable-proto leaves constructor.prototype open; freezing is shallow; pollution can become RCE through Node core gadgets (consensus, grounded): C08-C11, C12 (the __proto__ accessor, single-source).
- Never build code from strings; Function is not a safe eval; parse data with JSON.parse; lint and Trusted Types as enforcement (consensus mostly, grounded): C14-C21.
- node:vm is not a sandbox; the permission model is a seat belt with known symlink and descriptor gaps (single-source and consensus, grounded; the model's strength is contested): C22, C38-C41.
- Shell injection: avoid exec and the shell option, use spawn or execFile with an argument array, prefer library calls, allowlist and least privilege (consensus, grounded): C23-C26.
- Path injection: path.isAbsolute and normalize do not confine; use trusted names; canonicalize before checking containment (the Node recipe is inferred, thin evidence): C27-C29.
- ReDoS: bound input length, avoid nested quantifiers and ambiguous alternation, anchor fully, prefer a non-backtracking engine where one exists (V8's is experimental), timeouts count as failure, heuristics are necessary not sufficient, blocks the event loop; HashDoS patch fact (consensus mostly, grounded): C30-C37.
- Trust model: all code in a Node process is trusted by the runtime (consensus, grounded): C41, C42.
- Deserialization: only language-neutral principles are grounded; none for JavaScript deserializers (consensus and single-source, grounded for the neutral principle): C43-C45.
- Secrets: no hardcoding, environment variables as the weaker channel, detection and rotation; evidence of leakage scale (consensus, majority, single-source, grounded): C46-C48.

### Reading notes

- Scope check requested by the caller. The Node threat model (SRC-140) excludes pollution that requires attacker control of input from core vulnerabilities, and says so in terms of trust: "any scenario that requires control over user input is not considered a vulnerability". The sources that treat pollution as a threat (SRC-139, SRC-137, SRC-134, SRC-277, SRC-125, SRC-132 §15.3.6) address application and library code. SRC-078, Node's own best-practices page, holds both statements: it repeats the threat-model exclusion and then lists seven mitigations for application authors. So there is no disagreement between admitted sources; the two statements answer "what does the Node project treat as its own vulnerability" and "what must a developer defend against". Recorded once, in RUNSEC-C01, as consensus; not listed as contested.
- Restrictions applied: SRC-053 used only for regex and allowlist statements; SRC-125 and SRC-130 for facts only; SRC-132 for requirement text only; SRC-133, SRC-136, SRC-138 for language-neutral principles only; SRC-250, SRC-273, SRC-275, SRC-278, SRC-279, SRC-280 for evidence with its year, never as tool recommendations. SRC-280 and SRC-276 were read but do not ground any claim row. SRC-318 and SRC-317 (T3) appear only beside a T1 source.
- Audit note confirmed: CVSS for the lodash advisory is 9.1 on the advisory page; CVE-2025-55130 is rated High on the Node project post, no 9.1 figure appears there.
- Node documentation inconsistency (kept in C38 tags, not settled): the permissions page reads "v23.5.0, v22.13.0: This feature is no longer experimental. Stability: 2 - Stable" while the CLI page labels --permission and --allow-child-process "Stability: 1.1 - Active development".

### Gaps

- **JavaScript-specific unsafe deserialization**: no admitted T1. Searched: SRC-133 (confirmed by fetch: covers PHP, Python, Java, .NET only), SRC-132 §15.1.5 (neutral). Not available in the register: Node v8.deserialize documentation, advisories for node-serialize and js-yaml before 4, the JSON.parse and __proto__ semantics in ECMA-262.
- **Path containment in Node**: SRC-127 has one sentence on path.isAbsolute; the resolve-then-prefix-then-realpath recipe is only inferred (C29). Node fs documentation is not in the register.
- **Secrets**: only language-neutral grounds (SRC-138, SRC-275). No Node or npm source on .env files, --env-file (SRC-079 documents the flag as stable from v24.10.0 and v22.21.0 but gives no security guidance), or secrets bundled into client code.
- **Annex B text**: SRC-122 unreadable through the fetch tool (table of contents only, on tc39.es multipage, the single-page anchor URL and the fundamental-objects page; raw source URLs returned 404). The __proto__ accessor semantics and duplicate-__proto__ rule in object literals are therefore grounded only through MDN (C12, C13).
- **Regex timeouts in JavaScript**: SRC-053 says to treat a timeout as failure; no admitted source says what timeout mechanism JavaScript offers (C34 states the condition). Current V8 non-backtracking engine status unknown beyond 2021 (C33).
- **Command injection on Windows** (.bat and .cmd files cannot be launched by execFile without a shell, which reopens the shell option): the fact is in SRC-126 but the guidance on handling it was not extracted as a claim.
- **eval and CSP**: the deployment-policy side (Content-Security-Policy) belongs to the web architecture guideline and is not extracted.
- **Linters**: no register source holds the ESLint rule documentation, so C18 rests on OWASP naming the rules.
